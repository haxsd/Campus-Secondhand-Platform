# 通用打包部署学习笔记：从源码到可访问网站

> 本笔记正在逐章细化。本版改成一条可以照着执行的主线：先准备环境，
> 再打包后端和前端，准备配置，启动中间件、后端和 nginx，最后逐层验证。
> 示例全部使用中性名称，不绑定任何具体项目。

## 0. 先看最终目标

最终请求链路应该是：

```text
浏览器 http://localhost
        │
        ▼
nginx：提供前端 dist，并把 /api/ 转发给后端
        │
        ▼
Java 后端：监听 8080
        │
        ├─ 数据库：my-app-mysql:3306
        ├─ 缓存：my-app-redis:6379
        └─ 消息队列：由名称服务、Broker、代理等组件协作
```

“本机能跑”通常只是 IDE 帮你准备好了 JDK、Node、数据库、环境变量和启动
顺序。部署要把这些隐含条件变成文件、命令和可检查的结果。下面每一步都写
清楚三件事：

1. 要执行什么；
2. 成功时应该看到什么；
3. 为什么需要这一步，以及做错会出现什么。

以下命令默认从工程根目录 `D:\workspace\my-app` 执行。这个路径只是示例，
换成自己的工程目录即可。

## 1. 准备工作

### 1.1 推荐目录结构

```text
D:\workspace\my-app\
├─ backend\                 Java/Spring Boot 工程
│  ├─ mvnw.cmd              Maven Wrapper
│  └─ target\               后端构建产物（不提交）
├─ frontend\                Vue 工程
│  ├─ package.json
│  ├─ package-lock.json
│  └─ dist\                 前端构建产物（不提交）
├─ deploy\
│  ├─ .env.example          配置模板
│  ├─ .env                  本机真实配置（不提交）
│  ├─ docker-compose.yml
│  └─ nginx\nginx.conf
└─ docs\
```

目录的意义是让别人能猜到文件在哪里。构建目录可以删除并重新生成，配置
模板可以提交，真实配置和密码不能提交。

### 1.2 检查 JDK、Node 和 Docker

PowerShell：

```powershell
java -version
node --version
npm --version
docker version
docker compose version
```

成功输出的关键部分类似：

```text
java version "17.0.x"
v20.x.x
10.x.x
Client: Docker Engine
Docker Compose version v2.x.x
```

Windows cmd 的命令相同。Linux/macOS 也使用同样的 `java -version`、
`node --version` 和 `docker compose version`。

如果 `java` 找不到，先确认 `JAVA_HOME` 和 PATH；如果 Docker 客户端存在但
连接失败，先启动 Docker Desktop 或 Docker Engine。不要在应用启动失败后才
发现机器根本没有容器运行时。

### 1.3 规划端口并检查冲突

示例规划：

| 服务 | 容器端口 | 宿主端口 | 用途 |
|---|---:|---:|---|
| nginx | 80 | 80 | 浏览器入口 |
| 后端 | 8080 | 8080 | Java API |
| MySQL | 3306 | 3306 | 数据库 |
| Redis | 6379 | 6379 | 缓存 |
| MQ 名称服务 | 9876 | 9876 | 服务发现 |
| MQ Broker | 10911 | 10911 | 消息服务 |

Windows 检查：

```powershell
netstat -ano | findstr ":80 :8080 :3306 :6379"
docker ps --format "table {{.Names}}\t{{.Ports}}"
```

预期是没有不认识的进程占用目标端口。端口被占用时，后面通常会看到：

```text
Error response from daemon: Ports are not available:
listen tcp 0.0.0.0:8080: bind: An attempt was made to access a socket
in a way forbidden by its access permissions.
```

先用 `docker ps` 或 `netstat -ano` 找到占用者，再决定换端口还是停止旧服务。

## 2. 后端打包

### 2.1 Maven 生命周期

Maven 生命周期是预先定义好的构建阶段。常用阶段如下：

| 阶段 | 做什么 | 是否会执行前置阶段 |
|---|---|---|
| `clean` | 删除 `target/` | 不属于 default 生命周期 |
| `compile` | 编译主源码为 class | 会准备资源和编译 |
| `test` | 编译并执行单元测试 | 会执行前面的编译阶段 |
| `package` | 打包 JAR/WAR | 会执行测试阶段 |
| `install` | 打包后安装到本机 Maven 仓库 | 会执行 package |

最常用的可发布构建：

```powershell
cd D:\workspace\my-app\backend
.\mvnw.cmd -B clean package -DskipTests
```

成功输出的结尾类似：

```text
[INFO] Building my-app 1.0.0
[INFO] --- maven-compiler-plugin:...:compile ...
[INFO] --- spring-boot-maven-plugin:...:repackage ...
[INFO] BUILD SUCCESS
```

`-DskipTests` 会跳过测试执行，但通常仍会编译测试代码；适合已经在 CI
执行过测试、现在只想快速打包的场景。`-Dmaven.test.skip=true` 会同时跳过
测试编译和测试执行，速度更快，但更容易掩盖测试代码或测试依赖的问题：

```powershell
.\mvnw.cmd -B clean package -DskipTests
.\mvnw.cmd -B clean package -Dmaven.test.skip=true
```

发布前更稳妥的顺序是先运行：

```powershell
.\mvnw.cmd -B test
```

再用 `-DskipTests` 生成最终产物。

### 2.2 Maven Wrapper

Maven Wrapper 是项目自带的 Maven 启动脚本。Windows 使用 `mvnw.cmd`，Linux
使用 `./mvnw`。第一次运行时它会下载项目指定版本的 Maven，之后复用本地
缓存，因此不要求每台机器预先安装 Maven。

`backend/.mvn/wrapper/maven-wrapper.properties` 的完整示例：

```properties
distributionUrl=https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.9/apache-maven-3.9.9-bin.zip
wrapperUrl=https://repo.maven.apache.org/maven2/org/apache/maven/wrapper/maven-wrapper/3.3.4/maven-wrapper-3.3.4.jar
distributionType=only-script
```

| 字段 | 作用 | 写错的后果 |
|---|---|---|
| `distributionUrl` | Maven 分发包地址和版本 | 下载失败或使用错误 Maven |
| `wrapperUrl` | Wrapper 自身 JAR 地址 | 第一次启动无法下载启动器 |
| `distributionType` | 下载 binary、source 等类型 | 下载体积或行为不符合预期 |

实际项目可能只有其中部分字段；以项目文件和 Wrapper 版本支持为准。

### 2.3 Maven 打包插件的关键配置

要生成能直接 `java -jar` 的 Spring Boot fat jar，`pom.xml` 中通常有：

```xml
<build>
  <plugins>
    <plugin>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-maven-plugin</artifactId>
      <version>3.3.5</version>
      <configuration>
        <mainClass>com.example.app.Application</mainClass>
      </configuration>
      <executions>
        <execution>
          <goals>
            <goal>repackage</goal>
          </goals>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
```

| 字段 | 作用 | 漏掉或写错的后果 |
|---|---|---|
| `groupId`/`artifactId` | 确定插件身份 | Maven 找不到插件 |
| `version` | 固定插件行为 | 不同机器可能产生不同产物 |
| `mainClass` | 指定应用入口 | 多入口或扫描不到入口时启动失败 |
| `repackage` | 把普通 JAR 重新包装成可执行 JAR | 只有普通 JAR，缺少嵌套依赖 |

### 2.4 `target/` 目录逐项看

打包后执行：

```powershell
Get-ChildItem target
```

常见内容：

| 路径 | 内容 | 是否部署 |
|---|---|---|
| `classes/` | 编译后的主 class 和资源 | 不单独部署 |
| `test-classes/` | 测试 class | 不部署 |
| `generated-sources/` | 插件生成的源码 | 不部署 |
| `maven-archiver/` | 归档元数据 | 不单独部署 |
| `my-app-1.0.0.jar` | 最终可执行 fat jar | 部署它 |
| `my-app-1.0.0.jar.original` | repackage 前普通 JAR | 通常不要部署 |

### 2.5 fat jar 内部结构

```powershell
jar tf target\my-app-1.0.0.jar | ForEach-Object -Begin {$i=0} -Process {if($i++ -lt 30){$_}}
jar xf target\my-app-1.0.0.jar META-INF/MANIFEST.MF
Get-Content META-INF\MANIFEST.MF
Remove-Item META-INF -Recurse -Force
```

典型输出：

```text
META-INF/
META-INF/MANIFEST.MF
BOOT-INF/
BOOT-INF/classes/
BOOT-INF/classes/com/example/app/Application.class
BOOT-INF/lib/
BOOT-INF/lib/spring-boot-3.3.5.jar
org/springframework/boot/loader/
```

Manifest 重点字段类似：

```text
Main-Class: org.springframework.boot.loader.launch.JarLauncher
Start-Class: com.example.app.Application
```

`BOOT-INF/classes` 放自己的 class 和资源，`BOOT-INF/lib` 放依赖。启动时
`Main-Class` 先启动 Spring Boot Loader，Loader 再把嵌套 JAR 加入 classpath，
最后调用 `Start-Class`。所以 fat jar 能在不把依赖解压到系统目录的情况下运行。

### 2.6 故意启动错误的 `.jar.original`

先确认主 JAR：

```powershell
Get-ChildItem target\*.jar
java -jar target\my-app-1.0.0.jar
```

故意启动原始 JAR：

```powershell
java -jar target\my-app-1.0.0.jar.original
```

常见错误：

```text
no main manifest attribute, in target/my-app-1.0.0.jar.original
```

或：

```text
Error: Could not find or load main class ...
Caused by: java.lang.ClassNotFoundException: ...
```

根因是 `.jar.original` 没有 Spring Boot Loader 和嵌套依赖，不能当成发布
产物。部署脚本应明确排除它。

## 3. 前端打包

### 3.1 `npm ci` 和 `npm install`

`package.json` 描述依赖范围，`package-lock.json` 锁定实际解析到的版本和
依赖树。发布环境应优先使用锁文件：

| 命令 | 行为 | 适合场景 |
|---|---|---|
| `npm ci` | 删除现有 `node_modules`，严格按 lock 安装 | CI、发布、可重复构建 |
| `npm install` | 解析依赖，可能更新 lock | 开发时新增或升级依赖 |

如果 `package.json` 和 lock 不一致，`npm ci` 会直接失败，而不是悄悄修改
lock。这种“严格失败”是优点，因为它能阻止不同机器构建出不同结果。

```powershell
cd D:\workspace\my-app\frontend
npm ci
npm run build
```

成功输出通常类似：

```text
added 412 packages
vite v5.x.x building for production...
✓ 128 modules transformed.
dist/index.html                   0.52 kB
dist/assets/index-Ab12Cd34.js   183.20 kB │ gzip: 58.41 kB
✓ built in 4.21s
```

### 3.2 `vite build` 输出怎么看

| 输出 | 含义 | 注意事项 |
|---|---|---|
| `modules transformed` | 已编译的模块数 | 不是页面数量 |
| `dist/index.html` | 浏览器入口 | 没有它 nginx 无法提供首页 |
| `assets/*.js`/`*.css` | 打包后的资源 | 文件名 hash 用于缓存失效 |
| `gzip` | gzip 压缩后的估算大小 | 不是磁盘原始大小 |
| `chunk size warning` | 某个 JS chunk 偏大 | 警告不一定阻止发布，但影响首屏 |

chunk 过大时可按需路由、动态 `import()`、拆分第三方依赖，或检查是否把
大型 JSON 和图片直接打进 JavaScript。不要为了消除警告盲目拆包，先看真实
加载路径和性能数据。

### 3.3 `base` 和子路径部署

根路径部署：

```js
import { defineConfig } from 'vite'

export default defineConfig({
  base: '/',
})
```

部署在 `https://example.com/my-app/`：

```js
import { defineConfig } from 'vite'

export default defineConfig({
  base: '/my-app/',
})
```

`base` 会影响资源 URL 和路由基准。设置成 `/my-app/` 却部署在域名根路径，
浏览器会请求错误的 `/my-app/assets/...`；反过来也会导致子路径下资源找不到。

### 3.4 动手检查前端产物

```powershell
Test-Path dist\index.html
Get-ChildItem dist -Recurse -File | ForEach-Object -Begin {$i=0} -Process {if($i++ -lt 20){$_.FullName + " " + $_.Length}}
```

预期：

```text
True
```

如果 `dist/index.html` 不存在，先不要启动 nginx。nginx 启动成功也无法
凭空生成前端文件。

## 4. 准备配置

### 4.1 三件配置文件的完整示例

主配置 `src/main/resources/application.yml`：

```yaml
spring:
  application:
    name: my-app
  profiles:
    active: ${SPRING_PROFILES_ACTIVE:dev}
  datasource:
    url: ${DB_URL:jdbc:mysql://localhost:3306/my_app?serverTimezone=Asia/Shanghai&characterEncoding=utf8}
    username: ${DB_USERNAME:app}
    password: ${DB_PASSWORD:}
  data:
    redis:
      host: ${REDIS_HOST:localhost}
      port: ${REDIS_PORT:6379}
server:
  port: ${APP_PORT:8080}
app:
  jwt:
    secret: ${APP_JWT_SECRET:change-this-in-dev}
  mq:
    topic: ${APP_MQ_TOPIC:my_app_order_timeout}
```

开发配置 `application-dev.yml`：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 5
  data:
    redis:
      database: 0
logging:
  level:
    com.example.app: DEBUG
app:
  file-dir: ${APP_FILE_DIR:./tmp/uploads}
```

生产配置 `application-prod.yml`：

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: ${DB_POOL_SIZE:20}
  data:
    redis:
      database: ${REDIS_DATABASE:0}
logging:
  level:
    root: INFO
    com.example.app: INFO
app:
  file-dir: ${APP_FILE_DIR:/var/lib/my-app/uploads}
```

### 4.2 字段解释

| 字段 | 作用 | 漏掉或写错的后果 |
|---|---|---|
| `spring.application.name` | 应用名、日志和监控标识 | 多服务日志难以区分 |
| `spring.profiles.active` | 选择环境配置 | 可能误用开发配置 |
| `spring.datasource.url` | 数据库连接地址和时区 | 连错库或时间转换错误 |
| `username/password` | 数据库认证 | 密码为空时连接失败 |
| Redis `host/port` | 缓存地址 | 应用连接本机而不是容器 |
| `server.port` | 后端监听端口 | nginx upstream 连接失败 |
| JWT `secret` | 签名登录 Token | 为空或太短会启动失败或不安全 |
| `app.mq.topic` | 消息 Topic 名 | 生产消费使用不同 Topic |

配置文件中的空默认值 `${DB_PASSWORD:}` 意味着“没有配置就为空”。生产中
应该改成启动必填校验，而不是接受空密码。

### 4.3 外部化配置优先级

Spring Boot 常用优先级从高到低可以记为：

```text
命令行参数
  >
SPRING_APPLICATION_JSON
  >
环境变量
  >
profile 配置文件
  >
主配置文件
  >
代码默认值
```

每一级的实际例子：

```powershell
# 1. 命令行参数，最高
java "-Dserver.port=9090" -jar app.jar --server.port=9091

# 2. SPRING_APPLICATION_JSON
$env:SPRING_APPLICATION_JSON='{"server":{"port":9092}}'

# 3. 环境变量
$env:SERVER_PORT='9093'

# 4. application-prod.yml
server:
  port: 9094

# 5. application.yml
server:
  port: 8080
```

同一个属性同时出现时，前面的高优先级值覆盖后面的值。命令行示例中
`--server.port=9091` 比 JVM `-Dserver.port=9090` 更高，这是因为它们属于
不同配置来源。

### 4.4 占位符与 relaxed binding

`${VAR:default}` 的意思是读取 `VAR`，不存在时使用 `default`：

```yaml
server:
  port: ${APP_PORT:8080}
app:
  db:
    url: ${DB_URL:${DEFAULT_DB_URL:jdbc:mysql://localhost:3306/my_app}}
```

后一个例子是嵌套占位符：先找 `DB_URL`，没有再找 `DEFAULT_DB_URL`，都没有
才使用 JDBC 默认值。

Spring Boot 的 relaxed binding（宽松绑定）允许不同命名风格映射到同一属性：

```text
app.jwt.secret
APP_JWT_SECRET
app_jwt_secret
```

常见规则是点、短横线和下划线可以互相对应，环境变量通常转成大写并把点换成
下划线。数组和数字下标还会有额外规则，复杂配置应查框架文档并实际打印
生效配置。

### 4.5 profile 激活

三种常见写法：

```powershell
java -jar app.jar --spring.profiles.active=prod
$env:SPRING_PROFILES_ACTIVE='prod'
```

也可以在配置中写：

```yaml
spring:
  profiles:
    active: dev
```

命令行和环境变量通常比配置文件优先。多个 profile 可以叠加：

```powershell
java -jar app.jar --spring.profiles.active=prod,region-cn
```

文件会按 profile 顺序合并，后加载的同名属性覆盖先加载的属性。不要同时
激活互相冲突的两个环境而不做说明。

### 4.6 三种 shell 设置环境变量

PowerShell 当前窗口：

```powershell
$env:DB_PASSWORD = 'example-only'
java -jar app.jar
```

Windows cmd 当前窗口：

```cmd
set DB_PASSWORD=example-only
java -jar app.jar
```

Linux bash 当前命令或当前 shell：

```bash
export DB_PASSWORD='example-only'
java -jar app.jar
```

这些写法默认只影响当前 shell 或子进程。关闭窗口后是否保留，取决于你是否
写入系统环境变量；生产环境不要把密码直接写进共享脚本。

### 4.7 PowerShell 的 `-D` 参数坑

不要依赖 PowerShell 把复杂参数自动按你想的方式传给 Java。把整个 JVM 参数
包在双引号里：

```powershell
java "-Duser.timezone=Asia/Shanghai" "-Dserver.port=8080" -jar app.jar
```

错误拆分时可能出现：

```text
Error: Could not find or load main class ...
```

根因不是 Java 找不到业务 class，而是 shell 把参数拆坏后，Java 把错误的
字符串当成了主类名。脚本中也可以使用参数数组，避免长命令被 shell 重新解释。

### 4.8 故意缺少必填变量

把配置改成没有默认值：

```yaml
app:
  jwt:
    secret: ${APP_JWT_SECRET}
```

再启动：

```powershell
Remove-Item Env:APP_JWT_SECRET -ErrorAction SilentlyContinue
java "-Duser.timezone=Asia/Shanghai" -jar app.jar
```

典型报错：

```text
Caused by: java.lang.IllegalArgumentException:
Could not resolve placeholder 'APP_JWT_SECRET' in value "${APP_JWT_SECRET}"
```

读这段错误要找三件事：`Could not resolve placeholder` 表示占位符没有值；
单引号中的变量名告诉你要设置哪个变量；最外层的 Bean 或配置类告诉你是哪
个功能在读取它。修法是设置变量、提供安全的开发默认值，或在部署前做配置
检查，而不是把生产密码写回源码。

## 5. 启动中间件

### 5.1 完整 Compose 文件

下面是一个教学用的完整 `docker-compose.yml`。它包含数据库、缓存和 nginx
三个服务；nginx 依赖前两个服务健康，但它不会自动等待 Java 后端，因为后端
由宿主机单独启动。

```yaml
name: my-app

services:
  mysql:
    image: mysql:8.4
    container_name: my-app-mysql
    restart: unless-stopped
    environment:
      MYSQL_ROOT_PASSWORD: ${MYSQL_ROOT_PASSWORD:?MYSQL_ROOT_PASSWORD is required}
      MYSQL_DATABASE: ${MYSQL_DATABASE:-my_app}
      MYSQL_USER: ${MYSQL_USER:-app}
      MYSQL_PASSWORD: ${MYSQL_PASSWORD:?MYSQL_PASSWORD is required}
      TZ: ${TZ:-Asia/Shanghai}
    ports:
      - "${MYSQL_PORT:-3306}:3306"
    volumes:
      - mysql-data:/var/lib/mysql
      - ./sql:/docker-entrypoint-initdb.d:ro
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h localhost -u root -p$${MYSQL_ROOT_PASSWORD}"]
      interval: 10s
      timeout: 5s
      retries: 12

  redis:
    image: redis:7-alpine
    container_name: my-app-redis
    restart: unless-stopped
    command: ["redis-server", "--appendonly", "yes"]
    ports:
      - "${REDIS_PORT:-6379}:6379"
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 12

  nginx:
    image: nginx:1.27-alpine
    container_name: my-app-nginx
    restart: unless-stopped
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
    ports:
      - "${HTTP_PORT:-80}:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ../frontend/dist:/usr/share/nginx/html:ro
    profiles: ["web"]

volumes:
  mysql-data:
  redis-data:
```

### 5.2 `.env` 完整示例

```dotenv
MYSQL_ROOT_PASSWORD=example-root-password
MYSQL_DATABASE=my_app
MYSQL_USER=app
MYSQL_PASSWORD=example-app-password
MYSQL_PORT=3306
REDIS_PORT=6379
HTTP_PORT=80
TZ=Asia/Shanghai
```

不要把这份包含生产密码的文件提交。提交 `.env.example` 时把密码改成
占位符，并在部署前复制为 `.env`。

### 5.3 Compose 字段解释

| 字段 | 作用 | 漏掉或写错的后果 |
|---|---|---|
| `name` | Compose project 名 | 可能与别的目录撞名，互认 orphan |
| `services` | 服务集合 | 不声明服务就不会被当前文件管理 |
| `image` | 使用的镜像和版本 | 不固定版本可能每次拉到不同内容 |
| `container_name` | 容器显示名称 | 名称冲突会导致创建失败 |
| `restart` | 进程退出后的重启策略 | 宕机后不会自动恢复 |
| `environment` | 注入容器变量 | 数据库初始化参数缺失 |
| `ports` | 宿主端口映射到容器端口 | 宿主端口被占用或外部访问不到 |
| `volumes` | 数据或配置挂载 | 容器删除后数据丢失 |
| `healthcheck` | 定义“服务可用”的检测 | 只看进程存在，依赖可能仍不可用 |
| `depends_on` | 定义启动依赖 | 不等于所有业务都已就绪 |
| `condition` | 等待健康或成功完成 | 写错会导致顺序不符合预期 |
| `profiles` | 可选服务组 | 不带 profile 时 nginx 不会启动 |

启动：

```powershell
Copy-Item .env.example .env
docker compose --env-file .env --profile web up -d
```

成功输出的关键部分类似：

```text
✔ Network my-app_default Created
✔ Container my-app-mysql Healthy
✔ Container my-app-redis Healthy
✔ Container my-app-nginx Started
```

### 5.4 镜像、容器和卷实验

不挂卷时，数据写在容器可写层：

```powershell
docker run --name demo-no-volume redis:7-alpine sh -c "echo data > /tmp/demo.txt; sleep 300"
docker exec demo-no-volume cat /tmp/demo.txt
docker rm -f demo-no-volume
docker run --name demo-no-volume redis:7-alpine test -f /tmp/demo.txt
```

最后一条通常失败，因为新容器没有旧容器的可写层。

挂命名卷时：

```powershell
docker volume create demo-data
docker run --name demo-with-volume -v demo-data:/data redis:7-alpine sh -c "echo data > /data/demo.txt; sleep 300"
docker exec demo-with-volume cat /data/demo.txt
docker rm -f demo-with-volume
docker run --rm -v demo-data:/data redis:7-alpine cat /data/demo.txt
docker volume inspect demo-data
docker volume rm demo-data
```

最后的 `cat` 仍能读到 `data`。卷独立于容器，所以容器可替换而数据保留。

### 5.5 `ports` 的方向和冲突

```yaml
ports:
  - "8081:80"
```

左边是宿主端口，右边是容器端口：访问宿主 `8081` 会进入容器 `80`。写成
`80:8081` 不是“交换顺序”，而是另一种映射。

端口冲突常见报错：

```text
Error response from daemon: driver failed programming external connectivity:
Bind for 0.0.0.0:80 failed: port is already allocated
```

或：

```text
listen tcp 0.0.0.0:8080: bind: address already in use
```

排查：

```powershell
docker ps --format "table {{.Names}}\t{{.Ports}}"
netstat -ano | findstr :80
```

### 5.6 命名卷、绑定挂载和匿名卷

| 类型 | 写法 | 优点 | 风险 |
|---|---|---|---|
| 命名卷 | `mysql-data:/var/lib/mysql` | Docker 管理，适合数据库 | 需要记住卷名和归属 |
| 绑定挂载 | `./sql:/docker-entrypoint-initdb.d:ro` | 直接映射宿主文件 | 路径和权限受宿主影响 |
| 匿名卷 | `/var/lib/mysql` | 写法简单 | 不易定位和备份 |

Compose 会把逻辑卷名拼成：

```text
<project>_<volume>
my-app_mysql-data
```

把 project 从 `my-app` 改成 `my-app-v2`，即使 YAML 中仍写
`mysql-data`，也可能得到另一套物理卷。结果是“数据库像空了一样”，因为
新容器挂载了新卷。改项目名必须同时盘点旧卷、迁移数据和回滚方案。

### 5.7 Compose project、orphan 和危险清理

默认 project name 通常取 Compose 文件所在目录名。两个不同项目如果都放在
叫 `deploy` 的目录里，默认名就可能都是 `deploy`。Compose 通过容器标签判断
归属，而不是通过“这个容器是谁创建的”判断：

```powershell
docker inspect --format '{{index .Config.Labels "com.docker.compose.project"}}' my-app-mysql
```

如果两个项目标签相同，项目 A 的 YAML 没有声明项目 B 的容器时，执行 `up`
可能看到：

```text
Found orphan containers ([other-app-db]) for this project.
```

`--remove-orphans` 会删除当前 project 标签下、但当前 YAML 没声明的容器，
所以可能误删另一个项目。正确做法是给每组服务唯一项目名：

```yaml
name: my-app
```

并在操作前查看：

```powershell
docker ps -a
docker inspect --format '{{.Name}} {{index .Config.Labels "com.docker.compose.project"}}' my-app-mysql
```

### 5.8 Compose 命令危险度

| 命令 | 作用 | 风险 |
|---|---|---|
| `up -d` | 创建或更新并后台运行 | 中 |
| `stop` | 停止容器，不删除 | 低 |
| `rm` | 删除已停止容器 | 中 |
| `logs -f` | 查看并跟随日志 | 低 |
| `exec` | 进入运行中的容器执行命令 | 中 |
| `down` | 删除当前项目容器和网络 | 中 |
| `down -v` | 额外删除当前项目卷 | 高 |
| `up --remove-orphans` | 额外删除 orphan 容器 | 高 |

数据库环境优先使用 `stop`，需要重建容器时才用 `down`；除非已经确认备份
和卷归属，不要使用 `down -v`。

### 5.9 数据库初始化和卷权限

MySQL 官方镜像的 `/docker-entrypoint-initdb.d` 脚本通常只在数据目录为空的
第一次初始化时执行。修改初始化 SQL 后，对已有卷执行 `up` 不会自动补表或
补索引。已有数据库要用版本化迁移；Flyway 和 Liquibase 都可以记录并执行
这种 schema（数据库结构）升级。

卷权限问题的典型现象：

```text
Permission denied
Failed to open ...
container exited with code 1
```

排查：

```powershell
docker logs my-app-mysql
docker inspect my-app-mysql
docker exec my-app-mysql id
docker exec my-app-mysql ls -ln /var/lib/mysql
```

宿主机初始化目录可能属于 root，而容器进程使用非 root UID。修复应让目录
属主匹配镜像要求，或用一次性的权限初始化容器；不要长期把中间件改成 root
运行来掩盖问题。

### 5.10 故意制造 orphan 警告

准备两个目录，但目录名都叫 `deploy`：

```text
D:\lab\a\deploy\docker-compose.yml
D:\lab\b\deploy\docker-compose.yml
```

两个文件都声明同名服务：

```yaml
services:
  demo:
    image: redis:7-alpine
    container_name: demo-shared-name
```

先在第一个目录运行：

```powershell
docker compose up -d
```

再在第二个目录运行：

```powershell
docker compose up -d
```

可能看到：

```text
Found orphan containers ([demo-shared-name]) for this project.
```

停止并删除实验容器后，在两个文件分别增加不同的顶层名称：

```yaml
name: demo-a
```

和：

```yaml
name: demo-b
```

重新执行 `up -d`，两个 project 标签不同，orphan 警告应消失。实验结束：

```powershell
docker compose down
docker ps -a
```

## 6. 启动后端

### 6.1 启动命令

先确认中间件健康，再启动 fat jar：

```powershell
docker compose ps
java "-Duser.timezone=Asia/Shanghai" "-Dserver.port=8080" `
  -jar backend\target\my-app-1.0.0.jar
```

成功日志关键行类似：

```text
Tomcat initialized with port 8080 (http)
Tomcat started on port 8080
Started Application in 3.842 seconds
```

`-Duser.timezone` 要在 JVM 参数中设置，因为定时任务和延迟消息时间计算
发生在 Java 进程内。数据库连接串也应使用同一时区；两者不一致时，算出的
目标时间可能已经过去，延迟消息会立即投递。

### 6.2 健康检查

如果项目启用了 Actuator：

```powershell
curl.exe -i http://localhost:8080/actuator/health
```

成功输出：

```text
HTTP/1.1 200
Content-Type: application/vnd.spring-boot.actuator.v3+json

{"status":"UP"}
```

返回 200 只能说明应用和已配置的健康检查通过，不能替代完整业务测试。

### 6.3 启动失败对照

端口占用：

```text
Web server failed to start. Port 8080 was already in use.
```

检查 `netstat -ano | findstr :8080`，停止旧进程或换端口。

数据库连接失败：

```text
Communications link failure
The driver has not received any packets from the server.
```

先检查数据库容器健康、端口、主机名和连接串。Compose 网络内应使用服务名
如 `mysql`，宿主机进程访问容器则通常使用 `localhost` 加映射端口。

配置缺失：

```text
Could not resolve placeholder 'APP_JWT_SECRET' in value "${APP_JWT_SECRET}"
```

设置变量或选择正确 profile，不要在日志中打印真实密钥。

## 7. 启动 nginx 并接通前端

### 7.1 完整 nginx.conf

下面是一份可以作为起点的完整文件：

```nginx
events {
    worker_connections 1024;
}

http {
    include       /etc/nginx/mime.types;
    default_type  application/octet-stream;

    log_format main '$remote_addr - $remote_user [$time_local] "$request" '
                    '$status $body_bytes_sent "$http_referer" '
                    '"$http_user_agent" "$http_x_forwarded_for"';
    access_log /var/log/nginx/access.log main;
    error_log  /var/log/nginx/error.log warn;

    sendfile on;
    keepalive_timeout 65;
    gzip on;
    gzip_types text/plain text/css application/json application/javascript
               application/xml image/svg+xml;

    server {
        listen 80;
        server_name _;
        root /usr/share/nginx/html;
        index index.html;

        location = /healthz {
            access_log off;
            return 200 "ok\n";
        }

        location /api/ {
            proxy_pass http://host.docker.internal:8080;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }

        location / {
            try_files $uri $uri/ /index.html;
        }
    }
}
```

字段和漏配后果：

| 字段 | 作用 | 漏掉的后果 |
|---|---|---|
| `events` | nginx 连接处理基础配置 | 配置不完整，nginx 无法启动 |
| `worker_connections` | 单 worker 最大连接数 | 并发较高时连接不足 |
| `http` | HTTP 服务配置上下文 | `server` 无法生效 |
| `mime.types` | 文件扩展名到 Content-Type 的映射 | JS/CSS 类型错误 |
| `log_format` | 定义访问日志格式 | 排查缺少请求信息 |
| `access_log` | 记录访问请求 | 不知道请求是否到达 nginx |
| `error_log` | 记录代理和配置错误 | 502 等问题难以定位 |
| `sendfile` | 高效发送静态文件 | 性能较低但不是功能必需 |
| `gzip` | 压缩文本资源 | 页面传输体积更大 |
| `listen` | nginx 监听端口 | 浏览器连不上 |
| `root` | 静态文件目录 | 首页返回 404 |
| `location /api/` | API 请求入口 | API 可能被当成静态文件 |
| `proxy_pass` | 后端转发地址 | 出现 502 或路径错误 |
| `proxy_set_header` | 保留原始请求信息 | 后端拿到网关 IP 或错误协议 |
| `try_files` | SPA 路由回退 | 刷新子路由返回 404 |

### 7.2 `location` 匹配优先级

常用优先级可以记为：

```text
= 精确匹配
> ^~ 前缀匹配（阻止后续正则）
> 正则匹配
> 普通最长前缀匹配
```

给出规则：

```nginx
location = /healthz { ... }
location ^~ /assets/ { ... }
location ~* \.(css|js)$ { ... }
location / { ... }
```

请求演算：

| URL | 命中规则 | 原因 |
|---|---|---|
| `/healthz` | `= /healthz` | 精确匹配最高 |
| `/assets/app.js` | `^~ /assets/` | `^~` 前缀阻止正则继续 |
| `/main.css` | `~* \.(css|js)$` | 普通前缀 `/` 后再匹配正则 |
| `/orders/1` | `/` | 没有更具体规则 |

### 7.3 `proxy_pass` 末尾斜杠的四种组合

假设请求是 `/api/users`，`location` 是 `/api/`：

| location | proxy_pass | 常见转发结果 |
|---|---|---|
| `/api/` | `http://backend:8080` | `http://backend:8080/api/users` |
| `/api/` | `http://backend:8080/` | `http://backend:8080/users` |
| `/api` | `http://backend:8080` | 保留原 URI，通常是 `/api/users` |
| `/api` | `http://backend:8080/` | 按匹配前缀替换，需用实际请求验证 |

最容易出错的是后端实际接口是 `/api/users`，却配置成第二种，后端收到
`/users` 后返回 404。每次改变斜杠，都用后端访问日志确认实际收到的 URL。

### 7.4 转发头

| Header | 作用 | 漏掉的后果 |
|---|---|---|
| `Host` | 原始域名 | 多域名路由或生成链接错误 |
| `X-Real-IP` | 直接客户端 IP | 后端只看到 nginx 地址 |
| `X-Forwarded-For` | 代理链 IP | 审计和限流拿不到真实来源 |
| `X-Forwarded-Proto` | 原始 HTTP/HTTPS | HTTPS 请求被后端重定向成 HTTP |

后端必须只信任自己管理的代理发送的这些头，否则客户端可以伪造 IP。

### 7.5 SPA history 和 host.docker.internal

浏览器刷新 `/orders/123` 时，会直接请求 nginx 的 `/orders/123`。磁盘上通常
没有这个文件，所以必须：

```nginx
try_files $uri $uri/ /index.html;
```

故意删除这行并 reload：

```powershell
docker exec my-app-nginx nginx -s reload
curl.exe -i http://localhost/orders/123
```

错误实验输出：

```text
HTTP/1.1 404 Not Found
```

恢复后再次请求应返回 `index.html`，通常是 `HTTP/1.1 200 OK`。

Docker Desktop 上，`host.docker.internal` 让容器访问宿主机进程。Linux 上
可能需要在 Compose 中加入：

```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```

或者直接让后端也进入 Compose 网络，nginx 使用服务名 `backend:8080`，这通常
比依赖宿主机地址更稳定。

### 7.6 nginx 运维命令

```powershell
docker exec my-app-nginx nginx -t
docker exec my-app-nginx nginx -s reload
docker logs my-app-nginx
docker exec my-app-nginx tail -n 50 /var/log/nginx/access.log
docker exec my-app-nginx tail -n 50 /var/log/nginx/error.log
```

成功语句：

```text
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
```

故意删掉一个分号：

```text
nginx: [emerg] unexpected "}" in /etc/nginx/nginx.conf:...
nginx: configuration file /etc/nginx/nginx.conf test failed
```

先恢复配置并通过 `nginx -t`，再 reload。不要直接 reload 未验证的文件。

## 8. 逐层验证部署成功

### 8.1 浏览器层

```powershell
curl.exe -i http://localhost/
curl.exe -i http://localhost/healthz
```

预期：

```text
HTTP/1.1 200 OK
```

浏览器 DevTools 的 Network 应看到首页、JS、CSS 和 API 请求。首页失败说明
先查 nginx 或静态文件；页面能开但 API 失败，不要先重装前端。

### 8.2 nginx 层

```powershell
docker exec my-app-nginx nginx -t
docker logs my-app-nginx --tail 50
```

`nginx -t` 成功但 API 返回 502，通常是 upstream 地址、端口或后端进程问题。
access log 没有请求，说明请求还没有到 nginx。

### 8.3 应用层

```powershell
curl.exe -i http://localhost:8080/actuator/health
netstat -ano | findstr :8080
```

看到：

```text
HTTP/1.1 200
{"status":"UP"}
```

说明后端独立可访问。后端直连正常、经过 nginx 失败，重点检查
`proxy_pass` 和容器到宿主机的路径。

### 8.4 中间件层

```powershell
docker compose ps
docker logs my-app-mysql --tail 50
docker exec my-app-redis redis-cli ping
docker exec my-app-mysql mysqladmin ping -h localhost -u root -p
```

预期：

```text
my-app-mysql   Up ... (healthy)
my-app-redis   Up ... (healthy)
PONG
mysqld is alive
```

消息队列还要检查名称服务、Broker、Topic 属性和消费日志。容器“Up”只证明
进程还在，不证明应用一定连通；健康检查和直接连接才是更有用的证据。

## 9. 日常运维

### 9.1 正确停止和重启顺序

后端是宿主机进程时，先停止后端，再停止 nginx，最后按需停止中间件：

```powershell
Get-Process java
docker compose --profile web stop nginx
docker compose stop
```

数据库和消息队列通常不需要因为前端发布而重启。无数据变更时，优先
`stop/start`，不要习惯性 `down -v`。

### 9.2 改代码后的最小发布步骤

```powershell
cd D:\workspace\my-app\backend
.\mvnw.cmd -B clean package -DskipTests

cd ..\frontend
npm ci
npm run build

cd ..
java "-Duser.timezone=Asia/Shanghai" -jar backend\target\my-app-1.0.0.jar
docker exec my-app-nginx nginx -t
docker exec my-app-nginx nginx -s reload
curl.exe -I http://localhost/
```

如果只改后端，不必重新构建前端；如果只改前端，也不必重启数据库。

### 9.3 数据库结构变更

初始化 SQL 适合空库首次创建，不适合升级已有库。新增表、字段或索引时，
使用带版本号的 Flyway/Liquibase migration，发布时记录“应用版本”和“数据库
版本”，失败时按迁移工具的回滚或前向修复策略处理。

### 9.4 日志

```powershell
Get-Content $env:TEMP\my-app.out.log -Wait
docker logs -f my-app-nginx
docker logs -f my-app-mysql
docker compose logs -f redis
```

先保留时间、请求路径、状态码和异常第一行，再追完整堆栈。不要把密码、
Token 或完整连接串复制到公共聊天或工单。

### 10.2 常见报错对照

| 原文 | 根因 | 修法 |
|---|---|---|
| `no main manifest attribute` | 启动了普通 JAR 或 `.jar.original` | 启动 repackage 后的 fat jar |
| `Could not find or load main class` | shell 拆坏 `-D` 参数或 classpath 错 | PowerShell 把完整 `-Dkey=value` 用双引号包住 |
| `Could not resolve placeholder 'APP_JWT_SECRET'` | 必填配置没有注入 | 设置环境变量或选择正确 profile |
| `Port 8080 was already in use` | 旧进程占用端口 | `netstat` 找 PID，停止或换端口 |
| `Communications link failure` | 数据库未就绪、地址或端口错误 | 查健康状态、服务名和连接串 |
| `address already in use` | 宿主端口已被占用 | 查 `docker ps` 和 `netstat` |
| `502 Bad Gateway` | nginx upstream 连不上后端 | 直连后端，再查 `proxy_pass` |
| `404 Not Found` 刷新前端子路由 | 缺少 SPA fallback | 加 `try_files $uri $uri/ /index.html` |
| `nginx: [emerg] unexpected "}"` | nginx 语法错误 | `nginx -t` 定位并修复分号/括号 |
| `Found orphan containers` | Compose project 名撞车 | 设置唯一 `name`，不要直接加 `--remove-orphans` |
| `Permission denied` | 宿主卷属主与容器 UID 不匹配 | 查 `id`、目录属主和日志后修权限 |
| `TLS handshake failed` | 客户端启用 TLS，但服务端口是明文 | 对齐协议和端口配置 |
| 延迟消息立即投递 | JVM、数据库或 Broker 时区不一致 | 统一时区，检查计算出的目标时间 |

遇到错误时，先记录完整原文和执行命令，再按浏览器、nginx、应用、中间件
的顺序验证。不要只复制最后一句“启动失败”，因为真正的根因通常在前几行。
