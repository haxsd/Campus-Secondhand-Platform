# 通用打包部署学习笔记

> 这份笔记面向会写 Java 和 Vue，但还没有独立完成过部署的开发者。  
> 目标不是背命令，而是建立一套可以迁移到不同项目、不同服务器的思考方法。

## 1. 部署到底在做什么

### 1.1 从“本机能跑”到“换台机器也能跑”

本机运行成功，只能说明当前电脑上的一组条件刚好满足。换一台机器后，下面
任何一项不同，都可能导致程序启动失败或运行结果不一致：

| 条件 | 典型内容 | 为什么要关心 |
|---|---|---|
| 依赖 | JDK、Node.js、浏览器、系统库 | 版本或平台不同可能无法构建 |
| 配置 | 数据库地址、端口、密码、密钥 | 不能把本机配置直接带到生产环境 |
| 运行时 | Java 进程、nginx、容器运行时 | 程序需要有人启动、重启和监控 |
| 中间件 | 数据库、缓存、消息队列 | 应用代码通常依赖外部服务 |
| 网络 | DNS、端口、防火墙、代理 | 服务可能启动了，但彼此连不到 |
| 数据 | 表结构、初始数据、历史数据 | 新代码不一定适配旧数据库 |

部署就是把这些隐含条件显式化：准备依赖，生成构建产物，注入环境配置，
启动运行时和中间件，配置网络入口，再用可重复的方式验证结果。

### 1.2 部署的核心问题

每次部署都应该能回答四个问题：

1. **我要运行什么？**——明确 Java JAR、前端静态文件和中间件。
2. **它依赖什么？**——明确 JDK、数据库、缓存、消息队列、目录权限和端口。
3. **它从哪里读配置？**——明确环境变量、配置文件和密钥来源。
4. **我如何知道它真的正常？**——准备健康检查、日志和一条最小业务链路。

如果这些问题只能依靠“记得上次怎么做”，部署就还没有工程化。

## 2. 构建产物

### 2.1 Java：源码、class 和 JAR

Java 源码首先被编译器编译成字节码文件，也就是 `.class` 文件。JVM
（Java 虚拟机）运行的是字节码，而不是直接运行 `.java` 源码：

```text
.java 源码
    ↓ 编译
.class 字节码
    ↓ 按项目结构和依赖打包
.jar
```

Spring Boot 项目通常构建成 **fat jar**（也叫可执行 JAR）：除了自己的
class 和资源，还把运行所需的依赖 JAR 放入包内，并提供启动入口。因此目标
机器通常只需要合适版本的 Java，不需要安装 Maven。

### 2.2 fat jar、普通 jar 和 war

| 类型 | 内容 | 常见运行方式 | 适用场景 |
|---|---|---|---|
| 普通 JAR | 主要是本项目 class 和资源 | 需要额外准备依赖 | 类库或由其他程序加载 |
| fat jar | 项目内容加运行依赖和启动器 | `java -jar app.jar` | 独立运行的 Spring Boot 应用 |
| WAR | Web 应用归档，通常交给 Servlet 容器 | 部署到外部 Tomcat 等 | 传统应用服务器模式 |

Spring Boot 的可执行 JAR 不等于“把所有东西简单压成一个 ZIP”。它通常有
启动器、嵌套依赖和约定目录，启动器负责建立 classpath（类搜索路径）并找到
应用入口。

### 2.3 `.jar.original` 是什么

Spring Boot Maven 插件重新打包后，可能留下一个类似
`app.jar.original` 的文件。它一般是重新打包前的原始普通 JAR，不含可执行
启动器和完整运行依赖。

部署时要先确认脚本选择的是哪个文件。常见做法是：

- 选择主 JAR；
- 排除 `.jar.original`；
- 同时排除测试、源码或 plain JAR；
- 不要仅仅因为目录里“有一个 JAR”就盲目启动。

### 2.4 前端：为什么浏览器不认 `.vue`

浏览器能直接理解 HTML、CSS 和 JavaScript，但 `.vue` 是 Vue 单文件组件
格式，里面可能同时包含模板、脚本和样式。浏览器没有解析这种项目源文件
的职责，因此前端必须先构建：

```text
Vue 源码
  ↓ 编译：解析单文件组件、转换现代语法
  ↓ 打包：合并模块并分析依赖
  ↓ 压缩：减少 JavaScript、CSS 和 HTML 体积
  ↓ hash：给文件名加入内容指纹
静态资源（HTML、JS、CSS、图片等）
```

文件名中的 hash 能让浏览器和 CDN（内容分发网络）准确判断缓存是否需要
更新：内容变了，文件名通常也会变。

### 2.5 为什么构建产物不进版本库

`node_modules/` 是依赖安装目录，体积大且可以由锁文件恢复；`dist/` 是可
重新生成的前端产物；`target/` 是 Java 构建目录。把它们提交到版本库会：

- 增大仓库；
- 把特定机器或特定构建时间的内容混进去；
- 造成源码与产物不一致；
- 让合并冲突和审查变得困难。

例外是明确采用“只发布静态产物、不在服务器构建”的发布流程，但即使如此，
通常也应把产物交给制品库，而不是直接提交到源码仓库。

## 3. 配置与环境分离

### 3.1 为什么不能把密码写死

把数据库密码、JWT 密钥或第三方 Token 写进源码，会带来：

- 每个环境都使用同一个秘密；
- 密钥进入 Git 历史后很难彻底清除；
- 换密码必须重新构建；
- 日志、压缩包或代码分享可能意外暴露秘密。

代码应该描述“需要什么配置”，而不是携带真实秘密。配置注入和代码发布
应该是两件事。

### 3.2 配置层级和优先级

不同框架细节略有不同，但可以先记住一个通用原则：

```text
命令行参数 > 环境变量 > 配置文件中的默认值
```

命令行适合临时覆盖，环境变量适合部署系统注入，配置文件适合提交不敏感
的默认配置。实际使用时要查清具体框架的优先级，不要只凭经验判断。

例如，下面的配置表达“环境变量不存在时使用默认值”：

```yaml
server:
  port: ${APP_PORT:8080}
spring:
  datasource:
    url: ${DB_URL:jdbc:mysql://localhost:3306/my_app}
    username: ${DB_USERNAME:app}
    password: ${DB_PASSWORD:change-me}
```

默认值适合本地开发或示例，不代表生产环境可以继续使用它。

### 3.3 profile 机制

profile（配置环境）用于区分开发、测试和生产。例如：

```text
application-dev.yml
application-test.yml
application-prod.yml
```

它们可以分别配置日志级别、数据库地址、跨域策略和外部服务。启动时通过
环境变量或命令行选择 profile：

```powershell
java -jar app.jar --spring.profiles.active=prod
```

profile 不是密钥管理工具。生产 profile 可以提交非敏感结构，但真实密码
仍应由环境变量或密钥系统注入。

### 3.4 `.env` 的定位

`.env` 常用于给 Compose 或本地脚本提供环境变量，例如：

```dotenv
APP_PORT=8080
DB_PASSWORD=replace-me
MQ_BROKER_PORT=10911
```

它的作用是集中管理一次部署所需的变量，不是让密码变得安全。真实 `.env`
通常不进入版本库，仓库只提交 `.env.example`，说明变量名称、用途和示例
格式。

更成熟的生产环境会使用 Vault、KMS 或云平台 Secret Manager（密钥管理服务）
在部署时注入秘密，而不是把秘密放在磁盘上的普通文本文件里。

## 4. 进程、端口与跨域

### 4.1 端口是进程的入口

一个 TCP 端口在同一台机器上通常只能被一个监听进程占用。应用启动失败时，
先看端口是否被旧进程占用，比立刻修改配置更可靠：

```powershell
netstat -ano | findstr :8080
```

找到进程后还要确认它是不是自己想要的进程。不要为了“让它启动”而随便
停止陌生服务。

### 4.2 同源策略是什么

浏览器的同源策略会比较协议、域名和端口。三者只要有一个不同，就可能被
视为跨源请求。例如：

```text
页面：http://localhost:5173
API： http://localhost:8080
```

虽然都是 localhost，但端口不同，浏览器仍可能阻止前端读取响应。

### 4.3 三种跨域解决方式

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| CORS | 后端响应允许指定来源 | 开发直观、部署简单 | 要正确处理凭证、预检和来源白名单 |
| 开发代理 | Vite 等开发服务器转发 `/api` | 开发体验好，浏览器看到同源 | 只解决开发环境，生产还要另配 |
| 同源部署 | nginx 用同一域名提供前端并代理 API | 生产结构清晰，浏览器不跨源 | 需要配置 nginx 和发布入口 |

生产环境通常选择同源部署：用户只访问一个入口，前端请求相对路径，nginx
再把 API 转发到后端。

## 5. nginx

### 5.1 两个角色

nginx 在前端部署中常见的两个角色是：

1. **静态服务器**：直接返回 HTML、JavaScript、CSS、图片等文件；
2. **反向代理**：用户请求 nginx，nginx 代表用户请求后端应用。

反向代理的好处是后端端口不必直接暴露给用户，还能统一 TLS、域名、压缩、
缓存和访问日志。

### 5.2 `location` 匹配

`location` 决定某类 URL 由哪段规则处理。一个简化示例：

```nginx
server {
    listen 80;

    location /api/ {
        proxy_pass http://backend:8080;
    }

    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;
    }
}
```

真实配置中要注意不同 `location` 的匹配优先级，避免静态页面规则抢走
API 请求，或者 API 规则覆盖了不应代理的路径。

### 5.3 `proxy_pass` 和转发头

反向代理通常传递这些信息：

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

- `Host` 让后端知道用户访问的原始主机；
- `X-Real-IP` 提供直接客户端地址；
- `X-Forwarded-For` 记录经过的代理链；
- `X-Forwarded-Proto` 区分用户原始请求是 HTTP 还是 HTTPS。

后端只有在信任代理来源时，才应该信任这些头，不能无条件把用户提交的同名
请求头当成真实信息。

### 5.4 SPA history 模式

Vue Router 的 history 模式把 `/products/123` 当成前端路由。用户从首页
点击进去时，前端可以接管；但用户刷新这个 URL 时，浏览器会直接向 nginx
请求 `/products/123`。

如果服务器只按文件路径查找，找不到这个文件就会返回 404。需要回退到入口：

```nginx
location / {
    try_files $uri $uri/ /index.html;
}
```

这样 nginx 返回 `index.html`，再由前端路由决定显示哪个页面。

### 5.5 `proxy_pass` 末尾斜杠陷阱

`proxy_pass` 是否带末尾斜杠，会影响 nginx 替换 URI 前缀的方式。例如：

```nginx
location /api/ {
    proxy_pass http://backend:8080/;
}
```

和：

```nginx
location /api/ {
    proxy_pass http://backend:8080;
}
```

对 `/api/users` 的转发路径可能不同。配置后要用日志或后端实际收到的路径
验证，不要只凭视觉判断。

## 6. 容器与 Compose

### 6.1 镜像、容器和卷

| 概念 | 可以理解为 | 生命周期 |
|---|---|---|
| 镜像 | 只读的程序和文件模板 | 可被多个容器复用 |
| 容器 | 镜像启动后的进程实例 | 删除容器通常不会删除镜像 |
| 卷 | 独立于容器的数据存储 | 容器删除后仍可保留 |

容器更像“可替换的运行实例”，卷才适合保存数据库文件、消息数据和上传
文件。把数据只写在容器可写层里，删除或重建容器后数据就可能消失。

### 6.2 Compose 解决什么问题

Compose 用一个 YAML 文件描述一组服务、网络、卷、端口和依赖关系。它把
“先启动谁、挂载什么、服务如何互相访问”变成可复用的声明式配置。

它解决的是编排问题，不等于完整的生产平台。高可用、滚动发布、自动扩缩容
等需求可能还需要 Kubernetes 或云平台能力。

### 6.3 Compose project（项目名）机制

Compose project 是一组相关容器、网络和卷的逻辑归属。默认项目名通常取
Compose 文件所在目录名，也可以用顶层 `name:` 或 `-p` 显式指定：

```yaml
name: my-app
```

如果两个互不相关的项目恰好都叫 `deploy`，Compose 可能认为它们属于同一个
项目。执行其中一个项目的命令时，另一个项目的容器就可能被识别为 orphan
（孤儿容器：存在于该项目标签中，但当前文件没有声明）。

### 6.4 为什么 `--remove-orphans` 危险

`--remove-orphans` 的意思是：把当前 Compose project 中、但当前 YAML 没有
声明的容器删除。它不是“只删除我刚才改过的容器”，判断依据是 project
标签。

因此，两个项目撞了 project name 时：

1. 项目 A 的 YAML 没有声明项目 B 的容器；
2. Compose 把项目 B 容器列为 orphan；
3. 执行 `up --remove-orphans` 或其他带该选项的命令；
4. 项目 B 的容器可能被删除。

防范方法：

- 为每个独立项目显式设置唯一项目名；
- 启动和停止前确认 `docker compose ps` 以及容器的
  `com.docker.compose.project` 标签；
- 不把 `--remove-orphans` 当成默认清理选项；
- 如果必须使用，先确认 project 边界和 orphan 列表；
- 不同项目不要共用容易重复的目录名。

### 6.5 `down` 和 `down -v`

| 命令 | 通常会做什么 | 数据风险 |
|---|---|---|
| `docker compose down` | 停止并删除当前项目容器和网络 | 保留命名卷 |
| `docker compose down -v` | 另外删除当前项目声明的卷 | 可能删除数据库和消息数据 |

任何涉及 `-v` 的命令都要先确认卷归属、备份和恢复方案。停止一个服务不等于
可以删除它的全部数据。

## 7. 中间件部署要点

### 7.1 关系数据库

数据库初始化脚本通常只在数据目录第一次为空时执行。容器重启不会重复执行
初始化脚本，已有数据库也不会因为你修改了脚本而自动补齐新表或新索引。

因此要区分：

- **初始化脚本**：用于创建全新数据库；
- **迁移脚本**：用于把已有数据库从版本 N 升级到版本 N+1。

数据库卷必须持久化。字符集通常统一使用 UTF-8 系列，并检查客户端连接、
数据库、表和排序规则，避免“库里存的是问号，应用却以为是中文”的问题。

### 7.2 缓存

缓存数据是否持久化取决于业务：

- 纯缓存可以接受丢失，重启后从数据库重新加载；
- 具备会话、队列或临时状态语义的数据，可能需要持久化；
- 无论是否持久化，都要设计缓存失效、过期和重建策略。

不要把缓存当成唯一事实来源，除非系统明确把它设计成数据存储。

### 7.3 消息队列

消息队列经常不是一个容器，而是多个组件协作：名称服务、Broker、代理、
权限初始化和 Topic 初始化等。排查时要先确认每个组件的职责和依赖顺序。

客户端连接的端口也要分清：

| 连接对象 | 常见用途 |
|---|---|
| 名称服务端口 | 发现 Broker |
| Broker 端口 | 生产和消费消息 |
| 代理端口 | 客户端通过代理访问消息服务 |

延迟消息或定时消息通常需要显式开启 Broker 能力，或者在 Topic 声明时设置
消息类型。Topic 名字存在，不代表它具备延迟消息能力；要验证实际属性和
Broker 配置。

### 7.4 容器用户与文件权限

很多镜像会让宿主机先创建卷目录。宿主机创建出来的目录可能属于 root，但
容器内的中间件进程使用非 root UID 运行，于是它无法写入数据目录，表现为：

- 容器反复重启；
- 日志出现 `Permission denied`；
- Broker 或数据库初始化失败；
- 卷看起来已经挂载，但程序仍无法启动。

排查顺序：

```bash
docker inspect my-app-broker
docker exec my-app-broker id
docker exec my-app-broker ls -ln /var/lib/my-service
docker logs my-app-broker
```

确认进程 UID、目录属主和权限后，用一次性的权限初始化容器，或在宿主机按
镜像要求调整属主。不要为了省事长期让业务中间件以 root 运行。

## 8. 时区与字符编码

### 8.1 三个时区来源

时间可能同时受到三层影响：

1. JVM 时区：Java `Date`、定时任务和业务时间计算；
2. 数据库时区：`CURRENT_TIMESTAMP`、连接会话和时间类型转换；
3. 连接串时区：驱动如何把数据库时间转换成 Java 时间。

如果 JVM 使用 UTC，但业务按东八区计算，定时任务可能提前或延后；延迟消息
还可能因为算出的目标时间已经在过去而立即投递。

### 8.2 正确做法

在部署层统一时区，例如：

```text
JVM:      -Duser.timezone=Asia/Shanghai
数据库:   服务器和连接会话统一 Asia/Shanghai
连接串:   按驱动要求显式指定时区
```

也可以全链路使用 UTC，但必须从数据库、应用到展示层都一致。不要在业务 SQL
里到处加减小时数来“修复”部署时区问题，这会制造更多边界错误。

### 8.3 字符集

统一使用 UTF-8，检查源码文件编码、HTTP 响应头、数据库字符集、连接参数和
终端编码。中文乱码往往不是“某一行 SQL 写错”，而是链路中的某一层按错误
编码解释了字节。

## 9. 排查方法论

### 9.1 先分层，再深入

建议按请求链路从外到内排查：

```text
浏览器 → nginx → 应用 → 中间件
```

先证明哪一层坏了，再研究该层内部。不要看到页面报错就直接重启数据库，
也不要看到应用异常就先改 nginx。

### 9.2 分层排查表

| 层次 | 常见症状 | 首先验证什么 |
|---|---|---|
| 浏览器 | 页面空白、跨域、请求失败 | DevTools Network、Console、请求 URL 和响应 |
| nginx | 404、502、刷新路由失败 | nginx 日志、配置语法、静态文件和 upstream |
| 应用 | 500、启动失败、健康检查异常 | 应用日志、健康检查端点、端口监听 |
| 数据库 | SQL 错误、连接超时、数据缺失 | 容器状态、数据库日志、直接连接和表结构 |
| 缓存 | 登录失效、缓存击穿、连接拒绝 | 缓存日志、连通性、键和过期时间 |
| 消息队列 | 消息不消费、延迟不生效 | Broker 状态、Topic 属性、生产消费日志 |

### 9.3 几个实用原则

- **先看状态，再看日志**：容器是否运行、端口是否监听，是最便宜的证据；
- **先做最小验证**：先访问健康检查，再跑完整业务；
- **区分连接问题和业务问题**：能连上数据库不代表 SQL 正确；
- **记录命令和输出**：可复现的证据比“我感觉刚才可以”可靠；
- **每次只改一个变量**：否则无法知道哪次修改真正解决了问题。

## 10. 典型事故复盘

### 10.1 PowerShell 拆开 `-D` 参数

- **现象**：启动 Java 时提示找不到主类，或把某个配置值当成了主类名。
- **根因**：PowerShell 对命令行参数的解析方式与预期不同，`-Dxxx=yyy`
  没有作为一个完整参数传给 Java。
- **修法**：先用 `java -version` 和一条最小命令确认 shell 行为；将 JVM
  参数写成完整参数，必要时用数组传参或显式引用。
- **如何预防**：把启动命令放进经过验证的脚本，并在脚本中打印最终参数，
  不要把长命令只存在聊天记录里。

### 10.2 Compose 项目名撞车删除了另一个项目容器

- **现象**：启动一个项目时出现 orphan 警告，带 `--remove-orphans` 后，
  另一个项目的容器消失。
- **根因**：两个项目默认使用了相同的 Compose project name，Compose 只按
  project 标签判断归属。
- **修法**：为每个项目设置唯一 `name:` 或 `-p`，核对现有容器标签后再操作。
- **如何预防**：把项目名写进 Compose 文件，默认禁止 `--remove-orphans`，
  执行清理前先保存 `docker ps -a`。

### 10.3 卷属主是 root，非 root 进程无法写入

- **现象**：中间件卷已经挂载，但容器启动失败并持续重启。
- **根因**：宿主机创建的目录属主是 root，容器内非 root UID 没有写权限。
- **修法**：检查进程 UID、目录数字属主和启动日志；使用权限初始化步骤
  调整为正确 UID，或按镜像文档创建卷。
- **如何预防**：第一次部署就设计权限初始化，不要等到生产数据卷已有内容
  后才临时改权限。

### 10.4 UTC 与业务东八区不一致

- **现象**：延迟消息计算出的时间已经过去，消息几乎立即投递；定时任务
  也出现提前或延后。
- **根因**：JVM 使用 UTC，而业务时间和数据库按东八区理解。
- **修法**：统一 JVM、数据库和连接驱动的时区配置。
- **如何预防**：部署检查清单中加入当前时间、UTC 时间和数据库时间的对照，
  不在 SQL 中到处加减小时。

### 10.5 明文代理端口与客户端默认 TLS 冲突

- **现象**：客户端连接本地明文代理端口时提示 TLS 协商失败。
- **根因**：服务端端口只提供明文协议，但客户端默认开启了 TLS。
- **修法**：确认端口实际协议，关闭不适用的 TLS 选项，或改用真正启用 TLS
  的端口。
- **如何预防**：在配置中同时写清协议、端口和证书要求，不只写一个数字。

### 10.6 老数据库缺少新索引

- **现象**：全新数据库性能正常，老环境查询变慢或执行计划不同。
- **根因**：初始化脚本增加了索引，但初始化脚本只对空数据库执行；老库没有
  自动升级。
- **修法**：为已有数据库单独执行经过审查的迁移 SQL，并验证索引和执行计划。
- **如何预防**：使用 Flyway 或 Liquibase 管理带版本号的 schema migration，
  不把“初始化脚本”误当成完整升级机制。

### 10.7 构建产物误入版本库，或忘记构建

- **现象**：仓库体积变大、产物和源码不一致；或者部署后 nginx 找不到
  静态入口，Java 也没有可运行 JAR。
- **根因**：没有明确源码、依赖目录、构建目录和发布制品的边界。
- **修法**：把 `node_modules/`、`dist/`、`target/` 排除在源码仓库之外，
  部署前显式检查构建产物存在。
- **如何预防**：用锁文件恢复依赖，用 CI 构建并保存制品，部署脚本在启动前
  检查 JAR 和静态入口文件。

## 12. 面试常被问到的点

### Q1：Java 项目从源码到上线经历了什么？

**答法要点：**

- Maven 编译源码得到 class；
- Spring Boot 插件把应用和依赖打成可执行 fat jar；
- 服务器准备 JDK、配置和中间件；
- 通过 `java -jar` 启动应用；
- nginx 提供前端静态文件并反向代理 API；
- 用健康检查和业务链路验证发布结果。

### Q2：为什么生产要用 nginx 反向代理？

**答法要点：**

- 对外只暴露统一域名和端口；
- 前后端可以同源，减少跨域问题；
- nginx 适合提供静态文件；
- 后端端口不直接暴露；
- 可以集中处理 TLS、压缩、缓存和访问日志。

### Q3：镜像、容器和卷有什么区别？

**答法要点：**

- 镜像是不可变模板；
- 容器是运行中的实例；
- 卷是独立于容器生命周期的数据；
- 容器可以替换，数据库数据不能只放在容器可写层。

### Q4：Compose project name 为什么重要？

**答法要点：**

- Compose 用项目名给容器、网络和卷划分逻辑归属；
- 默认项目名可能来自目录名；
- 两个项目撞名会互认 orphan；
- `--remove-orphans` 可能删除另一个项目的容器；
- 应显式设置唯一项目名并谨慎执行清理。

### Q5：如何管理不同环境的配置？

**答法要点：**

- 非敏感默认配置可以进入版本库；
- dev、test、prod 用 profile 区分；
- 密码和密钥通过环境变量或密钥系统注入；
- 命令行、环境变量和配置文件有优先级；
- `.env` 适合本地或部署注入，但真实文件不应提交。

### Q6：如何处理时区问题？

**答法要点：**

- 先明确系统采用 UTC 还是某个业务时区；
- JVM、数据库会话和连接驱动必须一致；
- 延迟消息和定时任务尤其容易暴露时区错误；
- 在部署层统一配置，不在 SQL 里到处加减小时。

### Q7：线上接口报错，你怎么排查？

**答法要点：**

- 按浏览器、nginx、应用、中间件分层；
- 浏览器看 Network 和 Console；
- nginx 看配置和访问/错误日志；
- 应用看启动日志、健康端点和异常堆栈；
- 中间件直接验证容器状态、日志和连接；
- 先确认哪一层坏了，再深入查原因。

### Q8：初始化脚本改了，为什么老数据库没有新索引？

**答法要点：**

- 初始化脚本通常只在空数据目录第一次执行；
- 老数据库需要独立的版本化迁移；
- 应使用 Flyway、Liquibase 或同类方案；
- 迁移后检查 `SHOW INDEX` 和执行计划；
- 数据库结构变更也要纳入发布流程和回滚设计。
