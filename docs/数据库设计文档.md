# 校园二手交易平台 · 数据库设计文档

> 与 `deploy/sql/init.sql` 一一对应。库名 `campus_trade`，MySQL 8，utf8mb4，InnoDB。
>
> 全局约定：
> - 主键统一 `BIGINT AUTO_INCREMENT`，返回前端一律转字符串（防 JS 精度丢失）。
> - 状态字段用 `TINYINT` 存稳定编码，含义由后端枚举维护（见各表说明）。
> - 金额统一 `DECIMAL(10,2)`；时间统一 `DATETIME`，`created_at`/`updated_at` 由数据库默认值维护。
> - **不建物理外键**：关联完整性由应用层校验 + 唯一约束 + 状态机保证（学生项目规模下更灵活，也是很多互联网公司的实践）。
> - 历史订单、快照、评价、纠纷**永不物理删除**（交易凭证与审计），业务撤销用状态字段表达；商品用 `deleted` 软删除。

## 表总览（12 张，按领域分 4 组）

| 领域 | 表 | 一句话职责 |
| --- | --- | --- |
| 用户与信用 | `user` | 账号事实数据（登录、角色、封禁） |
| | `user_credit_summary` | 信用聚合读模型（注册初始化，评价后重算） |
| 商品 | `category` | 商品分类字典 |
| | `product` | 商品主表（内容、价格、库存、状态机） |
| | `product_image` | 商品图片（1 商品 : N 图） |
| | `product_review_log` | 人工审核轨迹 |
| | `browse_history` | 用户浏览记录（upsert） |
| 交易 | `trade_order` | 订单事实数据 + 状态机 |
| | `product_snapshot` | 下单瞬间的商品快照（1 单 : 1 快照） |
| | `trade_order_log` | 订单状态流转日志（1 单 : N 条） |
| 交易后 | `trade_review` | 交易评价（第一版一单一评） |
| | `dispute` | 纠纷单（第一版一单一纠纷） |

关系速记：`user` 1—N `product` 1—N `trade_order` 1—1 `product_snapshot`；评价/纠纷都挂在订单上，不能脱离订单创建。

## 1. user — 用户表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | 用户ID |
| student_no | VARCHAR(32) | 学号，登录账号之一，**唯一** |
| phone | VARCHAR(20) | 手机号，登录账号之一，**唯一** |
| password | VARCHAR(100) | BCrypt 哈希（自带盐，非 MD5） |
| nickname | VARCHAR(30) | 昵称 |
| avatar | VARCHAR(255) | 头像地址，可空 |
| campus | VARCHAR(30) | 所在校区 |
| role | TINYINT | 0 普通用户 / 1 管理员 |
| status | TINYINT | 0 正常 / 1 封禁 |
| created_at / updated_at | DATETIME | |

约束与设计原因：
- `uk_student_no`、`uk_phone` 两个唯一索引：**并发注册防重的最终兜底**——"先查再插"挡不住两个请求同时通过查询，靠唯一键冲突转业务异常。
- 密码只存 BCrypt 哈希；登录失败统一提示"账号或密码错误"，防账号枚举。

## 2. user_credit_summary — 用户信用摘要表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| user_id | BIGINT PK | 用户ID（与 user 一对一） |
| credit_score | INT | 信用分，默认 100，区间 60~100（100 + 好评×1 − 差评×3） |
| deal_count | INT | 成交次数（订单首次完成时 +1） |
| review_count | INT | 收到的可见评价数 |
| avg_rating | DECIMAL(3,2) | 平均评分 |
| good_review_rate | DECIMAL(5,4) | 好评率（≥4 分占比） |
| bad_review_count | INT | 差评数（≤2 分） |
| version | INT | 重算版本号 |
| calculated_at | DATETIME | 最近重算时间 |

设计原因：
- 这是**读模型**：商品详情页要展示卖家信用，不能每次实时扫评价表聚合。评价明细（trade_review）才是事实源，本表可随时全量重算。
- `version`：防并发覆盖——较早开始的慢重算任务不能把新统计写回成旧值（更新时带 version 条件）。
- 注册时与 user 同事务初始化，保证详情页不缺数据。

## 3. category — 商品分类表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| name | VARCHAR(30) | 分类名，唯一 |
| sort | INT | 排序值 |
| enabled | TINYINT | 1 启用 / 0 停用 |

发布/编辑商品时校验分类"存在且启用"。init.sql 预置 6 个分类。

## 4. product — 商品主表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| seller_id | BIGINT | 卖家ID，**只取 UserContext，不接受前端指定** |
| category_id | BIGINT | 分类 |
| title | VARCHAR(60) | 标题 |
| description | VARCHAR(2000) | 描述 |
| price | DECIMAL(10,2) | 单价 |
| stock | INT | **当前可售库存**，下单条件扣减、取消回补 |
| item_condition | TINYINT | 成色 0 全新 / 1 几乎全新 / 2 轻微使用 / 3 明显使用（`condition` 是 MySQL 保留字故改名） |
| campus | VARCHAR(30) | 校区 |
| trade_place | VARCHAR(60) | 默认交易地点 |
| status | TINYINT | **0 草稿 / 1 待人工审核 / 2 审核驳回 / 3 在售 / 4 已下架 / 5 已售罄** |
| view_count | INT | 浏览次数（异步累计，不在读路径同步 update） |
| version | INT | 编辑乐观锁（两个页面同时编辑防后写覆盖） |
| deleted | TINYINT | 软删除 |

索引与设计原因：
- `idx_list(status, campus, category_id, price, id)`：服务买家列表页"在售 + 校区 + 分类 + 价格区间"筛选；实际是否生效要用 EXPLAIN 验证（动态条件可能跳列）。
- `idx_seller(seller_id, status)`：卖家"我的商品"页。
- 库存规则：下单 `stock=stock-n where status=3 and stock>=n` 条件更新防超卖；扣到 0 同步置为已售罄；取消/超时回补。
- 状态机：草稿→(申请上架)→待审核→通过→在售 / 驳回→修改重提；在售不可直接编辑内容（先下架），防"审核的是旧内容，展示的是新内容"。

## 5. product_image — 商品图片表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| product_id | BIGINT | 所属商品 |
| url | VARCHAR(255) | 图片地址（后端受控生成的随机对象名） |
| sort | INT | 展示顺序 |

索引 `idx_product_sort(product_id, sort)`：详情页按顺序取图。与 product 的插入/替换同事务。

## 6. product_review_log — 商品审核日志

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| product_id | BIGINT | 被审核商品 |
| reviewer_id | BIGINT | 审核管理员 |
| result | TINYINT | 1 通过 / 2 驳回 |
| reason | VARCHAR(500) | 驳回原因/修改建议 |

审核动作与商品状态变更同事务写入，留审计轨迹。

## 7. browse_history — 浏览记录表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| user_id / product_id | BIGINT | 谁看了什么 |
| last_browsed_at | DATETIME | 最后浏览时间 |

约束与设计原因：
- `uk_user_product(user_id, product_id)` 唯一 + upsert：重复浏览只更新时间，不堆记录。
- `idx_user_time(user_id, last_browsed_at)`：个人中心按时间倒序。
- 弱一致行为数据：只在详情接口写、失败不影响详情返回、未登录不记录。

## 8. trade_order — 交易订单表（核心）

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| order_no | VARCHAR(32) | 业务订单号，后端生成，**唯一**，前端按字符串处理 |
| request_id | VARCHAR(64) | 客户端幂等ID（进下单页生成一次 UUID，重试沿用） |
| buyer_id / seller_id / product_id | BIGINT | 三方关系 |
| quantity | INT | 购买数量 |
| unit_price | DECIMAL(10,2) | 下单时单价（**后端按库中价格算，不信前端**） |
| total_amount | DECIMAL(10,2) | = unit_price × quantity |
| trade_time / trade_place / remark | | 线下面交约定 |
| status | TINYINT | **0 待卖家确认 / 1 已确认 / 2 已完成 / 3 已取消 / 4 超时取消 / 5 纠纷中** |
| status_before_dispute | TINYINT | 进入纠纷前的状态（驳回纠纷时恢复用） |
| confirm_deadline | DATETIME | 卖家确认截止时间（超时关单依据） |
| finished_at | DATETIME | 完成时间 |

约束/索引与设计原因：
- `uk_buyer_request(buyer_id, request_id)`：**请求幂等的最终兜底**——网络超时重试不会创建两笔订单，命中冲突返回第一笔。Redis 防抖只管体验，这里管正确性。
- `uk_order_no`：业务订单号可稳定查询。
- `idx_buyer / idx_seller (xx_id, status)`：买家/卖家订单列表按状态筛选。
- `idx_timeout_scan(status, confirm_deadline, id)`：定时任务扫"待确认且已到期"的订单，id 用于分批稳定翻页。
- 状态流转全部用 `update ... where id=? and status=旧状态` 条件更新，影响行数 0 = 已被并发处理，绝不重复回补库存。

## 9. product_snapshot — 商品快照表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| order_id | BIGINT | 所属订单，**唯一**（一单一快照） |
| product_id | BIGINT | 原商品 |
| title / description / price / item_condition / campus / trade_place | | 下单那一刻的商品信息 |
| images | JSON | 图片地址列表 |

设计原因：保存"下单瞬间买家看到的内容"。卖家之后改价、改描述、删图、下架，都不影响历史订单展示和纠纷取证。与订单创建同事务写入。

## 10. trade_order_log — 订单状态日志

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| order_id | BIGINT | |
| from_status / to_status | TINYINT | 流转前后状态 |
| operator_type | TINYINT | 0 买家 / 1 卖家 / 2 系统 / 3 管理员 |
| operator_id | BIGINT | 系统操作时为空 |
| reason | VARCHAR(200) | 取消原因等 |

每次状态变化追加一条（与状态更新同事务），客服解释、纠纷判断、排障都靠它。

## 11. trade_review — 交易评价表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| order_id | BIGINT | **唯一**（第一版一单一评） |
| reviewer_id | BIGINT | 评价人=订单买家（由订单推导，不信前端） |
| seller_id | BIGINT | 被评卖家（由订单推导） |
| rating | TINYINT | 1~5 分 |
| content / tags | | 评价内容、标签 |
| visible | TINYINT | 1 可见 / 0 被管理员隐藏（隐藏后触发信用重算） |

索引 `idx_seller(seller_id, visible, created_at)`：商品详情页取卖家最近可见评价。前置条件：订单已完成且当前用户是买家。

## 12. dispute — 纠纷表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | BIGINT PK | |
| order_id | BIGINT | **唯一**（第一版一单一纠纷，防并发点击建两张） |
| applicant_id / respondent_id | BIGINT | 申请人/被投诉方（由订单关系推导） |
| reason_type | TINYINT | 0 货不对板 / 1 未履约 / 2 其他 |
| statement | VARCHAR(2000) | 申请人陈述（**当事人主张，非已验证事实**） |
| evidence | JSON | 证据材料地址列表 |
| status | TINYINT | **0 待处理 / 1 待补充材料 / 2 已驳回 / 3 维持完成 / 4 取消交易** |
| handler_id / handle_note / handled_at | | 处理管理员、说明、时间 |

索引 `idx_status(status, created_at, id)`：管理员后台按状态排队处理。发起纠纷时同事务：建纠纷单 + 订单存 `status_before_dispute` + 订单条件更新为纠纷中。处理结果动作走后端白名单（驳回恢复原状态 / 维持完成 / 取消交易可选回补库存 / 待补材料）。

## 附：面试高频追问点速查

| 问题 | 答案所在 |
| --- | --- |
| 怎么防超卖？ | product.stock 条件更新（表 4），不是先查再减 |
| 怎么防重复下单？ | 三层：Redis 防抖(体验) → uk_buyer_request(正确性) → 库存条件更新(并发)（表 8） |
| 卖家改商品，历史订单会变吗？ | 不会，product_snapshot 固定下单瞬间内容（表 9） |
| 怎么防重复取消/重复回补库存？ | 状态机条件更新，影响行数为 0 直接结束（表 8） |
| 信用分怎么算、会不会算错覆盖？ | 摘要是可重建读模型 + version 防旧任务覆盖（表 2） |
| 为什么不建外键？ | 全局约定一节：应用层校验 + 唯一约束 + 状态机兜底 |
