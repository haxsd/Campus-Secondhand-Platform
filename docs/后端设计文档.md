## 1. 技术栈与全局约定

### 1.1 技术栈

| 层 | 选型 | 作用 |
| --- | --- | --- |
| 语言/框架 | Java 17 + Spring Boot 3 | Web 服务、依赖注入、自动配置 |
| 持久层 | MyBatis + MySQL 8 | SQL 直接可控（学习项目不用 JPA，SQL 一目了然） |
| 缓存/防抖 | Redis 7（Redisson 客户端） | 登录态、商品详情缓存、下单防抖 |
| 构建 | Maven | 依赖管理、打包 |
| 部署 | Docker Compose + Nginx | 见第 12 节 |

> 为什么用 MyBatis 而不是 JPA/MyBatis-Plus：学习阶段希望你**看得见每一条 SQL**（尤其是"条件更新扣库存"这种关键语句），MyBatis 的 XML/注解 SQL 最直观，也是国内后端最常见的技术栈，面试友好。

### 1.2 全局约定（后端必须遵守，很多是和前端/数据库对齐的硬规则）

- **统一返回结构**：所有接口都返回 `{ "code": 0, "message": "ok", "data": {} }`（见第 4.1 节 Result）。前端 `request.js` 依赖这个结构，不能各写各的。
- **错误码语义**（与 API 文档一致）：`0` 成功 / `400` 参数错 / `401` 未登录 / `403` 无权限 / `404` 不存在 / `409` 状态冲突 / `429` 太频繁 / `500` 内部错误。
- **BIGINT 主键序列化成字符串**：`id`、`orderNo` 等所有 Long 主键在 JSON 里必须是字符串，否则前端 JS 大整数会精度丢失（Jackson 全局配置一处解决，见 4.4）。
- **金额**用 `BigDecimal`，保留两位小数；**时间**统一 `yyyy-MM-dd HH:mm:ss` 字符串。
- **密码**只存 BCrypt 哈希（自带盐），永不存明文/MD5；登录失败统一提示"账号或密码错误"（防账号枚举）。
- **不建物理外键**：关联完整性靠"应用层校验 + 唯一约束 + 状态机条件更新"保证（与数据库文档一致）。
- **卖家/买家身份只从登录态（UserContext）取，绝不信前端传的 userId**：例如发布商品的 `sellerId`、评价人 `reviewerId` 都由后端从 token 推导。
- **权限后端必须真正校验**：前端路由守卫只是体验层，后端每个需登录/管理员接口都要独立校验（未登录→401，越权→403）。
- **契约纪律**：开发中发现契约不合理，**先改 `docs/API接口文档.md`，再改代码**，前后端以文档为准。

## 2. 工程结构与分层

### 2.1 包结构（按"业务模块"竖切，不按"技术层"横切）

```text
backend/
├── pom.xml                         Maven 依赖
├── Dockerfile                      多阶段构建（maven 打包 → JRE 运行）
└── src/main/
    ├── resources/
    │   ├── application.yml          公共配置
    │   ├── application-dev.yml      开发环境（连本机 Docker 的 MySQL/Redis）
    │   ├── application-prod.yml     生产环境（连 compose 服务名，密码走环境变量）
    │   └── mapper/                  MyBatis XML（如果用 XML 写 SQL）
    └── java/com/campus/trade/
        ├── CampusTradeApplication.java   启动类
        ├── common/          统一返回 Result、错误码、业务异常、全局异常处理、UserContext、常量、工具
        ├── config/          MyBatis / Redis(Redisson) / Web(拦截器注册、静态资源、跨域) / Jackson 配置
        ├── auth/            注册登录退出、JwtProvider、LoginInterceptor、AdminInterceptor
        ├── user/            用户信息 + 信用摘要（user_credit_summary）
        ├── category/        商品分类
        ├── product/         商品：发布/编辑/上下架/审核/库存/列表/详情/图片
        ├── history/         浏览记录（详情接口内写入）
        ├── order/           订单：下单/状态机/快照/日志/超时扫描
        ├── review/          评价 + 信用重算
        ├── dispute/         纠纷：发起 + 管理员处理
        └── file/            FileStorageService（本地磁盘实现，预留 OSS 接口）
```

> 为什么按业务模块分包（而不是全项目一个 controller/、一个 service/）：模块内高内聚，改"订单"只动 `order/` 一个目录，找代码快；模块多时也不会出现一个 service 包塞 30 个文件。每个模块内部再分 `XxxController / XxxService / XxxMapper / 实体` 几个文件。

### 2.2 分层职责（一个请求怎么走完）

```text
HTTP 请求
  ▼
Controller   只做：接收参数、基础校验(@Valid)、调用 Service、包装成 Result 返回
  ▼
Service      业务核心：事务边界(@Transactional)、状态机判断、调用 Mapper、组装 DTO
  ▼
Mapper       只做：一条条 SQL（增删改查、条件更新）
  ▼
MySQL / Redis
```

- **Controller 不写业务逻辑**，不直接碰数据库；**Service 不感知 HTTP**（不出现 request/response 对象），方便复用与测试。
- **对外返回用 DTO/VO，不直接返回数据库实体**：比如 `user` 表有 `password` 字段，返回给前端的 `UserVO` 绝不能带它。
- 三种对象各司其职：`实体/DO`（对应数据库表）、`DTO`（接收前端入参）、`VO`（返回给前端）。学习项目可适当合并，但"绝不把带密码的实体直接吐给前端"这条要守住。

## 3. 认证与授权（第一件要搭的基础件）

### 3.1 登录态方案：JWT + Redis 双层

```text
登录成功：
  1) 生成 JWT（载荷含 userId、role、签发时间），用服务端密钥签名 → 返回给前端
  2) 同时把 token（或其 jti）写入 Redis：key=login:token:{userId 或 jti}，value=用户信息，TTL=有效期
后续请求：
  拦截器取 Authorization: Bearer <token>
  → 验签 + 未过期（JWT 自校验）
  → 且 Redis 里存在该 token（服务端可控失效）
  → 解析出 userId/role 放进 UserContext
退出登录：删除 Redis 里的 token → 该 token 立即失效（JWT 本身无法提前作废，靠 Redis 兜这一层）
```

> **为什么两层都要**（面试高频）：JWT 无状态、扩容友好，但签发后无法主动失效（改密码/退出/封号时想让旧 token 立刻失效做不到）；加一层 Redis 白名单，退出/封禁时删 key 即可让 token 立即作废，同时还能存在线态、做单设备登录等。学习项目第一版可先只用 Redis 存 token（最简单），JWT 作为演进项，二者取其一亦可——**但接口契约（返回 token、带 Bearer 头）不变**。

### 3.2 拦截器与 UserContext

- `LoginInterceptor`：拦截需登录的接口，校验 token，成功则 `UserContext.set(currentUser)`，失败返回 401。
- `AdminInterceptor`（或在拦截器内判断）：管理员接口额外校验 `role==1`，否则 403。
- `UserContext`：用 `ThreadLocal<CurrentUser>` 存当前请求的用户，Service 层随时 `UserContext.get()` 取当前用户 id/role。**拦截器 `afterCompletion` 里必须 `remove()`**，否则线程池复用会串号（上一个请求的用户泄漏到下一个请求）。
- 放行清单：`/api/auth/login`、`/api/auth/register`、`GET /api/categories`、`GET /api/products`、`GET /api/products/{id}` 等公开接口不拦。

### 3.3 认证接口实现要点（对应 API 文档第 1 节）

| 接口 | 关键实现 |
| --- | --- |
| POST /auth/register | 校验学号/手机号/密码格式；密码 BCrypt 加密；`user` 与 `user_credit_summary` **同事务**插入（保证详情页不缺信用数据）；靠 `uk_student_no`/`uk_phone` 唯一键兜并发重复注册，冲突转 400"学号或手机号已注册" |
| POST /auth/login | account 既可是学号也可是手机号（一条 SQL `where student_no=? or phone=?`）；BCrypt 校验密码；封禁账号返回 403；成功签发 token 并写 Redis |
| POST /auth/logout | 删除 Redis 里当前 token |
| GET /auth/me | 从 UserContext 取 userId 查库返回（不能像前端 mock 那样固定返回第一个用户） |

## 4. 公共基础件（common / config）

### 4.1 统一返回 Result<T>

```text
Result<T> { code:int, message:String, data:T }
静态方法：Result.ok(data) / Result.ok() / Result.fail(code, message)
Controller 里正常 return Result.ok(vo)；异常统一由全局异常处理转成 Result.fail
```

### 4.2 业务异常 + 全局异常处理

```text
BizException(code, message)：业务层主动抛（如库存不足抛 BizException(409, "库存不足或商品已变化")）
@RestControllerAdvice 全局兜底：
  - BizException           → Result.fail(e.code, e.message)
  - 参数校验异常(MethodArgumentNotValidException) → 400 + 具体字段原因
  - 未捕获异常 Exception    → 500 "服务器繁忙"（日志打全栈，响应不暴露细节）
```

> 好处：Service 里想报错就 `throw new BizException(...)`，不用层层 return 错误码；HTTP 状态统一 200、业务结果看 body.code（与前端 `request.js` 约定一致）。

### 4.3 常量与错误码

- 状态枚举（商品/订单/纠纷/成色/角色）后端也建一份枚举类，**编码值与数据库、与前端 constants 三方一致**（见数据库文档与 API 文档，本文不再重复列举，改动时三处同步）。
- 关键业务常量：确认超时 `CONFIRM_TIMEOUT_HOURS=24`、售后窗口 `DISPUTE_WINDOW_DAYS=7`、防抖 `ORDER_DEBOUNCE_SECONDS=5`、详情缓存 `PRODUCT_CACHE_SECONDS=300`（都做成可配置常量，别散落魔法数字）。

### 4.4 Jackson 配置（Long → String）

```text
全局把 Long / long 序列化为字符串（ObjectMapper 注册 SimpleModule）
→ id、orderNo 等大整数传到前端不丢精度
BigDecimal 保留两位小数输出；LocalDateTime 用 yyyy-MM-dd HH:mm:ss
```

### 4.5 MyBatis / Redis / Web 配置

- MyBatis：开启驼峰映射（`user_id`↔`userId`）、扫描 mapper、分页（PageHelper 或手写 `limit`）。
- Redis：Redisson 客户端（后续做分布式锁/防抖用），序列化用 String/JSON。
- Web：注册拦截器；`/uploads/**` 映射到本地上传目录（让上传的图片能被访问）；开发期跨域优先靠 Vite proxy，不在后端到处加 `@CrossOrigin`。
- 时区统一 `Asia/Shanghai`（JVM、MySQL 连接串 `serverTimezone`、容器时区三处一致，防差 8 小时）。

## 5. 通用机制（贯穿多个模块，先理解再看业务）

### 5.1 防重复 / 幂等（下单为例，三层防护）

```text
第一层 Redis 防抖（体验层）：下单前 SET NX EX 5 一个 key（buyer+product），
        拿不到锁 → 429"操作太频繁"，挡住用户连点。
第二层 唯一键幂等（正确性）：trade_order 有 uk_buyer_request(buyer_id, request_id)，
        网络超时重试用同一个 requestId → 命中唯一键冲突 → 返回第一次创建的订单（不重复下单）。
第三层 库存条件更新（并发正确性）：见 5.2。
```

> requestId 由**前端进下单页时生成一次 UUID**，提交失败重试沿用同一个（前端设计文档 5.6 已约定）。Redis 防抖只保体验，真正防重复靠数据库唯一键。

### 5.2 条件更新防超卖 / 防重复流转（最重要的一招）

```text
扣库存：UPDATE product SET stock = stock - #{n}
        WHERE id = #{id} AND status = 3 AND stock >= #{n}
        影响行数 = 1 → 扣成功；= 0 → 库存不足或状态变了 → 抛 409
状态流转：UPDATE trade_order SET status = 新状态
        WHERE id = #{id} AND status = 旧状态
        影响行数 = 0 → 已被并发/重复操作处理过 → 抛 409，绝不重复回补库存/重复完成
```

> 为什么不用"先查再改"：两个请求可能同时查到 stock=1 都以为能买，先查再减会超卖。把判断写进 `WHERE`，让数据库行锁保证原子性，是防超卖/防重复的标准做法。

### 5.3 乐观锁 version（编辑商品、信用重算）

```text
UPDATE product SET ... , version = version + 1
       WHERE id = #{id} AND version = #{version}
影响行数 = 0 → 期间被别人改过 → 409"商品已被其他请求修改，请刷新后重试"
```

### 5.4 事务边界与 @Transactional 失效场景（务必掌握）

- 一个业务动作里"多张表要么全成功要么全失败"的，放同一个 Service 方法加 `@Transactional`：如下单要同事务写 `trade_order + product_snapshot + trade_order_log` 并扣库存。
- **@Transactional 失效的常见 4 种**：①方法非 public；②同类内部方法自调用（不走代理）；③异常被自己 try-catch 吞了没抛出；④抛的是受检异常但没配 `rollbackFor`。写事务方法时对照这四点自检。
- 缓存删除放在 **事务提交之后**（afterCommit），避免"缓存已删但事务回滚导致又读回旧数据"。

### 5.5 分页规范

- 入参 `page`（从 1）、`pageSize`（默认 10，最大 50，后端强制夹逼防止前端传超大值拖垮库）。
- 返回 `{ list, total, page, pageSize }`（与 API 文档一致）。

## 6. 商品模块（product）

### 6.1 公开接口

| 接口 | 实现要点 |

### 6.2 卖家接口（需登录，只操作本人商品）

| 接口 | 状态流转/规则 |
| --- | --- |
| GET /products/mine | 当前用户全部状态商品，可按 status 过滤（走 `idx_seller`） |
| POST /products 发布 | 校验分类"存在且启用"；`sellerId` 取 UserContext；创建为**草稿(0)**；商品与 `product_image` 同事务写入 |
| PUT /products/{id} 编辑 | **仅草稿/驳回/已下架可编辑**（在售要先下架，防"审的是旧内容、展示是新内容"）；带 version 乐观锁；只能改自己的（否则 403） |
| POST /products/{id}/submit-review 申请上架 | 前提 状态∈{草稿,驳回,已下架} 且 stock>0；条件更新 → 待审核(1) |
| POST /products/{id}/withdraw-review 撤回 | 待审核(1) → 草稿(0) |
| POST /products/{id}/off-shelf 下架 | 在售(3) → 已下架(4) |
| POST /products/{id}/stock 调库存 | 仅在售；`{delta}` 增减，减少后至少保留 1；条件更新 |

商品状态机：
```text
草稿(0) ──申请上架──▶ 待审核(1) ──通过──▶ 在售(3)
   ▲  ▲                    │ 驳回              │ 下架
   │  └────撤回────────────┘                  ▼
   └──────────────────── 审核驳回(2) ◀──   已下架(4)
下单扣库存到 0 → 已售罄(5)；取消/超时回补库存且原为售罄 → 恢复在售(3)
```

## 8. 订单模块（order，交易核心，最复杂）

对应 API 文档第 5 节、数据库文档表 8/9/10。

### 8.1 下单流程（POST /orders，一个事务里做完）

```text
1. Redis SET NX EX 5 防抖 → 拿不到 → 429
2. 查 uk_buyer_request(buyer_id, request_id) → 已存在 → 直接返回那笔订单（幂等, code=0）
3. 校验：商品在售、买家≠卖家(否则400)、数量合法
4. 条件更新扣库存：UPDATE product SET stock=stock-n WHERE id=? AND status=3 AND stock>=n
   影响行数=0 → 409"库存不足或商品已变化"
5. 扣到 0 → 商品置已售罄(5)
6. 同事务写：trade_order（unitPrice 用库中价格，不信前端；total=price*qty；
   status=0；order_no 后端生成；confirm_deadline=now+24h）
   + product_snapshot（下单瞬间商品内容+图片 JSON）
   + trade_order_log（fromStatus=null→toStatus=0, operatorType=0 买家）
7. afterCommit 删商品详情缓存
```

> `unitPrice` 后端按库中价算，`total_amount` 后端算——**绝不信前端传的金额**。`product_snapshot` 保存下单瞬间内容，卖家日后改价/改描述/删图/下架都不影响历史订单和纠纷取证。

### 8.2 订单状态机（confirm / cancel / complete）

```text
待卖家确认(0) ──卖家确认──▶ 已确认(1) ──买家完成──▶ 已完成(2)
      │                        │
      └──买/卖取消(回补库存)───┴──▶ 已取消(3)
待确认(0) 超时未确认 ──系统定时──▶ 超时取消(4)（回补库存）
已确认(1)/已完成(2) ──发起纠纷──▶ 纠纷中(5)（见第 10 节）
```

| 接口 | 流转 | 谁能操作 | 副作用 |
| --- | --- | --- | --- |
| /orders/{id}/confirm | 0→1 | 卖家 | 写日志 |
| /orders/{id}/cancel | 0或1→3 | 买或卖 | **回补库存**（售罄商品有货后恢复在售）、写日志、带 reason |
| /orders/{id}/complete | 1→2 | 买家 | 记 finished_at、写日志、**首次完成信用 deal_count+1** |

- 所有流转用**条件更新** `WHERE id=? AND status=旧状态`，影响行数 0 → 409 并返回最新状态，前端刷新。
- 回补库存也用条件更新，`status` 日志保证不会重复回补（数据库文档表 8 的设计）。

### 8.3 can* 字段（订单详情返回，驱动前端按钮）

```text
GET /orders/{id} 时后端按"当前用户身份 + 订单状态"计算：
  canConfirm  = 是卖家 && status==0
  canCancel   = (是买家||卖家) && status∈{0,1}
  canComplete = 是买家 && status==1
  canReview   = 是买家 && status==2 && 未评价
  canDispute  = (是买家||卖家) && status∈{1,2} && 未发起过纠纷（含售后窗口判断）
```
> 前端据此显隐按钮，但**后端每个操作仍独立做最终校验**（前端能被绕过）。

### 8.4 超时关单（定时任务，第一版用扫表）

```text
@Scheduled 每分钟：
  SELECT id FROM trade_order WHERE status=0 AND confirm_deadline<=now() （走 idx_timeout_scan，分批）
  逐单调用 timeoutCancel(orderId)：0→4 条件更新 + 回补库存 + 写日志(operatorType=2 系统)
```
> 第一版扫表足够（简历文档也认可"扫表是第一版/兜底"）；第二步可演进为"RocketMQ 延迟消息为主 + 扫表兜底"，这是现成的面试演进叙事。手动取消与超时取消复用同一段"取消+回补"逻辑，避免两处实现不一致。

## 9. 评价模块（review）

对应 API 文档第 6 节、数据库文档表 11、表 2。

- POST /reviews：前提 **订单已完成(2) 且当前用户是买家**；`reviewerId`/`sellerId` 由订单推导（不信前端）；靠 `uk order_id` 保证**一单一评**，重复 → 409"该订单已评价"。
- 评价成功后触发卖家 `user_credit_summary` 重算（第一版可同步重算，接口契约不变）：`credit_score = 100 + 好评×1 − 差评×3`（夹在 60~100）、更新 `deal_count/review_count/avg_rating/good_review_rate/bad_review_count`；更新带 `version` 防旧任务覆盖新值。
- GET /reviews/seller/{sellerId}：卖家收到的**可见(visible=1)** 评价分页（走 `idx_seller`）。

## 10. 纠纷模块（dispute）

对应 API 文档第 7 节、数据库文档表 12。

### 10.1 发起纠纷（POST /disputes）

```text
前提：订单已确认(1)，或已完成(2)且在售后窗口内（默认7天，常量可配）；当事双方才可发起
同事务：
  建 dispute（applicant/respondent 由订单推导；statement 是"当事人主张非已验证事实"；evidence JSON）
  + 订单存 status_before_dispute（记住进纠纷前的状态，驳回时恢复用）
  + 订单条件更新为 纠纷中(5) + 写日志
靠 uk order_id 保证一单一纠纷，重复 → 409
```

### 10.2 管理员处理（POST /admin/disputes/{id}/handle，action 白名单）

| action | 效果 |
| --- | --- |
| REJECT 驳回 | 纠纷→已驳回(2)；订单**恢复 status_before_dispute** |
| KEEP_COMPLETED 维持完成 | 纠纷→维持完成(3)；订单→已完成(2) |
| CANCEL_TRADE 取消交易 | 纠纷→取消交易(4)；订单→已取消(3)；`restock:true` 时回补库存 |
| NEED_MORE 待补材料 | 纠纷→待补充材料(1)；订单仍为纠纷中(5) |

- 处理动作与订单状态变更**同事务**；记 `handler_id/handle_note/handled_at`，并写订单日志(operatorType=3 管理员)。
- **action 必须走后端白名单**，不接受白名单外的值。
- GET /admin/disputes：按 status 分页排队（走 `idx_status`）。

## 11. 文件模块（file）

对应 API 文档第 2 节。

- POST /files/upload：multipart，字段名 `file`，一次一个；**校验 MIME + 文件头**（不能只看扩展名）；jpg/png/webp、≤5MB；生成随机文件名（防覆盖/防猜名）；返回 `{ "url": "/uploads/xxx.jpg" }`。
- `FileStorageService` 抽象接口，第一版 `LocalFileStorage` 存本地磁盘 volume；预留 `OssFileStorage` 二期切换（对上层只换实现，接口不变）。

## 12. 部署（Docker Compose + Nginx）

> 这一节承接原《全栈实施方案》里的部署内容。前端打包产物由 Nginx 托管，后端是被部署的核心，故并入本文。

### 12.1 架构

```text
浏览器 → Nginx(80) ├── /        → 前端静态文件(Vue 打包产物)
                    └── /api/**  → 反代后端 8080
后端 Spring Boot ── MySQL 8 / Redis 7 / 本地磁盘 volume(图片)
```
关键认知：**compose 写好后本地和云跑同一份文件**，本地跑通≈部署完成 90%，上云只是换台机器 `docker compose up -d` 再配防火墙。

### 12.2 多环境配置（从第一天就分开）

| 端 | 开发 | 生产 |
| --- | --- | --- |
| 后端 | `application-dev.yml`（连 localhost 的 Docker MySQL/Redis） | `application-prod.yml`（连服务名 mysql/redis，密码走环境变量） |
| 前端 | `.env.development`（VITE_USE_MOCK 开关 + Vite proxy /api→8080） | `.env.production`（走 Nginx 同域 /api） |

密钥（JWT secret、数据库密码）一律环境变量注入，绝不进代码和 Git。

### 12.3 compose 组成

- 4 个服务：`mysql`（挂数据 volume + 初始化 init.sql）、`redis`、`backend`（多阶段 Dockerfile：maven 打包→JRE 运行）、`nginx`（托管前端 + 反代）。
- `depends_on` + `healthcheck`：等 MySQL healthcheck 通过再起 backend（否则后端连不上库启动失败）。
- 容器间用**服务名**互访（`jdbc:mysql://mysql:3306/...`），不是 localhost。

### 12.4 上云安全清单

- 安全组只开 22/80；SSH 改密钥登录、禁密码。
- **MySQL/Redis 端口不映射到宿主机公网**（仅 compose 内网访问）。
- 所有默认密码改强密码；`.env` 不进 Git。

## 13. 后端开发顺序建议（对应原方案 D4~D6）

```text
1. 工程骨架：Spring Boot 建项目 + pom 依赖 + application-dev.yml；起 MySQL/Redis 容器、跑 init.sql
2. 基础件：Result + 全局异常 + Jackson(Long→String) + MyBatis/Redis/Web 配置
3. 认证：注册/登录/退出/me + JwtProvider + LoginInterceptor + UserContext（用 Apifox 自测）
4. 类目 + 文件上传（商品依赖它们）
5. 商品：发布/编辑/上下架/审核/列表/详情（先不加缓存，跑通再加）
6. 订单：下单(防抖+幂等+条件扣库存+快照+日志同事务) → 状态机(确认/取消/完成) → 超时扫表
7. 评价 + 信用重算 → 纠纷(发起 + 管理员处理)
8. 浏览记录（详情接口内写入）
9. 加商品详情 Redis 缓存 + 空值缓存 + afterCommit 删缓存
10. 关前端 mock 开关联调（重点核对：Long 精度、时间格式、分页字段名）
11. Docker Compose 全量 → 本地跑通 → 上云
```
每写完一个模块**立即用 Apifox/Postman 自测**，不要攒到最后。

自测验收（不依赖前端）：注册→登录→发布→审核→下单→确认→完成→评价 全链路 2xx；重复 requestId 返回同一订单；两账号并发买库存 1 的商品只成功一单；改短 confirm_deadline 验证超时关单。
