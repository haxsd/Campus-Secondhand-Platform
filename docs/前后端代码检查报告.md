## 1. P0：确认的业务错误（建议立即修复）

### 1.1 下单扣库存的 SQL 会把商品状态改错

**位置**：`backend/src/main/resources/mapper/product/ProductMapper.xml` → `decreaseStockForOrder`

```sql
UPDATE product
SET stock  = stock - #{quantity},
    status = CASE WHEN stock - #{quantity} = 0 THEN 5 ELSE status END,   -- ← 问题在这一行
    version = version + 1
WHERE id = #{id} AND status = 3 AND stock >= #{quantity} AND deleted = 0
```

XML 里的注释写着「CASE 只依据更新前库存判断」。**这个假设是错的。**

MySQL 的 `UPDATE ... SET a=..., b=...` 是**从左到右依次求值**的：第一个赋值 `stock = stock - n` 执行完之后，后面表达式里再出现的 `stock` 已经是**新值**。所以 `stock - #{quantity}` 实际算的是 `(旧库存 - n) - n`，等于把库存减了两次。

**我在你本机的 MySQL 上用临时表实测复现过**（下单数量 = 1）：

```sql
CREATE TEMPORARY TABLE t (id INT PRIMARY KEY, stock INT, status INT);
INSERT INTO t VALUES (1,1,3),(2,2,3),(3,5,3);
UPDATE t SET stock = stock - 1,
             status = CASE WHEN stock - 1 = 0 THEN 5 ELSE status END
WHERE id IN (1,2,3);
```

| 原库存 | 期望结果 | **实际结果** |
|---:|---|---|
| 1 | stock=0，status=5 售罄 | stock=0，**status=3 仍在售** |
| 2 | stock=1，status=3 在售 | stock=1，**status=5 被误标售罄** |
| 5 | stock=4，status=3 在售 | stock=4，status=3（这一档恰好正确） |

**造成的两个真实后果：**

1. **最后一件卖掉后商品不下架**：库存 0 但 status 仍是 3，首页公开列表的过滤条件如果只看 `status=3`，这件 0 库存商品会继续挂在首页；买家点进去下单，必然撞到 `stock >= quantity` 失败，看到一个莫名其妙的 409。
2. **卖掉倒数第二件时商品被误判售罄**：明明还剩 1 件，status 却变成 5。而 5 在当前状态机里是个**死状态**（见 3.4），卖家既不能下架、也不能调库存、也不能编辑，只能等这单被取消才可能恢复。

**建议改法**（两种都可以，第一种最小改动）：

```sql
-- 方案 A：显式用旧值判断（推荐，语义最清楚）
status = CASE WHEN stock = #{quantity} THEN 5 ELSE status END,
stock  = stock - #{quantity},

-- 方案 B：保持顺序但把表达式改对
stock  = stock - #{quantity},
status = CASE WHEN stock = 0 THEN 5 ELSE status END,   -- 此处 stock 已是新值
```

方案 A 更好：不依赖读者记住「MySQL SET 从左到右」这条冷知识。

> 这个 bug 的根因是**没有一条断言真实 SQL 行为的测试**。修复时建议顺手补一个集成测试：库存 2 件下单 1 件后，断言 `stock=1 且 status=3`；库存 1 件下单 1 件后，断言 `stock=0 且 status=5`。

## 2. P1：需要尽快决定并处理

### 2.1 信用分 credit_score 永远是 100，从来没被计算过

- 数据库设计文档写的规则是：`credit_score = 100 + 好评×1 − 差评×3`，区间 60~100（`docs/数据库设计文档.md` 第 57 行）。
- 实际代码里全库搜索 `credit_score`，只有 `ProductMapper.xml` 第 163 行**读**它（`COALESCE(cs.credit_score, 100)`），**没有任何一处写它**。
- `ReviewMapper.recalculateSellerCredit` 重算的是 `review_count / avg_rating / good_review_rate / bad_review_count` 四项，唯独没算 `credit_score`。

结果：商品详情页、管理员审核详情页上的「卖家信用 100 分」是个永远不变的常量。

**建议**：在 `recalculateSellerCredit` 的同一条 SQL 里顺带算出来，保持「摘要是可从 trade_review 重建的读模型」这个设计：

```sql
cs.credit_score = LEAST(100, GREATEST(60, 100 + r.good_count - 3 * r.bad_count))
```
（`good_count` 用 `SUM(rating >= 4)`，`bad_count` 已有。）

### 2.2 纠纷缺少「7 天售后窗口」判断

- 后端设计文档第 151、351 行、API 文档第 219 行都写了：已完成订单只能在售后窗口内（默认 7 天，常量可配）发起纠纷。
- `DisputeService.create()` 实际只判断了 `status == 1 || status == 2`，**没有任何时间判断**。

结果：一笔三年前完成的订单，今天仍然可以发起纠纷、把订单打回「纠纷中」。

**建议**：加一个配置常量 `campus.dispute.window-days`，在 `status == 2` 分支里比较 `order.finishedAt`。

### 2.3 API 文档写了但没实现的接口：`GET /api/disputes/{id}`

`docs/API接口文档.md` 第 220 行列了「纠纷详情（当事双方/管理员）」，后端 `DisputeController` 只有 `POST /disputes`。前端目前也没调用它，所以**不影响运行**，但属于文档与实现不一致。

**建议**：要么补实现，要么从 API 文档里删掉。我倾向后者——前端管理端列表里已经带了 statement 和 evidence，暂时够用。

### 2.4 「已售罄(5)」是个死状态，卖家会被卡住

对照 `ProductMapper.xml` 里几条状态机 SQL 的 WHERE 条件：

| 操作 | 允许的原状态 | 售罄(5) 能做吗 |
|---|---|---|
| 编辑 `updateBySeller` | 0 草稿 / 2 驳回 / 4 已下架 | 否 |
| 申请上架 `submitReviewBySeller` | 0 / 2 / 4 且 stock>0 | 否 |
| 下架 `offShelfBySeller` | 3 在售 | 否 |
| 调库存 `adjustStockBySeller` | 3 在售 | 否 |

也就是说商品一旦卖光进入 5，卖家**什么都做不了**，只能等某笔订单被取消、由 `restoreStockForCancelledOrder` 把它从 5 拉回 3。叠加上面 P0 的误判售罄，这个坑会被放大。

**建议**：允许 `5 → 4`（下架）和 `5` 可编辑/可补货，或者允许 `adjustStockBySeller` 在 `status IN (3,5)` 时生效并把 5 改回 3。这是业务取舍，等你拍板，我不擅自改。

### 2.5 前端「编辑商品」是拉全量列表再 find 出一件

`frontend/src/views/ProductEditView.vue` 的 `loadForEdit()`：

```js
const response = await getMyProducts()          // GET /products/mine，返回该卖家全部商品
const p = response.list.find((item) => String(item.id) === String(productId.value))
```

原因是后端只有公开详情 `GET /products/{id}`，而它只返回在售商品，草稿/驳回商品取不到，所以前端只能绕路。目前商品少，能跑；卖家商品上百件后就是每次编辑都拖全表。

**建议**：后端补一个 `GET /products/{id}/edit`（或让 `/products/mine` 支持 `id` 过滤）返回 `MyProductVO` 单条。属于新增接口，等你确认。

## 3. P2：不影响正确性，但建议改

### 3.1 四个 VO 的时间字段会带 ISO 的「T」

`application.yml` 里配了 `spring.jackson.date-format: yyyy-MM-dd HH:mm:ss`，**但这个配置对 `LocalDateTime` 不生效**——它只作用于老的 `java.util.Date`。JSR-310 类型走的是 JavaTimeModule，`write-dates-as-timestamps: false` 下输出 ISO-8601。

我用项目自己的 ObjectMapper 实测确认：

```text
输入 LocalDateTime.of(2026,7,24,10,15,30)
输出 {"createdAt":"2026-07-24T10:15:30"}      ← 带 T
```

订单相关 VO（`OrderDetailVO`、`OrderListItemVO`、`OrderLogVO`、`OrderCreatedVO`、`AdminDisputeVO`）都手动加了 `@JsonFormat`，所以正常。**漏掉的四个**会在页面上直接显示带 T 的字符串：

| VO | 字段 | 显示位置 |
|---|---|---|
| `BrowseHistoryVO` | `lastViewTime` | 浏览记录页「浏览于 2026-07-24T10:15:30」 |
| `RecentReviewVO` | `createdAt` | 商品详情「最近评价」时间 |
| `MyProductVO` | `createdAt` | 我的商品 |
| `PendingProductVO` | `createdAt` | 管理端待审核列表「提交时间」 |

**建议**：与其逐个补 `@JsonFormat`，不如在 `JacksonConfig` 里统一注册一次 `LocalDateTime` 的序列化器，一劳永逸，并且可以把已有的 `@JsonFormat` 都删掉。

### 3.2 卖家信用变化时，会把该卖家**所有**商品缓存逐个删除

`SellerDetailCacheInvalidator.invalidateAfterCommit()`：

```java
productMapper.selectBySeller(sellerId, null).forEach(p -> cacheService.invalidate(p.getId()));
```

一次评价提交 = 一次全表扫该卖家商品 + N 次 Redis 删除。逻辑是对的（详情里确实嵌了卖家信用），量大时是性能点。**当前数据量下无需处理**，知道就行。

### 3.3 管理端纠纷列表是 N+1 查询

`DisputeService.list()` 对每条纠纷再查 order、product、buyer、seller 四次。10 条纠纷 = 41 次查询。**建议**改成 XML 里一条 JOIN，或先批量取 id 再 `IN` 查。同样是「知道即可，暂不紧急」。

### 3.4 裁决「取消交易」时不回退 deal_count

`DisputeService.handle()` 的 `CANCEL_TRADE` 分支：如果这笔订单原本已经是「已完成(2)」（完成时已经给卖家 `deal_count + 1`），裁决取消后订单变已取消，但成交数没有减回去。

`KEEP_COMPLETED` 分支处理得很好（`if (o.getStatusBeforeDispute() == 1)` 才 +1，避免重复计数），说明这个点你是想过的，只是漏了对称的减法。

### 3.5 认证白名单里有一条指向不存在接口的规则

`PublicRequestMatcher` 里的 `SELLER_REVIEW_PATTERN = ^/reviews/seller/\d+$`，但 `ReviewController` 只有 `POST /reviews`，没有这个查询接口。**不是安全漏洞**（放行一个不存在的路径只会 404），但是死规则，容易让读代码的人误以为有这个接口。

### 3.6 文档写了的 429 防抖没有实现

后端设计文档第 151 行的 `ORDER_DEBOUNCE_SECONDS=5`、`ErrorCode.TOO_MANY_REQUESTS(429)` 都在，但没有任何地方抛 429。目前重复下单靠 `requestId` 幂等挡住了，功能上没问题。**建议**：要么实现，要么从文档删掉这个常量。

### 3.7 浏览记录不过滤商品状态

`BrowseHistoryMapper.selectPage` 只排除了 `deleted=0`，不过滤 status。所以已下架/售罄的商品仍会出现在浏览记录里，点进去会提示「商品不存在或已下架」。这可以算合理设计（浏览记录本就是历史），但前端最好在卡片上打个「已下架」角标。属于体验取舍。

### 3.8 学习指南里的接口表有一处路径笔误

`backend/docs/后端工程学习指南.md` 第 805 行写的是 `/api/browse-histories`，实际是 `/api/browse-history`（前端 `api/history.js` 和 API 文档都用单数）。**本次已随指南优化一并修正。**

### 3.9 开发默认密钥

`application-dev.yml` 里 `CT_DB_PASSWORD:root123`、`CT_JWT_SECRET:campus-trade-local-jwt-secret-change-me-2026` 都是明文默认值。写法本身是对的（环境变量优先），但部署时必须用环境变量覆盖。**上线前记得在部署文档里单独强调一次。**

这些是我重点怀疑过、最后验证下来是对的：

1. **前后端 32 个接口全部对得上**：路径、HTTP method、请求体字段名、query 参数名逐个核对，没有一处错配。包括容易错的 `POST /orders/{id}/cancel` 允许空 body（`@RequestBody(required = false)`）、`GET /products/mine?status=` 可选参数。
2. **交易时间格式对得上**：前端 `el-date-picker` 用 `value-format="YYYY-MM-DD HH:mm:ss"`，后端 `CreateOrderRequest.tradeTime` 用 `@JsonFormat(pattern = "yyyy-MM-dd HH:mm:ss")`，能正常解析。
3. **静态图片不会被 401 拦住**：`LoginInterceptor` 挂在 `/**` 上，本来会连 `/api/uploads/*.jpg` 一起拦（`<img>` 标签不会带 Authorization 头），但 `PublicRequestMatcher` 第 41 行显式放行了 `/uploads/`。这一处处理得很到位。
4. **公开白名单是「方法 + 路径」双重判断**：`GET /products/{id}` 公开、`PUT /products/{id}` 要登录，没有用 `/products/**` 一把梭。
5. **浏览记录的 id 是商品 id 不是记录 id**：`BrowseHistoryMapper.xml` 里 `SELECT p.id`，所以前端 `ProductCard` 用 `product.id` 跳详情是对的。这一点我特意查了，因为 VO 同时有 `id` 和 `productId` 两个字段，很容易踩。
6. **`restoreStockForCancelledOrder` 没有 P0 那个坑**：它的 `CASE WHEN status = 5` 读的是 status 列，而 SET 里没有先改 status，所以求值正确。
7. **纠纷裁决用了条件更新防并发**：`updateHandled ... WHERE id=? AND status IN (0,1)`，两个管理员同时点，只有一个成功，另一个收到「该纠纷已处理」。
8. **订单超时取消的多实例安全**：`OrderTimeoutScheduler` 扫描 + `OrderTimeoutService.cancelIfExpired` 单笔事务条件更新，影响行数为 0 就直接返回，不会重复回补库存。
9. **文件上传做了文件头魔数校验**：不信任浏览器 MIME、忽略原文件名、UUID 重命名、`target.startsWith(uploadDirectory)` 防路径穿越。这块写得很好。
10. **`user_credit_summary` 与 `user` 在注册时同事务创建**，不会出现「有用户没摘要」。
