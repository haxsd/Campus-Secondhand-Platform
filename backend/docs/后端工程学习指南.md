## 第一部分　宏观认知：后端工程到底在做什么

### 1.1 后端在整个系统中的位置

校园二手交易平台由四部分协作：

| 部分 | 主要职责 | 当前项目中的实现 |
|---|---|---|
| 前端 | 展示页面、收集输入、发 HTTP 请求 | Vue 3 + Axios |
| 后端 | 校验请求、执行规则、控制权限、组织响应 | Spring Boot |
| MySQL | 持久保存用户、商品、订单等业务数据 | Docker 中的 MySQL 8 |
| Redis | 保存有时效的高速数据 | 登录态白名单、商品详情缓存 |

一次普通请求的完整路径如下：

```text
# 浏览器只和后端 HTTP 接口交互，不直接连接数据库
Vue 页面
  → Axios 请求 /api/...
  → Spring MVC 拦截器：判断是否需要登录
  → Controller：接收 HTTP 参数
  → Service：执行业务规则
  → Mapper + XML：执行 SQL
  → MySQL / Redis：读写数据
  → Result：包装成统一 JSON
  → 前端响应拦截器：根据 code 处理成功或失败
```

一句话理解：**后端是系统规则的最终执行者**。前端校验可以改善体验，但用户能够绕过前端直接调用接口，所以账号权限、数据归属、库存、订单状态等重要规则最终必须由后端检查。


### 1.3 为什么按“业务模块 + 模块内分层”组织

当前结构不是把全项目的 Controller 全放一个大目录，而是先按业务分组：

```text
# 先按业务模块聚合，再在模块内部划分职责
com.campus.trade/
├─ auth/                 # 认证模块：注册、登录、JWT、登录态和权限拦截
│  ├─ controller/        # 认证 HTTP 接口
│  ├─ dto/               # 认证请求参数
│  ├─ interceptor/       # 登录与管理员权限校验
│  ├─ jwt/               # JWT 签发和解析
│  ├─ service/           # 认证业务流程
│  └─ vo/                # 认证接口响应数据
├─ category/             # 商品分类模块
│  ├─ controller/        # 分类 HTTP 接口
│  ├─ entity/            # category 表对应对象
│  ├─ mapper/            # 分类数据库访问接口
│  ├─ service/           # 分类业务
│  └─ vo/                # 返回前端的分类数据
├─ product/              # 商品模块：发布、编辑、状态机、审核、公开查询
│  ├─ controller/        # 商品与管理员审核 HTTP 接口
│  ├─ dto/               # 发布、编辑、库存、审核请求参数
│  ├─ entity/            # product 表对应对象
│  ├─ mapper/            # 商品、图片与审核日志数据库访问
│  ├─ model/             # 商品状态、成色和查询读模型
│  ├─ service/           # 商品状态机、归属校验和事务
│  └─ vo/                # 公开列表、详情、卖家管理和审核列表响应
├─ order/                # 订单模块：下单、库存占用、快照、状态流转
│  ├─ controller/        # 当前用户的订单 HTTP 接口
│  ├─ dto/               # 下单、取消订单请求参数
│  ├─ entity/            # 订单、商品快照、订单日志表对应对象
│  ├─ mapper/            # 订单、快照、日志及条件更新 SQL
│  ├─ model/             # 订单状态编码
│  ├─ mq/                # 超时延迟消息的配置、发送和消费
│  ├─ service/           # 幂等、库存、权限、状态机和事务
│  └─ vo/                # 创建结果、列表、详情、快照和状态日志响应
├─ review/               # 评价模块：已完成订单的一单一评与信用摘要重算
├─ dispute/              # 纠纷模块：双方发起、管理员裁决和订单状态回退
├─ file/                 # 文件模块：图片校验、本地存储与上传响应
│  ├─ controller/        # multipart 图片上传接口
│  ├─ service/           # MIME、文件头、大小和随机文件名校验
│  └─ vo/                # 上传后的公开 URL
├─ history/              # 浏览历史模块：登录用户的商品访问记录
│  ├─ controller/        # 浏览历史分页接口
│  ├─ mapper/            # 浏览记录写入和关联商品的查询 SQL
│  ├─ service/           # 仅在已登录时记录、分页读取历史
│  └─ vo/                # 历史列表响应数据
├─ user/                 # 用户模块：个人中心资料与密码修改
│  ├─ controller/        # /users/me 当前用户接口
│  ├─ dto/               # 允许修改的资料、密码请求
│  ├─ entity/            # user 表对应对象
│  ├─ mapper/            # 用户数据库访问
│  ├─ model/             # 用户角色、状态枚举
│  ├─ service/           # 资料权限、旧密码校验与令牌吊销
│  └─ vo/                # 不含密码哈希的个人中心响应
├─ common/               # 多个模块共用的响应、异常和用户上下文
├─ config/               # Spring MVC、Redis、密码、JSON 配置
└─ CampusTradeApplication.java  # 整个后端的启动入口
```

这样组织的好处是：开发“认证”功能时，相关文件基本都在 `auth` 中；将来模块变大或需要拆成独立服务时，边界也更清楚。

并不是每个模块都必须机械地拥有所有分层。`user` 现在有完整的个人中心闭环，因此拥有 Controller、Service、DTO 和 VO；如果将来某个模块只负责一个枚举或工具能力，也不应为了目录看起来整齐而创建没有用途的空类。

**本项目必须遵守的简化规则**

本项目首先是用于学习和面试讲解的单体项目，代码应以“能直接读懂”为优先，而不是提前模仿大型生产系统：

1. 只实现当前已经明确的需求，不为“以后可能会用”提前增加接口、版本号、策略类和配置项。
2. 一个基础类型能够表达的数据，不额外创建 DTO。比如超时消息只需要订单 ID，就直接发送订单 ID，不包装 JSON 事件。
3. 只有确实减少重复或隔离不同职责时才新增类；不能仅为了套设计模式而增加调用层级。
4. 配置项只开放当前需要调整的内容，其余使用框架默认值，出现真实需求后再增加。
5. 简化不能删除正确性边界。事务、权限校验、并发条件更新、幂等、缓存提交后删除和 MQ 失败兜底必须保留。
6. 每次引入新抽象前先回答两个问题：“现在是否有第二种实现？”“删除它是否会影响当前功能？”两个答案都是“否”时，不增加该抽象。

后续开发和重构都以这六条为检查标准：**不过度设计，也不以简化为理由牺牲业务正确性。**

## 第二部分　当前工程结构与搭建顺序

### 2.1 后端工程的关键目录

```text
# backend 是一个独立 Maven 工程
backend/
├─ pom.xml                         # Maven 坐标、Java 版本和依赖
├─ docs/
│  └─ 后端工程学习指南.md          # 后端唯一的工程说明文档
└─ src/
   ├─ main/
   │  ├─ java/com/campus/trade/    # Java 生产代码
   │  └─ resources/
   │     ├─ application.yml        # 所有环境共享的配置
   │     ├─ application-dev.yml    # 本地开发环境配置
   │     └─ mapper/                 # MyBatis SQL XML
   └─ test/java/com/campus/trade/  # 测试代码，包结构尽量对应生产代码
```

`target/` 是 Maven 编译生成的目录，不是手写源码。里面的 `.class`、测试报告和 JAR 都可以重新生成，不要在其中修改代码。

### 2.2 应用如何启动

入口是 `CampusTradeApplication.main()`：

```java
@SpringBootApplication // 开启自动配置，并扫描 com.campus.trade 根包下的 Spring 组件
public class CampusTradeApplication {

    public static void main(String[] args) {
        // 创建 Spring 容器、装配 Bean，并启动内嵌 Tomcat
        SpringApplication.run(CampusTradeApplication.class, args);
    }
}
```

启动阶段主要发生这些事情：

1. Maven 把依赖放进 classpath；
2. Spring 扫描 `@Controller`、`@Service`、`@Component`、`@Configuration`；
3. Spring 根据构造器建立对象之间的依赖关系；
4. 创建数据源、StringRedisTemplate、PasswordEncoder 等基础组件；
5. MyBatis 注册 Mapper；
6. Spring MVC 注册 Controller 和拦截器；
7. 内嵌 Tomcat 在默认 `8080` 端口接收请求。

### 2.3 配置文件为什么拆成两个

`application.yml` 保存所有环境通用的规则：

- 应用名称；
- 默认启用 `dev` 环境；
- JSON 时间格式；
- 服务端口和 `/api` 上下文路径；
- MyBatis XML 扫描路径；
- Actuator 暴露范围。

`application-dev.yml` 保存本地开发环境的连接信息：

- MySQL 地址、账号和连接池；
- Redis 地址；
- JWT 签发者、密钥和有效期；
- 开发日志级别。

配置采用“环境变量优先、冒号后是默认值”的写法：

```yaml
spring:
  datasource:
    # 如果系统存在 CT_DB_PASSWORD 就使用它，否则使用本地默认值 root123
    password: ${CT_DB_PASSWORD:root123}

campus:
  jwt:
    # 生产环境必须通过环境变量提供独立随机密钥，不能使用开发默认值
    secret: ${CT_JWT_SECRET:campus-trade-local-jwt-secret-change-me-2026}
```

这种写法让同一份代码可以进入不同环境，数据库密码不需要硬编码进 Java 类。

### 2.4 从零搭建这类工程的合理顺序

当前项目采用“先地基、后业务”的顺序：

1. 创建 Java 17 + Spring Boot Maven 工程；
2. 配置 MySQL、MyBatis 和 Redis 连接；
3. 定义统一响应 `Result`；
4. 定义错误码、业务异常和全局异常处理；
5. 配置 JSON 序列化和密码编码器；
6. 打通最简单的分类查询链路；
7. 实现注册以及数据库事务；
8. 实现登录、JWT 和 Redis 登录态；
9. 注册登录拦截器和管理员拦截器；
10. 编写单元测试与外部服务集成测试；
11. 完成商品发布、审核和公开查询闭环；
12. 再按照订单、评价、纠纷的业务顺序继续开发。

这个顺序的核心是：**越基础、被越多业务依赖的能力越早完成**。例如没有统一异常处理时就开发十几个业务模块，后面每个模块都要重复返工。

## 第三部分　核心概念逐个理解

### 3.1 Spring Bean 与构造器注入

带有以下注解的类会由 Spring 创建和管理：

- `@RestController`：HTTP 接口；
- `@Service`：业务服务；
- `@Component`：普通组件；
- `@Configuration`：配置类；
- `@Mapper`：由 MyBatis 创建代理对象。

`AuthController` 不自己 `new AuthService()`，而是使用构造器注入：

```java
private final AuthService authService; // final 表示依赖创建后不能被替换

public AuthController(AuthService authService) {
    // Spring 从容器中找到 AuthService，并在创建 Controller 时传进来
    this.authService = authService;
}
```

构造器注入能直接看出一个类依赖什么，也方便测试时传入 Mock 对象。字段注入虽然代码短，但依赖被隐藏，脱离 Spring 容器后也不容易测试。

### 3.2 Controller、Service、Mapper 分别负责什么

以分类查询为例：

| 层 | 文件 | 职责 |
|---|---|---|
| Controller | `CategoryController` | 处理 `GET /categories`，返回统一响应 |
| Service | `CategoryService` | 组织查询规则，把 Entity 转成 VO |
| Mapper | `CategoryMapper` | 声明数据库访问方法 |
| XML | `CategoryMapper.xml` | 编写真实 SQL |

标准调用方向是：

```text
# 上层可以调用下层，下层不反向依赖 HTTP 层
Controller
  → Service
  → Mapper
  → Mapper XML
  → MySQL
```

几个重要边界：

- Controller 不直接写 SQL；
- Mapper 不判断“用户是否可以购买自己的商品”等业务规则；
- Service 不接触 `HttpServletRequest`；
- Entity 不直接作为接口响应返回；
- 通用异常转换交给 `GlobalExceptionHandler`。

### 3.3 Entity、DTO、VO 为什么不能混用

三个对象看起来都只是字段集合，但数据方向不同：

| 类型 | 数据方向 | 示例 | 是否可能含敏感字段 |
|---|---|---|---|
| Entity | 数据库 ↔ 后端 | `User` | 是，例如密码哈希、账号状态 |
| DTO | 前端 → 后端 | `RegisterRequest` | 是，例如用户提交的明文密码 |
| VO | 后端 → 前端 | `LoginUserVO` | 应只包含允许公开的字段 |

注册时的数据转换是：

```text
# 输入和持久化模型分离，安全字段由后端决定
前端 JSON
  → RegisterRequest DTO       # 只承接允许用户填写的字段
  → User Entity               # 后端补充 role、status、密码哈希
  → user 表
```

登录响应不能直接返回 `User`，否则 `password` 等内部字段可能被 Jackson 序列化。项目使用 `LoginUserVO` 主动选择 `id`、`nickname`、`avatar`、`campus` 和 `role`。

### 3.4 record 是什么

`LoginRequest`、`Result`、`JwtClaims` 等只负责承载数据，因此使用 Java `record`：

```java
// record 自动生成构造器、account()、password()、equals()、hashCode() 和 toString()
public record LoginRequest(
        String account,  // 学号或手机号
        String password  // 用户本次提交的明文密码，只用于校验
) {
}
```

record 的字段不可在创建后重新赋值，适合请求、响应和不可变值对象。数据库 Entity 使用普通 JavaBean，是因为 MyBatis 需要通过 setter 写入查询结果，并在插入后回填自增主键。

### 3.5 参数校验如何工作

`RegisterRequest` 在字段上声明规则，Controller 参数上使用 `@Valid`：

```java
public record RegisterRequest(
        @NotBlank(message = "请输入手机号") // 拒绝 null、空字符串和纯空格
        @Pattern(
                regexp = "^1\\d{10}$",     // 当前规则要求 1 开头、总共 11 位数字
                message = "手机号格式不正确"
        )
        String phone
) {
}

@PostMapping("/register")
public Result<Void> register(
        @Valid @RequestBody RegisterRequest request // JSON 转 DTO 后立即执行字段校验
) {
    authService.register(request);                  // 校验通过后才进入业务层
    return Result.ok();                             // 注册成功不需要额外 data
}
```

校验失败时，Spring 抛出 `MethodArgumentNotValidException`。`GlobalExceptionHandler` 捕获它，并转换成项目统一的 `{code, message, data}`。

注意：格式校验不能代替业务校验。`@Pattern` 能检查手机号格式，却不能判断手机号是否已经注册；重复检查必须由 Service 和数据库唯一索引共同保证。

### 3.6 MyBatis 接口与 XML 如何对应

`UserMapper` 只声明 Java 方法：

```java
@Mapper // MyBatis 会为该接口创建代理对象，业务层无需手写实现类
public interface UserMapper {

    Optional<User> selectByAccount(
            @Param("account") String account // @Param 名称供 XML 中的 #{account} 使用
    );
}
```

XML 中的 `namespace` 对应接口完整类名，`id` 对应方法名：

```xml
<!-- namespace 必须与 UserMapper 的完整包名一致 -->
<mapper namespace="com.campus.trade.user.mapper.UserMapper">

    <!-- id=selectByAccount 对应同名 Java 方法 -->
    <select id="selectByAccount"
            resultType="com.campus.trade.user.entity.User">
        SELECT id, student_no, phone, password, nickname, avatar,
               campus, role, status, created_at, updated_at
        FROM `user`
        WHERE student_no = #{account}  <!-- 用户可以使用学号登录 -->
           OR phone = #{account}       <!-- 也可以使用手机号登录 -->
        LIMIT 1                        <!-- 两列都有唯一索引，最多取一行 -->
    </select>
</mapper>
```

`application.yml` 开启了 `map-underscore-to-camel-case`，所以数据库的 `student_no` 能自动映射为 Java 的 `studentNo`。

### 3.7 事务解决什么问题

注册不是只插入 `user` 一张表，还要初始化 `user_credit_summary`。这两个操作必须“要么都成功，要么都失败”：

```java
@Transactional // 方法正常结束时提交；运行时异常向外抛出时整体回滚
public void register(RegisterRequest request) {
    userMapper.insert(user);                    // 第一步：创建用户
    userMapper.insertCreditSummary(user.getId()); // 第二步：初始化信用摘要
}
```

如果第二次插入失败而没有事务，数据库会留下“有用户、没有信用摘要”的半成品数据。事务保证两次 SQL 属于同一个原子操作。

`@Transactional(readOnly = true)` 用在纯查询方法上，用于明确表达该方法不会修改数据库，也为以后读写分离留下空间。

### 3.8 为什么密码不能明文保存

项目使用 BCrypt：

```java
// 注册：把明文密码转换为带随机盐的不可逆哈希，再存入数据库
String passwordHash = passwordEncoder.encode(request.password());

// 登录：让 BCrypt 比较本次明文与数据库哈希，不能把哈希“解密”回原密码
boolean matched = passwordEncoder.matches(
        request.password(), // 用户本次输入的明文
        user.getPassword()  // 数据库保存的 BCrypt 哈希
);
```

同一个密码多次执行 `encode` 通常会得到不同字符串，因为 BCrypt 自动加入随机盐。这不是错误，登录时必须使用 `matches`，不能重新编码后直接比较两个字符串。

密码哈希降低数据库泄漏后的风险，但不能弥补弱密码、日志打印密码或把密码返回前端等问题。任何日志、VO 和异常信息都不应包含密码。

### 3.9 JWT 是什么

JWT 是服务端签名的令牌，通常由三段组成：

```text
# 三段使用英文句点连接；Payload 可读取，不代表加密
Header.Payload.Signature
# Header：签名算法
# Payload：userId、role、jti、签发和过期时间
# Signature：用于判断前两段是否被篡改
```

当前项目的关键字段：

| 字段 | 含义 | 当前值 |
|---|---|---|
| `iss` | 谁签发的 | `campus-trade` |
| `sub` | 令牌属于谁 | 用户 ID |
| `jti` | 本次登录的唯一编号 | 随机 UUID |
| `role` | 用户角色 | `0` 普通用户，`1` 管理员 |
| `iat` | 签发时间 | 当前时间 |
| `exp` | 过期时间 | 默认七天后 |

JWT 的 Payload 可以被解码读取，所以不能放密码、手机号等秘密。签名只能防止篡改，不负责隐藏内容。

### 3.10 为什么有 JWT 还需要 Redis

只使用 JWT 时，令牌一旦签发，在过期前通常一直有效。用户点击退出登录，服务端无法让已经发出的 JWT 立即消失。

当前项目把 JWT 的 `jti` 同时写入 Redis：

```text
# Redis 登录态示例；一天无访问自动过期，有效访问自动续期
key   = login:token:<jti>   # 每次登录拥有独立 key
value = 1                   # 值本身无业务含义，只关心 key 是否存在
ttl   = 1 天                # 每次有效请求后重新变为 1 天
```

后续请求必须同时满足：

1. JWT 签名正确；
2. JWT 签发者正确；
3. JWT 尚未过期；
4. Redis 中仍存在该 `jti`。

JWT 的 7 天是一次登录的最长有效期，Redis 的 1 天是空闲有效期。用户持续访问时，`getAndExpire()` 会用一次 Redis 操作读取登录态并刷新 TTL；连续一天没有访问时，Redis 自动删除该 key。退出登录仍只需要删除当前 `jti`，即使 JWT 尚未到期，后续请求也会被拒绝。

### 3.11 拦截器如何完成登录校验

`WebMvcConfig` 按顺序注册两个拦截器：

```java
// 第 0 顺位：对所有请求先判断是否公开；受保护请求必须完成登录认证
registry.addInterceptor(loginInterceptor)
        .addPathPatterns("/**")
        .order(0);

// 第 1 顺位：只有 /admin/** 继续检查管理员角色
registry.addInterceptor(adminInterceptor)
        .addPathPatterns("/admin/**")
        .order(1);
```

`LoginInterceptor` 的执行逻辑：

```text
# 公开白名单请求会在第一步直接放行
收到请求
  → PublicRequestMatcher 判断是否公开
  → 读取 Authorization: Bearer <token>
  → JwtProvider 验签、检查签发者和过期时间
  → LoginSessionService 检查 Redis 白名单
  → UserContext.set(CurrentUser)
  → Controller 和 Service 执行业务
  → afterCompletion 清理 UserContext
```

`AdminInterceptor` 解决的是授权问题：

- 登录认证回答“你是谁”；
- 管理员授权回答“你能不能执行这个操作”。

前端隐藏管理员菜单只是体验优化，真正的管理员权限必须由后端再次检查。

### 3.12 ThreadLocal 与 UserContext

受保护请求通过认证后，`LoginInterceptor` 把当前身份放进 `UserContext`。Service 可以直接读取当前用户，不需要每个方法重复传 `userId`。

```java
// 当前线程处理请求期间可以获取已经认证的用户
CurrentUser currentUser = UserContext.requireCurrentUser();

// 使用 JWT 中的可信 userId，而不是接受前端传入一个任意 userId
Long userId = currentUser.userId();
```

Tomcat 使用线程池，同一个线程以后会处理别人的请求。因此 `afterCompletion` 必须调用 `UserContext.clear()`。如果忘记清理，上一次请求的身份可能残留到下一次请求，形成严重的串号问题。

### 3.13 统一响应与全局异常

所有接口返回相同结构：

```jsonc
{
  "code": 0,        // 0 表示业务成功；其他值表示业务失败
  "message": "ok",  // 前端可展示的简短信息
  "data": {}        // 真正业务数据；无数据时为 null
}
```

业务代码不需要到处手动拼错误 JSON。Service 遇到可预期问题时抛出 `BizException`：

```java
if (accountBanned) {
    // 业务层只描述错误语义，由全局异常处理统一转换为 Result
    throw new BizException(ErrorCode.FORBIDDEN, "账号已被封禁");
}
```

`GlobalExceptionHandler` 分别处理：

- `BizException`：可预期业务失败；
- `MethodArgumentNotValidException`：DTO 字段校验失败；
- `HttpMessageNotReadableException`：JSON 格式错误；
- 其他 `Exception`：记录完整服务端日志，对前端只返回通用文案。

当前 API 契约使用响应体 `code` 表达业务结果，HTTP 状态保持 200。前端 `request.js` 也是根据 `body.code` 处理。以后如果改成 REST 风格 HTTP 状态码，需要前后端统一修改，不能只改一端。

### 3.14 Long 为什么序列化成字符串

JavaScript 的安全整数上限小于 Java `long` 的最大值。数据库主键增长较大后，直接作为 JSON 数字传给浏览器可能丢失精度。

`JacksonConfig` 只把包装类型 `Long` 序列化成字符串。VO 中的数据库主键使用 `Long`，分页总数等统计值通常使用基本类型 `long`，所以统计值仍是 JSON 数字：

```jsonc
{
  "id": "922337203685477580", // 使用字符串可避免 JavaScript 数字精度丢失
  "total": 21                 // 分页总数保持数字，前端分页组件可以直接使用
}
```

因此前端应把 ID 当字符串保存、传递和比较，不要对 ID 做数学运算。

### 4.2 注册流程：校验、密码哈希和事务

前端发送的数据：

```jsonc
{
  "studentNo": "20260001",   // 学号：4~32 位字母或数字
  "phone": "13812345678",    // 手机号：11 位
  "password": "Abc12345",    // 8~20 位，至少包含字母和数字
  "nickname": "小明",        // 对外展示昵称
  "campus": "东校区"         // 用户所在校区
}
```

完整流程：

```text
# POST /api/auth/register 被明确列入公开白名单
前端提交注册表单
  → RegisterRequest 接收 JSON
  → @Valid 检查字段格式
  → AuthService.register()
  → trim 学号、手机号、昵称和校区
  → 查询学号或手机号是否已经存在
  → BCrypt 加密密码
  → 后端固定 role=USER、status=NORMAL
  → INSERT user，并回填自增 user.id
  → INSERT user_credit_summary
  → 两次插入一起提交
  → Result.ok()
```

并发注册时，两个请求可能同时通过“账号不存在”的预查，所以数据库的唯一索引才是最终防线。SQL 触发 `DuplicateKeyException` 后，Service 仍转换为容易理解的“学号或手机号已注册”。

### 4.3 登录流程：数据库、JWT 与 Redis 协作

前端发送：

```jsonc
{
  "account": "20260001", // 可以是学号，也可以是手机号
  "password": "Abc12345" // 只在本次 HTTPS 请求中传输，不写日志
}
```

完整流程：

```text
# POST /api/auth/login 允许匿名访问
前端提交账号密码
  → LoginRequest 参数校验
  → UserMapper 按学号或手机号查询 User
  → BCrypt.matches 校验密码
  → 检查账号是否封禁
  → JwtProvider 生成 jti 并签发 JWT
  → LoginSessionService 把 jti 写入 Redis
  → 组装 LoginUserVO，排除密码等敏感字段
  → 返回 LoginResponse(token, user)
  → 前端把 token 和用户信息写入 Pinia + localStorage
```

账号不存在和密码错误统一返回“账号或密码错误”，避免攻击者通过错误提示批量探测系统中真实存在的账号。

### 4.4 登录后的受保护请求

前端请求头：

```http
# Axios 请求拦截器会自动添加该请求头
Authorization: Bearer <登录接口返回的 JWT>
```

以后调用受保护接口时：

```text
# JWT 与 Redis 两道检查都通过，Controller 才会执行
请求到达 LoginInterceptor
  → 去掉 Bearer 前缀
  → JwtProvider.parse(token)
  → LoginSessionService.isActive(claims.tokenId()) 检查登录态并刷新一天 TTL
  → UserContext 保存 userId、role、jti
  → Controller / Service 获取当前身份
  → 请求完成后清理 ThreadLocal
```

不要让前端通过请求体指定“当前用户 ID”。例如查询自己的资料应读取 `UserContext`，否则攻击者只需修改请求参数就可能访问别人的数据。

### 4.5 获取当前用户资料

项目只保留 `GET /api/users/me`，由个人中心模块查询完整的最新资料：

```text
# JWT 只提供稳定身份，易变化的资料重新查询数据库
LoginInterceptor 得到可信 userId
  → UserProfileService.getCurrentProfile()
  → UserMapper.selectById(userId)
  → 查询学号、手机号、昵称、头像和校区
  → 转换为 UserProfileVO
  → 返回给前端
```

这样用户修改昵称或头像后，不必等旧 JWT 过期，就能读取最新资料。

### 4.6 退出登录

`POST /api/auth/logout` 的核心不是“删除前端 token”，而是让服务端也不再接受它：

```text
# 前端清 localStorage 只影响当前浏览器，服务端删除 Redis 才能主动吊销
请求携带 JWT
  → LoginInterceptor 校验并得到 jti
  → AuthService.logout()
  → LoginSessionService.delete(jti)
  → Redis 白名单记录消失
  → 同一个 JWT 再次请求时返回 401 业务码
  → 前端清除本地 token 和用户信息
```

当前实现只退出“当前 token”，不会影响同一账号在其他设备签发的 token。这是明确的当前行为，不是异常。

```text
# 商品状态只能按业务规则流转，不能由前端直接提交 status 修改
草稿 / 审核驳回 / 已下架
  → 卖家申请上架
  → 待审核
  → 管理员通过 → 在售
  └ 管理员驳回 → 审核驳回

# 待审核商品可以由卖家主动撤回
待审核 → 草稿

# 在售商品可以由卖家下架
在售 → 已下架
```

商品编辑使用 `version` 乐观锁：前端提交编辑内容时带上读取到的版本号，SQL 会使用
`WHERE id=? AND seller_id=? AND version=? AND status IN (...)` 作为更新条件。影响行数为 0 时，后端返回 409，避免两个浏览器页面互相覆盖内容。

图片上传使用 `/api/files/upload`。上传服务以文件头魔数识别真实格式，只接受 jpg/png/webp，单张最大 5MB；浏览器声明的 MIME 类型可能因 Windows 或图片工具不准确，因此不会作为拒绝真实图片的依据。服务器忽略用户原文件名，以 UUID 生成文件名并保存到 `CT_UPLOAD_DIR`（默认 `backend/uploads`）。`WebMvcConfig` 将该目录映射为 `/api/uploads/**`，上传接口也返回此前缀的 URL，前端开发服务器可以通过既有 `/api` 代理直接展示图片。

公开商品详情使用 Redis 缓存，键为 `product:detail:{商品 id}`，正常详情缓存约 5 分钟并附加少量随机过期时间，避免大量键同时失效；不存在、未上架或已删除的商品会短暂缓存为“空值”，减少反复查询不存在商品造成的数据库压力。商品编辑、提交审核、撤回、下架、库存调整和管理员审核成功后，会在事务提交后删除该商品的详情缓存，下一次读取自动回源并写入新缓存。

`GET /api/products/{id}` 对游客仍可访问；如果请求携带有效 JWT，拦截器会额外建立当前用户上下文，详情读取成功后以 `user_id + product_id` 为唯一键写入或更新时间。`GET /api/browse-histories` 只返回当前登录用户自己的记录。这样既不强迫游客登录，也不会把浏览历史错误写到其他账号。

商品模块的推荐阅读顺序（**每个文件的精读要点见 6.1**）：

1. `product/model/ProductStatus.java`：先理解状态编码；
2. `product/controller/ProductController.java`：了解接口路径；
3. `product/service/ProductService.java`：阅读状态机和权限规则；
4. `product/mapper/ProductMapper.java` 与 `ProductMapper.xml`：查看条件更新与 SQL；
5. `file/service/FileStorageService.java`：理解文件上传的双重校验；
6. `product/service/ProductDetailCacheService.java`：理解 Redis 缓存与空值缓存；
7. `history/service/BrowseHistoryService.java`：理解可选登录态与浏览历史记录；
8. `product/service/ProductServiceTest.java`：理解如何不启动服务也验证核心规则。

### 5.6 订单模块：第二个完整业务闭环

订单状态流转如下：

```text
# 下单后先由卖家确认，再由买家确认线下交易完成
待卖家确认(0) → 卖家确认 → 已确认(1) → 买家确认完成 → 已完成(2)

# 买卖双方都可在交易完成前取消；取消和库存回补位于同一事务
待卖家确认(0) / 已确认(1) → 取消 → 已取消(3) → 商品库存归还
```

`POST /api/orders` 不相信前端传来的价格、卖家或总金额：后端读取商品价格和卖家 ID，再计算金额。每个下单页面生成一个 `requestId`；同一个买家使用同一个 requestId 重试，会返回首个订单而不会再次扣库存。库存扣减使用一条带 `stock >= quantity` 条件的 SQL，两个买家同时下单时最多只有库存足够的请求成功。

订单同时保存 `product_snapshot`：标题、描述、价格、成色、校区和图片在下单瞬间复制，卖家后来编辑商品也不会改变历史订单。订单详情额外返回 `canConfirm`、`canCancel`、`canComplete`，前端据此显示按钮；后端仍会再次检查当前用户身份与状态，前端按钮隐藏不能替代权限控制。

推荐阅读顺序（**每一步的精读要点见 6.4**）：

1. `order/model/OrderStatus.java`：先记住状态编码；
2. `order/controller/OrderController.java`：对应前端订单 API；
3. `order/service/OrderService.java`：理解幂等、库存、权限与事务；
4. `order/mapper/OrderMapper.xml`：查看订单、快照和日志 SQL；
5. `product/mapper/ProductMapper.xml` 中的 `decreaseStockForOrder`：理解条件更新防超卖（⚠️ 这条 SQL 目前有一处已确认的 bug，见第八部分 R1）；
6. `order/service/OrderServiceTest.java` 与 `OrderFlowIntegrationTest.java`：理解无服务测试和真实数据库验证。

### 5.7 后续业务应该怎样继续开发

评价和纠纷已经接入订单闭环：评价只允许买家对已完成订单提交一次，并同步重算卖家的平均评分、好评率和差评数；纠纷只允许交易双方在已确认或已完成阶段发起。管理员可以要求补材料、驳回并恢复原订单状态、维持完成或取消交易并选择回补库存。评价、成交数或库存变化后，会在事务提交后删除受影响商品详情缓存。

订单超时取消采用“RocketMQ 延迟消息主触发 + 定时任务兜底 + 数据库条件更新保证幂等”。订单事务提交后异步发送一条在 `confirmDeadline` 到期时投递的消息；消费者和每分钟扫描一次的 `OrderTimeoutScheduler` 都只调用 `OrderTimeoutService.cancelIfExpired(orderId)`。该方法用 `WHERE status=0 AND confirm_deadline<=CURRENT_TIMESTAMP` 条件更新争夺唯一处理资格，只有更新成功的一方才能回补库存、写系统状态日志并删除商品详情缓存。MQ 默认关闭，未部署时定时任务仍可独立工作。

以后开发订单超时取消、通知等模块时，继续遵循同一闭环：

```text
# 一次只完成一个可验证的业务闭环
确认前端需要的接口和字段
  → 确认数据库表与约束
  → 创建本业务模块目录
  → 定义 DTO / VO / Entity
  → 编写 Mapper 接口与 XML
  → 编写 Service 业务规则和事务
  → 编写 Controller
  → 配置公开或登录权限
  → 编写单元测试
  → 由你启动服务，用前端页面联调
```

开发时保持以下约束：

- 一个业务模块的代码放回自己的模块；
- Controller 保持薄，只处理 HTTP；
- Service 决定业务规则和事务；
- Mapper 只处理数据库访问；
- 前端输入使用 DTO，后端输出使用 VO；
- 用户身份来自 `UserContext`，不信任前端自报的 userId；
- 写操作既检查权限，也检查数据归属和业务状态；
- 金额使用 `BigDecimal`，不要使用 `double`；
- 并发正确性需要数据库约束或条件更新，不能只依赖“先查询再修改”；
- 新增业务时同步补充必要的代码注释和测试。

### 5.8 当前认证模块仍需注意的扩展点

现有登录注册主流程已经完成，但后续功能开发时有两个边界需要处理：

1. 商品详情已经采用**可选登录**：没有 token 可以匿名访问，携带合法 token 时会识别用户并记录浏览历史。今后新增公开接口时，仍需明确它是“完全匿名”还是“可选认证”，不能不经思考地直接放行。
2. 当前 Redis 只按 `jti` 保存单个登录态。以后实现管理员封禁用户、修改密码后全部下线时，需要额外维护“用户 ID → 该用户所有 jti”的关系，才能一次吊销全部设备会话。

上述扩展点不影响当前注册、登录、退出和 `/users/me`，但应该在对应业务开始前处理，而不是等线上出现权限问题后再补。

### 6.1 商品模块：状态机 + 归属校验 + 乐观锁

**① 解决什么问题**

一件商品从「卖家写草稿」到「挂上首页」中间要经过审核，卖家可以撤回、下架、补库存，管理员可以驳回。这些动作不能任由前端提交一个 `status` 字段来决定，必须由后端定义「哪些状态可以变成哪些状态、谁有资格变」。

**② 阅读顺序**

| 顺序 | 文件 | 读的时候关注什么 |
|---:|---|---|
| 1 | `product/model/ProductStatus.java` | 六个状态码的含义，先背下来 |
| 2 | `product/controller/ProductController.java` | 每个动作一个独立 URL，而不是一个 `POST /products/{id}/status?to=3` |
| 3 | `product/dto/CreateProductRequest.java`、`UpdateProductRequest.java` | 校验注解写在哪；`UpdateProductRequest` 比 Create 多一个 `version` |
| 4 | `product/service/ProductService.java` | **本模块的核心**，状态机和权限都在这 |
| 5 | `product/mapper/ProductMapper.java` + `resources/mapper/product/ProductMapper.xml` | 所有状态流转都是**带 WHERE 条件的 UPDATE** |
| 6 | `product/vo/MyProductVO.java`、`ProductDetailVO.java`、`PendingProductVO.java` | 同一张表，三个使用场景，三个不同的输出对象 |

**③ 调用链（以「卖家申请上架」为例）**

```text
前端 MyProductsView 点“申请上架”
  → POST /api/products/{id}/submit-review
  → LoginInterceptor：非公开路径，校验 JWT + Redis，写入 UserContext
  → ProductController.submitReview(id)
  → ProductService.submitReview(id)        # @Transactional
      ├─ UserContext.requireCurrentUser()  # 卖家身份来自 token，不来自请求参数
      ├─ requireOwnedProduct(id, sellerId) # 先查一次，用于给出友好的错误信息
      └─ productMapper.submitReviewBySeller(id, sellerId)
             UPDATE product SET status=1, version=version+1
             WHERE id=? AND seller_id=? AND status IN (0,2,4) AND stock>0 AND deleted=0
      └─ 影响行数 0 → 抛 BizException(CONFLICT)
      └─ 提交后删除该商品详情缓存
  → Result.ok()
```

**④ 关键方法签名**

```java
// ProductService
@Transactional public ProductIdVO create(CreateProductRequest request);
@Transactional public void update(Long productId, UpdateProductRequest request);
@Transactional public void submitReview(Long productId);
@Transactional public void withdrawReview(Long productId);
@Transactional public void offShelf(Long productId);
@Transactional public void adjustStock(Long productId, StockAdjustRequest request);
@Transactional public void reviewByAdmin(Long productId, boolean pass, String reason);

// 私有工具方法，是“归属校验”的统一入口
private Product requireOwnedProduct(Long productId, Long sellerId);
private void requireStatus(Product product, Set<Integer> allowedStatuses, String message);
```

**⑤ 为什么这么设计**

- **为什么每个动作一个 URL，而不是一个通用的「改状态」接口？**
  因为每个动作的**权限和前置状态都不一样**：撤回只有卖家能做、审核只有管理员能做。做成一个通用接口，就得在方法体里写一大坨 `if (to == 3) ... else if (to == 4)`，权限校验也会散落各处。一个动作一个 URL，还能让 `PublicRequestMatcher` 和 `AdminInterceptor` 按路径做粗粒度拦截。
- **为什么已经 `requireOwnedProduct()` 查过一次了，UPDATE 还要带 `seller_id=? AND status IN (...)`？**
  这是本项目**最重要的一个模式**，请务必理解：先 SELECT 再 UPDATE 之间存在时间差，这期间别人可能已经改过这条记录（比如管理员刚好审核通过了）。SELECT 出来的结果只用于**给用户友好的错误提示**，真正的**并发安全由 UPDATE 的 WHERE 条件保证**。判断标准是「影响行数是不是 0」。
- **为什么编辑要带 `version`？** 见 7.3。

**⑥ 常见误区**

- ❌「我在 Service 里 `if (product.getStatus() != 0) throw ...` 判断过了，SQL 就不用带条件了」——错。见上。
- ❌「影响行数 0 说明数据库出错了」——不是。影响行数 0 是**正常的业务结果**，含义是「你要改的那一行，现在已经不满足你以为的条件了」，对应 HTTP 语义就是 409 冲突。
- ❌「`deleted` 字段是给数据库自己看的」——不是。商品用软删除，所有查询和更新都必须显式带 `deleted = 0`，漏一个地方就会把已删除商品捞出来。

**⑦ 自测问题**

1. 卖家 A 能不能改卖家 B 的商品？代码里有几道防线拦住他？
2. 「申请上架」的 SQL 为什么要带 `stock > 0`？
3. 两个浏览器标签页同时编辑同一件商品，后点保存的那个会发生什么？
4. `MyProductVO` 里为什么有 `version`，而 `ProductDetailVO` 里没有？

### 6.2 商品公开查询与详情缓存

**① 解决什么问题**

首页列表和商品详情是全站访问量最高的接口，而且不需要登录。详情页还要拼装卖家信用、最近评价，查询较重，所以加了 Redis 缓存。

**② 阅读顺序**

1. `product/service/ProductService.java` 的 `listPublic()` 和 `getPublicDetail()`
2. `product/service/ProductDetailCacheService.java`
3. `resources/mapper/product/ProductMapper.xml` 的 `selectPublicPage` / `selectPublicDetail`
4. `product/model/SellerSummary.java`、`ReviewSummary.java`（只用于查询的「读模型」，不是数据库表的完整映射）

**③ 详情的读路径**

```text
GET /api/products/{id}
  → 先读 Redis：product:detail:{id}
      命中详情 JSON → 直接返回，一次数据库都不查
      命中空值标记 → 直接抛 404，不查库
      未命中 → 尝试获取该商品的 Redisson 锁：lock:product:detail:{id}
          获取锁成功 → 再读一次缓存（双重检查）→ 回源查数据库 → 写入详情 JSON 或空值标记 → 释放锁
          200ms 内未获取锁 → 直接回源查询，保证请求不因抢锁而长时间阻塞
  → 若请求带了合法 token，顺带写一条浏览历史
```

**④ 关键设计点**

| 设计 | 代码位置 | 为什么 |
|---|---|---|
| 正常详情 TTL ≈ 5 分钟 **+ 0~30 秒随机值** | `ProductDetailCacheService` | 防**缓存雪崩**：如果一批商品同时被缓存、同时到期，下一秒会有大量请求一起打到数据库。加随机值把过期时间打散 |
| 不存在的商品在同一个 `product:detail:{id}` 键中保存空值标记（TTL 10 秒） | 同上 | 防**缓存穿透**：有人拿不存在的 id 疯狂刷接口，如果不缓存「不存在」这个事实，每次都会穿透到数据库；共用一个键也避免一次请求读取两个 Redis key |
| 缓存未命中时按商品 ID 获取 Redisson 分布式锁，锁内再次查缓存 | 同上、`config/RedissonConfig.java` | 防**缓存击穿**：热点商品缓存失效的一瞬间，多个应用实例只让一个请求重建缓存；锁粒度是单个商品，不会把所有详情请求串行化 |
| 写操作**在事务提交之后**才删缓存 | `ProductService.invalidateDetailCacheAfterCommit()` | 见 7.4，这是缓存一致性的关键 |

**⑤ 常见误区**

- ❌「缓存就是查完存起来」——真正难的是「什么时候删」。本项目里凡是改了商品的地方（编辑、上下架、审核、调库存、下单扣库存、取消回补库存、超时取消）**都要删缓存**，漏一处就会出现「明明卖光了首页还显示在售」。你可以全局搜索 `invalidate` 看看一共有多少个调用点。
- ❌「分布式锁就是越久越安全」——锁的租约设为 10 秒，只覆盖一次详情查询和缓存写入；时间过长会在异常时无谓阻塞，时间过短则可能在慢查询未完成时提前释放。当前重建逻辑很短，10 秒留有余量即可。

**⑥ 自测问题**

1. 为什么 TTL 要加随机数？不加会怎样？
2. 空值缓存的 TTL 为什么只有 10 秒，而不是和正常缓存一样 5 分钟？
3. 为什么拿到锁后还要再读一次缓存？
4. 如果把「删缓存」放在 `@Transactional` 方法体的最后一行（而不是 afterCommit），会出现什么问题？

### 6.3 浏览历史：什么叫「可选登录」

**① 解决什么问题**

商品详情对游客开放，但如果访客是登录用户，要顺便记一条浏览历史。

**② 阅读顺序**

1. `auth/interceptor/PublicRequestMatcher.java`
2. `auth/interceptor/LoginInterceptor.java`（注意它对公开路径也会尝试解析 token）
3. `history/service/BrowseHistoryService.java`
4. `resources/mapper/history/BrowseHistoryMapper.xml`

**③ 关键点**

```java
// BrowseHistoryService
@Transactional public void recordIfAuthenticated(Long productId);   // 名字已经说明了一切
@Transactional(readOnly = true) public PageResult<BrowseHistoryVO> listMine(int page, int pageSize);
```

「可选登录」的含义是：**没有 token 照样放行，有合法 token 就顺带识别身份**。所以 `recordIfAuthenticated` 里先看 `UserContext` 有没有值，没有就直接 return，绝不抛 401。

去重靠数据库：`browse_history` 上有 `(user_id, product_id)` 唯一键，写入用

```sql
INSERT INTO browse_history (user_id, product_id, last_browsed_at)
VALUES (?, ?, CURRENT_TIMESTAMP)
ON DUPLICATE KEY UPDATE last_browsed_at = CURRENT_TIMESTAMP
```

一条 SQL 同时完成「没有就插入、有就更新时间」，不需要先查再判断，天然并发安全。这个写法叫 **upsert**，值得记住。

**④ 自测问题**

1. 游客访问商品详情时，`UserContext` 里有值吗？为什么不会抛异常？
2. 同一个人连续刷新同一商品 10 次，`browse_history` 表会多几行？

### 6.4 订单模块：全项目最难的一块

**① 解决什么问题**

下单要同时做四件事，而且必须**要么都成功要么都失败**：写订单、写商品快照、扣库存、（后续操作时）写状态日志。还要防重复提交、防超卖、防越权。

**② 阅读顺序**

| 顺序 | 文件 | 关注点 |
|---:|---|---|
| 1 | `order/model/OrderStatus.java` | 六个状态码 |

**⑤ 为什么这么设计**

- **为什么下单不接收前端传来的价格？**
  因为浏览器里的任何东西都可以被改。用 F12 把 `totalAmount` 改成 0.01 再提交，如果后端直接用，就是资损。**凡是钱、身份、权限，一律以数据库为准。**
- **为什么要存商品快照？**
  订单是历史凭证。卖家事后把商品标题改成别的、把图片换掉、甚至下架删除，历史订单里显示的必须还是**下单那一刻**的样子。所以 `product_snapshot` 把标题、描述、价格、成色、校区、图片整体复制一份。这也是为什么订单详情页取的是 `snapshot.title` 而不是 `product.title`。
- **为什么先插订单再扣库存，而不是反过来？**
  两种顺序都在同一个事务里，都能保证一致性。当前顺序的好处是：撞 requestId 唯一键时（重复提交），程序**还没有碰过库存**，直接返回首单即可，不需要任何补偿动作。
- **为什么 `canConfirm` 这类按钮标记由后端算？**
  前端也能算，但前端算只是为了少画一个按钮。后端在 `confirm()` 里**又完整校验了一遍身份和状态**——因为用户完全可以绕过页面直接调接口。记住这句话：**前端隐藏按钮是体验，后端校验才是安全。**
- **为什么 `cancel()` 是买卖双方都能调，而 `confirm()` 只有卖家、`complete()` 只有买家？**
  这是业务规则：卖家确认「我认这单」，买家确认「我拿到货了」，谁都可以在交易完成前反悔取消。注意 `complete` 只能由买家点，卖家不能自己把订单标记为完成——否则卖家可以单方面刷成交数。

**⑥ 常见误区**

- ❌「`@Transactional` 加上就万事大吉」——事务保证的是**原子性**，不保证**并发正确性**。两个人同时买最后一件，两个事务都能提交成功；真正拦住超卖的是 `WHERE stock >= ?` 这个条件，不是事务。
- ❌「requestId 是给日志用的追踪 ID」——不是。它是**幂等键**，配合数据库唯一索引 `(buyer_id, request_id)` 使用。前端进入下单页时生成一次，之后无论用户点多少次提交、网络重试多少次，都是同一个值。
- ❌「订单详情里直接关联查商品表就行，存快照太浪费」——见上，历史凭证不能跟着当前数据变。

### 6.5 订单超时取消：延迟消息、定时兜底与幂等消费

**① 解决什么问题**

买家下单后卖家一直不理，订单不能永远挂着占库存。规则是 24 小时内卖家不确认，系统自动取消并回补库存。

**② 阅读顺序**

1. `order/service/OrderService.java` 的 `publishTimeoutMessageAfterCommit`
2. `order/mq/OrderTimeoutMessagePublisher.java`
3. `order/mq/OrderTimeoutMessageConsumer.java`
4. `order/service/OrderTimeoutScheduler.java`
5. `order/service/OrderTimeoutService.java`
6. `resources/mapper/order/OrderMapper.xml` 的 `selectExpiredPendingOrderIds`、`timeoutCancelBySystem`

**③ 代码结构**

```java
// 订单事务提交后再发消息：回滚的订单不会产生超时消息。
private void publishTimeoutMessageAfterCommit(TradeOrder order) {
    TransactionSynchronizationManager.registerSynchronization(
            new TransactionSynchronization() {
                @Override
                public void afterCommit() {
                    // 异步发送不阻塞下单响应；发送失败由定时扫描补偿。
                    timeoutMessagePublisher.publish(
                            order.getId(),
                            order.getConfirmDeadline()
                    );
                }
            }
    );
}

// MQ 消费者：消息体只有订单 ID，不为一个 Long 创建 DTO 和 JSON 结构。
public ConsumeResult consume(MessageView messageView) {
    String body = StandardCharsets.UTF_8.decode(messageView.getBody()).toString();
    Long orderId = Long.valueOf(body);
    timeoutService.cancelIfExpired(orderId);
    return ConsumeResult.SUCCESS;
}

// Scheduler：只负责“每隔一段时间捞一批 ID”，本身不带事务。
@Scheduled(fixedDelayString = "${campus.order.timeout-scan-delay-ms:60000}")
public void cancelExpiredOrders() {
    orderMapper.selectExpiredPendingOrderIds(BATCH_SIZE) // 一次最多 100 条
               .forEach(timeoutService::cancelIfExpired);
}

// Service：MQ 和 Scheduler 共用同一个幂等入口，每一笔订单一个独立事务。
@Transactional
public void cancelIfExpired(Long orderId) {
    TradeOrder order = orderMapper.selectById(orderId).orElse(null);
    if (order == null) {
        return;
    }
    if (orderMapper.timeoutCancelBySystem(orderId) == 0) {
        // 已确认、已取消、尚未到期，或者已被另一个消费者/定时任务处理。
        return;
    }
    productMapper.restoreStockForCancelledOrder(order.getProductId(), order.getQuantity());
    // 写一条 operatorType=2（系统）的状态日志。
    invalidateAfterCommit(order.getProductId());
}
```

**④ 为什么这么设计（这一节的价值全在这里）**

- **为什么不用定时任务单独完成？**
  单独扫描最坏要等一个扫描周期，数据量大时还会不断查询。延迟消息能在每笔订单的截止时间附近主动触发；定时任务仍然保留，负责 MQ 发送失败、积压或停机后的最终补偿。
- **为什么消息要在订单事务提交后发送？**
  如果事务还没提交就发出消息，事务随后回滚，MQ 中会留下一个数据库里不存在的“幽灵订单”。`afterCommit` 保证只有已经落库的订单才尝试发送。发送本身失败不会回滚订单，因为数据库中的 `confirm_deadline` 仍能被定时任务扫描到。
- **“幂等消费”是不是把消息 ID 存进 Redis？**
  本项目不需要。RocketMQ 的 messageId 只用于日志追踪，真正的业务幂等由
  `UPDATE ... WHERE id=? AND status=0 AND confirm_deadline<=CURRENT_TIMESTAMP`
  保证。即使同一消息重复十次、MQ 与定时任务同时执行，也只有一个请求能把状态从 0 改成 4，只有它能回补一次库存。Redis 去重还可能因为过期或缓存丢失而失效，反而增加复杂度。
- **为什么扫描和处理要分成两个类？**
  如果整批一个事务，其中一笔出错就会导致整批回滚；而且事务会持续很久。拆开后，**一笔订单一个短事务**，互不影响。
- **为什么已经用 `WHERE status=0 AND confirm_deadline <= now()` 捞出来了，UPDATE 还要再判断一次？**
  捞出来到处理之间，卖家可能刚好点了「确认」。所以 `timeoutCancelBySystem` 的 SQL 依然是
  `UPDATE ... SET status=4 WHERE id=? AND status=0 AND confirm_deadline <= CURRENT_TIMESTAMP`，
  影响行数 0 就直接 return。**又是同一个模式：SELECT 只是候选，UPDATE 的 WHERE 才是判据。**
- **将来部署两个后端实例会不会重复取消？**
  不会。两个实例都会捞到同一批订单，但同一笔的条件 UPDATE 只有一个能返回 1，另一个返回 0 直接退出。**所以这里不需要分布式锁**——把「幂等」做进 SQL，比加锁更简单也更快。这是个很好的面试答案。
- **消费失败如何处理？**
  MySQL 等临时异常返回 `FAILURE`，交给 RocketMQ 重试，超过最大重试次数后进入死信队列；消息体无法解析成有效订单 ID 属于永久格式错误，记录 messageId 后返回成功，避免无意义地反复消费。无论哪种情况，定时扫描都保留最终补偿能力。
- `CT_ORDER_TIMEOUT_MESSAGE_ENABLED` 控制 MQ 链路；`CT_ORDER_TIMEOUT_SCAN_ENABLED` 控制定时兜底。正常运行时应同时开启，不要为了验证 MQ 而关闭兜底。

### 6.6 评价模块与「信用摘要」这个读模型

**① 解决什么问题**

买家对已完成订单评一次分，卖家的平均分/好评率要跟着更新，而且商品详情页要能快速展示这些数字。

**② 阅读顺序**

1. `review/service/ReviewService.java`（只有一个方法，但每一行都是规则）
2. `resources/mapper/review/ReviewMapper.xml` 的 `recalculateSellerCredit`
3. `product/service/SellerDetailCacheInvalidator.java`

**③ 三道校验 + 两个副作用**

```java
@Transactional public void create(CreateReviewRequest request) {
    // 1. 只有买家能评         → FORBIDDEN
    // 2. 只有已完成(2)订单能评 → CONFLICT
    // 3. 一单一评              → CONFLICT（先 exists 查一次，再靠 order_id 唯一键兜底）
    reviewMapper.insert(review);
    reviewMapper.recalculateSellerCredit(order.getSellerId());   // 副作用一：重算摘要
    cacheInvalidator.invalidateAfterCommit(order.getSellerId()); // 副作用二：删该卖家商品缓存
}
```

**④ 什么是「读模型」，为什么要有 `user_credit_summary` 这张表**

卖家的平均分完全可以每次 `SELECT AVG(rating) FROM trade_review WHERE seller_id=?` 算出来。但商品详情页每次打开都算一遍，量大了就慢。所以单独存一张**汇总表**，把算好的结果放进去——这种「为了读得快而额外维护的、可以随时从原始数据重建的表」就叫**读模型**（也叫物化视图 / 冗余汇总）。

关键在于 `recalculateSellerCredit` 的写法：它不是 `avg_rating = (avg_rating * n + 新分)/(n+1)` 这种**增量累加**，而是

```sql
UPDATE user_credit_summary cs
JOIN (SELECT seller_id, COUNT(*) review_count, AVG(rating) avg_rating, ...
      FROM trade_review WHERE seller_id=? AND visible=1 GROUP BY seller_id) r
  ON r.seller_id = cs.user_id
SET cs.review_count = r.review_count, cs.avg_rating = r.avg_rating, ...
```

**整体重算**。这么做的好处：即使某次更新失败、或者管理员手动隐藏了一条评价（`visible=0`），下一次重算就自动纠正了，不会像增量累加那样越错越离谱。**读模型必须能从原始数据重建**，这是设计这类表的第一原则。

**⑤ 常见误区**

- ❌「评价插入成功就够了，摘要慢慢算」——摘要和评价必须在同一个事务里，否则会出现「有评价但分数没变」。
- ⚠️ 注意 `credit_score`（信用分）**当前并没有被重算**，详见第八部分的已知风险 R2。

### 6.7 纠纷模块：状态回退与管理员裁决

**① 解决什么问题**

交易出问题时，双方可以发起纠纷，订单进入「纠纷中(5)」冻结状态，由管理员裁决。裁决结果可能是**回到原来的状态**、维持完成、取消交易，或者要求补材料。

**② 阅读顺序**

1. `dispute/entity/Dispute.java`（注意 `evidence` 是 JSON 列）
2. `dispute/service/DisputeService.java` 的 `create()`
3. `dispute/service/DisputeService.java` 的 `handle()`
4. `resources/mapper/dispute/DisputeMapper.xml` 的 `selectAdminCursorPage` / `updateHandled`
5. `dispute/model/AdminDisputeRow.java`（管理端列表专用读模型）
6. `resources/mapper/order/OrderMapper.xml` 的 `enterDispute` / `restoreFromDispute` / `completeFromDispute` / `cancelFromDispute`

> ⚠️ 提前说明：`DisputeService.java` 和 `ReviewService.java` 目前被压缩成了每个方法一行，读起来很痛苦。这不是什么高级写法，就是排版问题。建议你在 IDE 里用 `Ctrl+Alt+L`（IDEA 格式化）看，或者让我帮你展开成正常排版。

**③ 状态回退是怎么做到的**

订单表上有一个专门的列：

```sql
`status_before_dispute` TINYINT DEFAULT NULL COMMENT '进入纠纷前的状态，用于驳回纠纷时恢复'
```

发起纠纷时 `enterDispute` 把当前状态存进这一列，再把 `status` 改成 5。管理员选择「驳回纠纷」时，`restoreFromDispute(orderId, statusBeforeDispute)` 把它还原回去。

**这是一个很实用的小设计**：需要「临时冻结再还原」的状态机，与其在代码里猜「纠纷前应该是 1 还是 2」，不如老老实实存一列。

**④ 四种裁决动作对照表**

| action | 纠纷状态 | 订单状态 | 附带动作 |
|---|---|---|---|
| `NEED_MORE` | → 1 待补材料 | 不变（仍是 5） | 直接 return，不碰订单 |
| `REJECT` | → 2 驳回 | 5 → `status_before_dispute` | 写状态日志 |
| `KEEP_COMPLETED` | → 3 维持完成 | 5 → 2 已完成 | 若原状态是 1，卖家成交数 +1 |
| `CANCEL_TRADE` | → 4 取消交易 | 5 → 3 已取消 | 若 `restock=true`，回补库存 |

注意 `KEEP_COMPLETED` 那一行的 `if (statusBeforeDispute == 1)`：如果订单在发起纠纷前**已经是已完成**，说明成交数在 `complete()` 时已经加过了，这里就不能再加。这种「避免重复计数」的判断在做数据统计时非常典型。

**⑤ 并发怎么防**

两个管理员同时点「处理」：`updateHandled` 的 `WHERE id=? AND status IN (0,1)` 只会让一个成功，另一个影响行数为 0，抛「该纠纷已处理」。**又是同一个模式**，你现在应该已经很熟了。

**⑥ 管理端列表：从 N+1 查询改为 JOIN + 游标分页**

旧实现先查一页纠纷，再对每一行分别查询订单、商品、买家、卖家；一页有 `N` 条数据时会产生约 `1 + 4N + 1（COUNT）` 次 SQL。数据增长后，网络往返和数据库解析时间都会线性增加。

现在由 `selectAdminCursorPage` 用一条 `LEFT JOIN` 一次取齐页面所需字段，映射到 `AdminDisputeRow`；`DisputeService` 只负责解析证据 JSON、转换成 `AdminDisputeVO`，不再逐条访问数据库。查询时额外取一条记录（`pageSize + 1`）：多出的记录只用来判断 `hasNext`，不会返回给前端，也不再执行昂贵的 `COUNT(*)`。

```sql
-- 第一页：按稳定顺序读取最新的纠纷
ORDER BY d.created_at DESC, d.id DESC
LIMIT #{limit} -- limit = pageSize + 1，用额外一条记录判断是否还有下一页

-- 下一页：只读取当前游标之后的旧记录；id 用来处理相同 created_at 的并列情况
AND (
    d.created_at < #{cursorCreatedAt}
    OR (d.created_at = #{cursorCreatedAt} AND d.id < #{cursorId})
)
```

这里不能只用 `created_at` 作游标：多条纠纷可能有相同创建时间，缺少 `id` 会造成翻页重复或漏数据。响应中的 `nextCursorCreatedAt`、`nextCursorId` 必须取**本页最后一条实际返回记录**，而不是用于探测的第 `pageSize + 1` 条。

索引脚本在 `docs/纠纷列表索引升级.sql`：

| 索引 | 服务的查询 | 设计理由 |
|---|---|---|
| `uk_dispute_order_id(order_id)` | 一单一纠纷校验、按订单读取纠纷 | 将业务规则交给数据库兜底，并加速等值查询 |
| `idx_dispute_status_created_id(status, created_at DESC, id DESC)` | 带状态筛选的管理端游标列表 | 先等值筛选 `status`，再按游标排序字段连续扫描，尽量避免额外排序 |
| `idx_dispute_created_id(created_at DESC, id DESC)` | 不传状态筛选的管理端游标列表 | 与全量列表的排序和游标条件保持一致 |

执行前先用脚本中的 `SHOW INDEX FROM dispute` 检查索引是否已存在，再在目标 MySQL 环境执行；上线前可用 `EXPLAIN` 确认执行计划使用了预期索引。索引不是越多越好：它会占空间，也会增加纠纷新增、更新时维护索引的成本，因此只保留这三条与真实查询直接相关的索引。

### 6.8 文件上传：不要相信浏览器说的任何一句话

**① 阅读顺序**

1. `file/controller/FileController.java`（注意 `consumes = MULTIPART_FORM_DATA_VALUE`）
2. `file/service/FileStorageService.java`
3. `config/WebMvcConfig.java` 里 `/uploads/**` 的静态资源映射
4. `auth/interceptor/PublicRequestMatcher.java` 第 41 行

**② 这个类做了五层防护，每一层防的是什么**

| 防护 | 代码 | 防什么 |
|---|---|---|
| 大小限制 5MB | `MAX_FILE_SIZE` + `spring.servlet.multipart.max-file-size` | 有人上传 10GB 文件塞满磁盘 |
| **读文件头魔数**判断真实类型 | `ImageType` 判定 JPEG/PNG/WebP 的字节签名 | 把 `virus.exe` 改名成 `cat.jpg` 上传 |

| **忽略原文件名**，用 UUID 重命名 | `UUID.randomUUID() + imageType.extension()` | 原文件名里带 `../../` 或中文乱码 |
| 落盘前再检查一次路径 | `if (!target.startsWith(uploadDirectory)) throw ...` | 路径穿越（把文件写到 uploads 目录外面去） |

**③ 一个容易被忽略但很关键的点**

`LoginInterceptor` 挂在 `/**` 上，**静态资源请求也会经过它**。而浏览器渲染 `<img src="/api/uploads/xxx.jpg">` 时是**不会带 `Authorization` 头**的。如果不放行，全站图片都会变成 401。所以 `PublicRequestMatcher` 里有这一行：

```java
if ("/error".equals(path) || path.startsWith("/actuator/") || path.startsWith("/uploads/")) {
    return true;
}
```

**这类「拦截器把静态资源也拦了」的坑非常常见**，值得专门记一下。

## 第七部分　四个必须吃透的工程专题

这四个专题是本项目**真正的技术含量所在**，也是简历上写「校园二手交易平台」时面试官一定会追问的地方。前面各章都在反复用它们，这里集中讲一次。

### 7.1 幂等：同一个操作做多少次，结果都一样

**问题**：用户点了「提交订单」，转圈时不耐烦又点了一次；或者网络超时前端自动重试。怎么保证只生成一笔订单？

**本项目的解法（两层）**：

```text
第一层（应用层，快）：进下单页时前端生成一个 requestId，整页只生成一次
                     后端先 SELECT 有没有 (buyerId, requestId) 的订单，有就直接返回它
第二层（数据库层，绝对可靠）：trade_order 表上有唯一索引 (buyer_id, request_id)
                     两个请求同时越过第一层时，第二个 INSERT 必然撞唯一键
                     catch DuplicateKeyException → 读出第一笔返回
```

**为什么必须有第二层？** 因为第一层的「先查再插」中间有时间差，两个并发请求可以同时查到「没有」。**任何「先检查再写入」的逻辑，在并发下都不可靠，最终必须由数据库约束兜底。** 注册时的「学号是否已存在」也是同一个套路。

**记住这个判断法**：一个写接口是否幂等，问自己「原样重放两次，数据库会不会多一行 / 钱会不会多扣一次」。

### 7.2 防超卖：把判断写进 SQL 的 WHERE 里

**错误写法**（几乎每个新手都会先这么写）：

```java
Product p = mapper.selectById(id);
if (p.getStock() >= qty) {          // ← 两个线程可以同时走到这里，都判断为 true
    mapper.updateStock(id, p.getStock() - qty);
}
```

**正确写法**（本项目的写法）：

```sql
UPDATE product SET stock = stock - #{quantity}, ...
WHERE id = #{id} AND status = 3 AND stock >= #{quantity} AND deleted = 0
```

然后在 Java 里**判断影响行数**：

```java
if (productMapper.decreaseStockForOrder(product.getId(), request.quantity()) == 0) {
    throw conflict("库存不足或商品已变化，请刷新后重试");
}
```

**为什么这样就安全？** 因为一条 UPDATE 语句在 InnoDB 里会对命中的行加**排他锁**，两个并发 UPDATE 会串行执行。第二个执行时 `stock >= quantity` 已经不成立，命中 0 行。整个「判断 + 修改」被压缩进了一条原子语句，中间不存在时间差。

这个模式在本项目里出现了**十几次**（订单确认、取消、完成、超时取消、商品各种状态流转、纠纷裁决），你可以全局搜索 `== 0` 看看。把它总结成一句话：

> **不要「先查询再修改」，要「带条件修改，然后看改动了几行」。**

⚠️ **踩坑提醒（真实存在于当前代码）**：MySQL 的 `SET a = ..., b = ...` 是**从左到右依次求值**的，后面的表达式里再出现 `a`，拿到的已经是**新值**。`decreaseStockForOrder` 里的
`status = CASE WHEN stock - #{quantity} = 0 THEN 5 ELSE status END` 正好踩了这个坑（详见第八部分 R1）。**写多列 UPDATE 时，一定要意识到列的赋值顺序会影响结果。**

### 7.3 乐观锁：防的是「覆盖」，不是「超卖」

商品编辑用的是另一种并发控制：

```sql
UPDATE product SET title=?, price=?, ..., version = version + 1
WHERE id=? AND seller_id=? AND version=#{version} AND status IN (0,2,4) AND deleted=0
```

**场景**：你开了两个标签页编辑同一件商品。A 页面改了价格保存成功（version 1→2），B 页面还拿着 version=1，保存时 `WHERE version=1` 命中 0 行 → 返回 409「商品已被修改，请刷新后重试」。如果没有这个机制，B 会把 A 的修改**静默覆盖**掉，而且没有任何人发现。

**乐观锁 vs 悲观锁**：

| | 做法 | 适合 |
|---|---|---|
| 悲观锁 | `SELECT ... FOR UPDATE` 先把行锁住 | 冲突频繁、必须排队 |
| 乐观锁 | 不加锁，靠 version 在提交时发现冲突 | **冲突很少**，比如「两个人同时编辑同一件二手商品」几乎不会发生 |

叫「乐观」是因为它假设冲突很少发生，先干活，提交时才检查。

**注意区分**：`stock >= quantity` 那种叫**条件更新**，防的是资源被超额消耗；`version = ?` 叫乐观锁，防的是**丢失更新**。两者写法像，解决的问题不同。

### 7.4 缓存一致性与事务边界

**为什么删缓存必须放在事务提交之后？**

```java
// 错误：在事务里删缓存
@Transactional
public void offShelf(Long id) {
    mapper.offShelfBySeller(id, sellerId);
    cache.invalidate(id);          // ← 此时事务还没提交！
}                                  // ← 假如这里提交失败回滚了，缓存已经被删了；
                                   //    更糟的是删缓存后、提交前，别人读详情会把【旧数据】重新写进缓存
```

正确做法（项目里的写法）：

```java
private void invalidateDetailCacheAfterCommit(Long productId) {
    if (!TransactionSynchronizationManager.isSynchronizationActive()) {
        cacheService.invalidate(productId);          // 没有事务时直接删
        return;
    }
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        @Override public void afterCommit() {        // 注册回调：等事务真正提交成功后再删
            cacheService.invalidate(productId);
        }
    });
}
```

**顺带记住 `@Transactional` 的三条铁律**（新手 90% 的事务 bug 都出在这）：

1. **自调用失效**：同一个类里 `this.methodB()` 调用带 `@Transactional` 的方法，注解**不生效**。因为 Spring 是靠代理实现事务的，自调用不经过代理。
2. **默认只回滚 `RuntimeException`**：抛受检异常（checked exception）默认**不回滚**。本项目的 `BizException` 继承自 `RuntimeException`，所以没问题。
3. **事务里不要做慢操作**：HTTP 调用、发邮件、写文件、删缓存都不该在事务里做——事务开着就占着数据库连接和行锁。这也是为什么删缓存要挪到 `afterCommit`。

**补充：缓存一致性与缓存击穿解决的不是同一件事。** `afterCommit` 删除缓存解决的是「数据库提交后，缓存何时失效」；Redisson 商品级互斥锁解决的是「热点缓存刚失效时，大量并发请求如何避免同时回源数据库」。两者分别位于写路径和读路径，缺一不可，也不需要再引入复杂的异步重建或全局锁。

### 7.5 ThreadLocal 必须清理

`UserContext` 用 `ThreadLocal` 存当前用户，好处是 Service 层不用层层传 `userId`。但 **Tomcat 用的是线程池**，这个线程处理完你的请求后，会去处理别人的请求。如果不清理：

```text
请求1（用户A）→ 线程T 处理 → UserContext 里存了 A → 忘记清理
请求2（游客） → 恰好也分到线程T → UserContext 里还是 A → 游客被当成了 A ！
```

这是**严重的越权 bug**，而且在开发环境几乎测不出来（本地没并发）。所以 `LoginInterceptor.afterCompletion()` 里的 `UserContext.clear()` 是绝对不能省的一行。`afterCompletion` 的特点是**无论 Controller 是正常返回还是抛异常都会执行**，相当于 `finally`。

## 结语

理解当前后端只需要抓住四条主线：

1. **结构主线**：按业务模块组织，模块内部再分 Controller、Service、Mapper 等职责；
2. **数据主线**：DTO 接收输入，Entity 对应数据库，VO 控制输出；
3. **认证主线**：JWT 证明令牌未被篡改，Redis 决定令牌是否仍然有效；
4. **异常主线**：业务层抛异常，全局处理器统一转换成 `Result`。

先顺着分类查询理解标准分层，再顺着注册登录理解事务、JWT、Redis 和拦截器，接着阅读商品模块的状态机与乐观锁，最后阅读订单的幂等与库存条件更新。之后新增评价、纠纷等模块，本质上是在相同工程骨架中加入新的业务规则。

如果你只有一个晚上，只看两个地方：**第七部分**（幂等 / 防超卖 / 乐观锁 / 缓存一致性）和 **6.4 订单模块**。这两块是整个项目里唯一不能靠“多写几个 CRUD 就自然学会”的东西。
