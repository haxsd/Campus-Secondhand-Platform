# 校园二手交易项目整理版

> 本文档用于通过阅读来掌握两个简历项目的核心细节。两个项目属于同一业务体系：项目一是传统 Java 后端交易平台，项目二是在该平台基础上的 AI 智能体增强系统。

> 阅读口径：文中明确写“第一版采用”的内容可以作为当前设计口径；写“建议、可选、生产方案、未来扩展”的内容是面试时可以展开的改进方向，只有代码、配置、测试或压测已经验证后，才能表述成“已经实现”。性能数字、模型准确率和成本尤其不能凭空填写。

## 1. 项目一：校园二手交易平台

项目一按标准 Spring Boot 单体后端来设计，目标是支撑校园二手交易的完整业务闭环。

### 1.1 项目能力概览

| 能力 | 核心内容 |
| --- | --- |
| 用户体系 | 用户注册登录、JWT、Redis 登录态、鉴权拦截器 |
| 商品体系 | 商品发布、编辑、上架、下架、列表、详情 |
| 缓存与浏览 | 商品详情缓存、热点商品二级缓存、浏览记录 |
| 交易体系 | 库存下单、订单状态机、并发库存扣减、RocketMQ 延迟消息超时关单 |
| 异步与解耦 | RocketMQ：超时关单延迟消息、缓存删除失败补偿、信用摘要异步重算 |
| 信用与纠纷 | 交易评价、卖家信用、纠纷申请、证据链基础数据 |

#### 项目边界先说清楚

这个项目定位为**校内信息撮合 + 线下面交**，第一版不接支付、退款、物流和资金托管。因此：

1. 订单金额用于交易确认和证据留存，不代表平台已经完成收款。
2. 取消订单只处理订单状态和库存回补，不涉及支付渠道退款。
3. 纠纷模块负责沉淀材料、辅助管理员处理，不承担金融仲裁。
4. 如果未来接入在线支付，必须新增支付单、退款单、支付回调幂等、对账和资金状态机，不能直接复用现在的订单状态字段硬塞。

> 面试时主动说明“不做什么”很重要。一个学生项目把支付、物流、风控、推荐和 AI 全都说成完整生产实现，反而容易被追问穿。

### 1.4 业务流 1：注册、登录、退出与鉴权

这条业务流负责解决用户身份问题：用户第一次进入系统时可以注册账号，再次进入时可以登录拿到 token；访问需要登录的接口时，后端能识别当前用户是谁；用户退出登录或账号被禁用后，旧 token 不能继续访问系统。

#### 整体闭环

```text
注册成功
  -> user 表新增一条 NORMAL 用户
  -> 登录成功
  -> 生成 JWT
  -> Redis 保存 tokenId
  -> 前端后续请求携带 Authorization
  -> 拦截器解析 JWT
  -> Redis 校验 tokenId 是否仍然有效
  -> 查询或读取用户摘要
  -> 写入 UserContext
  -> Controller / Service 通过 UserContext 获取当前用户
  -> 请求结束清理 UserContext
```

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `user` | 用户表，保存账号、密码、状态等基础信息 |
| `user_credit_summary` | 用户信用摘要表，注册时初始化，商品详情页展示卖家信用 |

| Redis Key | TTL | 作用 |
| --- | --- | --- |
| `login:token:{tokenId}` | 7 天 | 判断 token 是否仍然有效，用于退出登录、封禁用户后的服务端失效控制 |
| `login:user_tokens:{userId}` | 与最长登录周期一致 | 保存该用户当前有效 tokenId，用于封禁、改密或后台踢下线时批量失效 |
| `user:summary:{userId}` | 30 分钟 | 缓存接口常用用户摘要，减少每次鉴权都查 user 表 |

这两个登录 Key 不是重复存储，而是两个查询方向：

```text
日常鉴权：tokenId -> login:token:{tokenId}，判断当前 Token 是否有效
批量失效：userId -> login:user_tokens:{userId} -> 全部 tokenId
```

只校验或退出当前 Token，一个 `login:token:{tokenId}` 就够；但多端登录时，封禁、改密或“退出全部设备”只有 userId，需要反向索引找到该用户的所有 tokenId，不能扫描 Redis 全部登录 Key。

#### 注册怎么走

注册时，后端先对学号和手机号做 trim、格式校验和规范化，再检查是否已注册。

校验通过后，后端创建用户基础记录，对密码做加密存储，同时初始化用户信用摘要，信用分默认 100。用户基础信息和信用摘要一起写入，保证后续商品详情页能直接展示卖家信用。

> 注册这里需要开事务，因为注册会同时写 `user` 和 `user_credit_summary` 两张表。如果用户插入成功但信用摘要初始化失败，后面商品详情页展示卖家信用时就会缺数据。事务可以保证用户基础信息和信用摘要一起成功或一起回滚。

> “先查询再插入”只能改善错误提示，不能防住两个并发注册请求同时通过查询。最终要靠 `user.student_no` 和 `user.phone` 的唯一索引兜底；插入时捕获唯一键冲突并转换成“学号或手机号已注册”的业务异常。

#### 登录怎么走

登录支持根据手机号或学号登录。

后端先查询 `user` 表，再校验用户是否存在、密码是否匹配、用户状态是否为 `NORMAL`。

校验通过后，后端生成不可预测的随机 `tokenId` 和 JWT：JWT 交给前端后续携带，Redis 保存这次登录是否仍然有效，并把 `tokenId` 加入 `login:user_tokens:{userId}`，同时缓存一份常用用户摘要。

> JWT 只放少量必要字段，不放手机号、密码等隐私信息。用户摘要缓存的是接口常用信息，用来减少鉴权时重复查库。Redis 登录态用于支持服务端主动失效，用户摘要缓存时间短一些，避免用户信息修改后长期不一致。

#### JWT 具体实现

| 项 | 选择 | 原因 |
| --- | --- | --- |
| 签名算法 | HS256 对称签名 | 单体服务自己签发自己验证，不需要把公钥分发给其他服务，HS256 实现简单、性能好；如果以后拆成多个服务再考虑 RS256 |
| 密钥管理 | 密钥放配置中心 / 环境变量，不写死在代码里 | 防止代码泄露连带密钥泄露 |
| Payload 字段 | `userId`、`role`、`tokenId`、`iat` 签发时间、`exp` 过期时间 | 只放鉴权必需的最小字段，不放手机号等隐私 |
| JWT 过期时间 | 7 天，和 Redis `login:token:{tokenId}` 的 TTL 保持一致 | 两者一致可以避免出现 JWT 没过期但登录态判断混乱的边界情况 |

> 面试常见追问：JWT 和 Redis TTL 的关系。回答口径：JWT 的 `exp` 是“这个 token 本身还能不能被解析通过”，Redis 的 key 是“这次登录是否仍被服务端承认”。两者都通过才算登录有效；退出登录、封禁只删 Redis，不需要也无法撤回已签发的 JWT。

> 密码存储用 BCrypt 加盐哈希（Spring Security 的 `BCryptPasswordEncoder`），不用 MD5。BCrypt 自带随机盐、可调代价因子，同一密码每次哈希结果不同，能防彩虹表。

登录接口还要做两层保护：按账号和 IP 做短时间失败次数限制；错误提示统一为“账号或密码错误”，避免攻击者通过提示枚举已注册账号。BCrypt 的 cost 不能照搬固定值，应在部署机器上压测到单次校验耗时可接受后确定。

#### 退出登录怎么走

退出登录时，拦截器先完成登录校验。

后端根据当前请求中的 tokenId，删除 Redis 的 `login:token:{tokenId}`，并从 `login:user_tokens:{userId}` 移除该 tokenId，保证当前设备的 token 立即失效。

第一版采用“多端并存”：每次登录生成独立 tokenId，退出只删除当前 tokenId；封禁、改密或强制下线时，读取用户的 tokenId 集合并批量删除全部登录态，同时清理用户摘要缓存。

#### 鉴权拦截器怎么恢复当前用户

鉴权拦截器从请求头取 token，解析 JWT，并判断 JWT 是否过期。

解析成功后，从 JWT 中取 tokenId，再查 Redis 的 `login:token:{tokenId}`。如果 Redis 不存在，说明 token 已经失效。

登录态有效时，拦截器优先从 Redis 读取当前用户摘要。

如果用户摘要不存在，就查 `user` 表重建摘要。

最后校验用户状态是否为 `NORMAL`，并把当前用户信息写入 UserContext。角色和账号状态不能只相信 JWT 中签发时的旧值：高权限接口要读取当前账号状态和角色，或者使用短 TTL 权限版本；否则用户被降权后，旧 JWT 中的管理员角色仍可能继续生效。

> 请求结束后必须清理 UserContext，避免 ThreadLocal 在线程复用时串数据。

#### 设计取舍

> 这里没有只用纯 JWT，因为纯 JWT 一旦签发，在过期前服务端很难主动让它失效。加 Redis 登录态后，退出登录、封禁账号、踢下线都可以通过删除 `login:token:{tokenId}` 实现。

> 用户摘要适合做短 TTL 缓存。每个需要登录的接口都会经过拦截器，如果每次都查 `user` 表，会浪费数据库资源；但用户摘要又可能被修改，所以不能长期缓存。

> UserContext 必须在请求结束后 clear。Web 容器线程会复用，如果 ThreadLocal 不清理，下一次请求可能读到上一次请求的用户信息。

鉴权顺序可以概括为：校验请求头格式 -> 校验签名和 `exp` -> 校验 Redis tokenId -> 加载当前账号状态与权限 -> 写入 UserContext。任何一步失败都返回统一 401/403，不把“签名错误、账号不存在、已封禁”等内部细节暴露给客户端。

整体上，这条登录链路用 JWT 携带用户标识、角色和登录态标识，用 Redis 保存这次登录是否仍然有效。

这样既保留了 JWT 无状态解析的便利，又能支持主动退出和封禁后失效。

拦截器解析 token 后，会从 Redis 校验登录态并加载用户摘要，然后写入 UserContext，后续业务层直接从 UserContext 获取当前用户。

### 1.5 业务流 2：商品发布、人工审核、编辑、上架与下架

这条业务流负责商品从创建、人工审核到公开展示，以及编辑和下架时的状态管理。项目一只实现人工审核；项目二会在人工审核之前增加 AI 合规初审。

> 文档统一使用“草稿、待人工审核、审核驳回、在售、已下架、已售罄”等中文业务状态。它们描述的是状态机含义，不限定代码中的枚举名或数据库存储值，实际实现可以使用数字或其他英文编码。

商品只维护一个当前库存数量，代码里可以落成 `stock` 字段。所有下单、取消和售罄判断都围绕这个数量变化。

#### 商品状态和审核流转

```text
卖家发布商品
  -> 商品先进入草稿状态
  -> 初始化库存数量
  -> 卖家检查内容、图片和库存
  -> 卖家申请上架，商品进入待人工审核
     ├─ 人工通过：进入在售，买家可见并可下单
     └─ 人工驳回：进入审核驳回，卖家修改后重新提交

在售
  -> 下单成功后扣减库存
  -> 库存变为 0 时进入已售罄
  -> 取消订单或超时取消时回补库存
```

#### 这条业务流解决什么问题

卖家能发布和编辑商品，但商品只有审核通过后才能进入买家列表；系统用 `stock` 表示当前还能被下单的数量，历史订单则通过商品快照保持稳定。卖家下架商品后，商品从公开列表消失，但已有订单不受影响。

只要商品内容、库存或状态发生变化，商品详情缓存就必须失效。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `product` | 商品主表，保存标题、价格、描述、状态、`stock`、卖家等核心信息 |
| `product_image` | 商品图片表，保存商品对应的图片地址和排序 |
| `category` | 商品分类表，用于校验发布或编辑时选择的分类是否存在且启用 |
| `product_review_log` | 保存人工审核人、审核结果、驳回原因和审核时间 |

| Redis Key | 作用 |
| --- | --- |
| `product:detail:{productId}` | 商品详情缓存；商品基础信息、图片、状态或库存发生变化时删除 |

#### 权限边界

卖家管理页只查询当前用户发布的商品，前端也只为本人商品显示编辑、上架和下架按钮，因此正常操作中不会看到别人的管理入口。但隐藏按钮不是安全校验，请求可以被伪造；后端仍统一从 `UserContext` 取 userId，并在编辑和状态更新 SQL 中附带 `seller_id = 当前用户`。这条规则在此统一说明，后续流程不再反复描述。

#### 发布商品怎么走

发布商品时，拦截器先校验 token。

后端接收商品信息，校验分类是否存在且启用、库存必须大于 0，并把商品照片存储到阿里云；`seller_id` 只能取自 `UserContext`，不能接受前端指定。

随后写入商品主记录，状态固定为草稿，库存初始化为：

```text
stock = 前端提交的库存数量
```

然后插入 `product` 表，再插入 `product_image` 表。

> 发布后不直接进入在售状态，因为卖家还没检查图片、价格、描述和库存，买家就可能看到错误信息。发布只负责创建草稿，真正进入买家可见列表必须走上架接口。

图片上传不能只校验文件后缀。后端还要限制文件数量和大小，校验 MIME 与文件头，使用随机对象名写入 OSS，数据库只保存受控对象地址；上传成功但事务回滚产生的孤儿文件，由定时清理任务回收。公开访问使用受控域名，日志中不记录 OSS 凭据或签名参数。

#### 上架商品怎么走

“上架”实际是申请人工审核：后端校验商品存在、未删除，状态为草稿、已下架或审核驳回，并且库存大于 0，再通过条件更新进入待人工审核。

管理员在审核页查看商品信息和图片。审核通过时，后端通过条件更新把商品改为在售；审核驳回时改为审核驳回，并保存原因和修改建议。两种结果都写入审核日志并删除商品详情缓存。

#### 编辑商品怎么走

编辑商品时，后端查询商品并校验其未删除，同时校验新类目存在且启用。

标题、描述、价格、类目、成色、交易地点和图片都会影响审核结果，因此编辑边界是：

1. 草稿、已下架、审核驳回状态可以编辑，之后重新申请审核。
2. 在售状态不能直接修改上述字段，必须先下架，防止“审核的是旧内容，展示的是新内容”。
3. 待人工审核期间锁定内容；卖家要修改时先撤回申请并回到草稿状态。

库存调整使用独立规则，不能在任何状态下随意覆盖：

1. 草稿、已下架且没有有效订单时，可以直接设置库存。
2. 在售时只提供“追加库存”或“减少可售库存”的独立接口，使用 `stock = stock + delta` 条件更新；减少后至少保留 1 件，要降为 0 必须走下架。
3. 不允许用把 `stock` 改为 0 来表达“暂停售卖”，暂停售卖必须走下架；已售罄只表示系统因可售库存耗尽而产生的状态。
4. 已有订单锁定的数量不能被商品编辑接口改掉，取消订单仍按订单数量回补。

> 已经创建的订单不依赖商品表当前内容，因为下单时会写入 `product_snapshot`。卖家后续编辑商品，不会影响历史订单展示和纠纷判断。

编辑和上下架都应带旧状态或 `version` 条件，例如 `where id=? and seller_id=? and version=? and deleted=0`。影响行数为 0 时重新读取并提示“商品已被其他请求修改”，防止两个页面同时编辑造成后写覆盖前写。

#### 下架商品怎么走

下架时，后端校验商品当前状态必须是在售。

校验通过后，将数据库中的商品状态更新为已下架，并删除商品详情缓存。

> 下架不是删除商品，也不会改订单状态。下架只表示商品不再对买家展示；已有订单仍然按订单状态机继续确认、取消、完成或纠纷处理。

#### 缓存什么时候删

| 动作 | 缓存处理 |
| --- | --- |
| 发布商品 | 商品处于草稿状态，不进入公开详情缓存，通常不需要删除缓存 |
| 编辑商品 | 商品内容或库存变化，删除正常详情和空值缓存 |
| 上架商品 | 商品状态变化，删除正常详情和空值缓存 |
| 下架商品 | 商品状态变化，删除正常详情和空值缓存 |
| 下单成功 | `stock` 变化，删除正常详情和空值缓存 |
| 取消订单 | `stock` 变化，删除正常详情和空值缓存 |
| 完成交易 | 订单状态变化，通常不影响商品库存；如果详情页展示成交状态，也删除详情缓存 |

> 这里选择删除缓存，而不是直接更新缓存，是因为商品详情可能包含主表、图片、分类、卖家摘要和库存字段等组合数据。删除缓存后，下一次查询再重新构建，逻辑更简单，也更不容易出现局部字段更新遗漏。

`product:detail:{id}` 和 `product:null:{id}` 必须一起失效。草稿或下架商品曾被公开详情查询时可能留下空值缓存；如果上架时只删正常详情 key，商品已经出现在列表，详情页仍会在空值 TTL 内误报不存在。

#### 事务边界

发布商品时，`product` 和 `product_image` 必须在同一个事务里。

编辑商品时，更新 `product`、删除旧图片、插入新图片也必须在同一个事务里。

申请审核时，商品进入待人工审核和创建审核记录要在同一个事务内完成。管理员审核时，再用事务校验商品仍在待人工审核状态，更新商品状态并写入 `product_review_log`。下架只需条件更新商品状态。

缓存删除放在数据库更新之后执行。

第一版可以在事务方法末尾删除；更严谨的做法是事务提交后再删除，避免数据库回滚但缓存已经被删。

#### 事务提交后删缓存怎么实现

用 Spring 的事务同步器，把删缓存动作注册到事务提交之后执行：

```java
TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
    @Override
    public void afterCommit() {
        // 只有事务真正提交成功后才删缓存，回滚时不会执行
        redisTemplate.delete("product:detail:" + productId);
    }
});
```

> 面试常被追问的 `@Transactional` 失效场景也要能说：① 同类内部方法自调用不走代理，事务不生效（解决：拆到另一个 Bean，或注入自身代理）；② 方法不是 public----Spring AOP 只能拦截 public 方法；③ 方法被 final / static 修饰---CGLIB 通过继承生成子类代理，无法重写 final 方法；static 是类方法，不走实例代理。   ④  默认只对 RuntimeException 回滚，受检异常要加 `rollbackFor = Exception.class`；

#### 设计取舍

商品发布后先保存为草稿，申请上架后进入人工审核，只有审核通过才进入在售状态。项目二是在这条稳定状态机之上增加 AI 初审

商品表只维护一个 `stock` 字段，表示当前还能被下单的库存。

下单成功就扣 `stock`，取消或超时取消就回补 `stock`。

历史订单展示和纠纷判断依赖 `product_snapshot`，不依赖商品表当前内容。

### 1.6 业务流 3：商品列表、商品详情、缓存与浏览记录

这条业务流分成两部分：商品列表负责让买家按条件浏览在售商品，商品详情负责展示完整信息，并承担缓存、浏览记录和浏览次数统计。

```text
商品列表
  -> 多条件分页查询
  -> 只展示在售且 stock > 0 的商品
  -> 不记录浏览历史
  -> 不做 Redis 缓存

商品详情
  -> 校验商品是否可公开展示
  -> 按缓存链路读取完整商品信息
  -> 缓存未命中时查询 MySQL 并重建
  -> 登录用户访问详情时记录浏览历史
  -> 异步累计 view_count
```

#### 这条业务流解决什么问题

买家可以按关键词、类目、校区、价格区间浏览在售且仍有库存的商品。

点进商品详情时，能看到卖家、图片、描述、价格、成色、交易地点、当前库存等完整信息。

登录用户查看详情后记录浏览历史，供个人中心展示，并为项目二的偏好分析提供基础数据。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `product` | 商品主表，保存标题、价格、状态、库存、浏览次数等核心信息 |
| `product_image` | 商品图片表，用于组装商品详情页图片列表 |
| `category` | 商品分类表，用于列表筛选和详情展示分类信息 |
| `user` | 用户表，用于展示卖家基础信息 |
| `browse_history` | 浏览记录表，用于记录登录用户最近看过的商品 |

| Redis Key | TTL | 作用 |
| --- | --- | --- |
| `product:detail:{productId}` | 5 分钟 + 随机值 | 缓存正常商品详情，随机 TTL 用来降低同一时间大量过期的风险 |
| `product:null:{productId}` | 10秒 | 缓存不存在的商品，防止恶意请求反复穿透到 MySQL |
| `product:lock:build:{productId}` | 由 Redisson 管理 | 热点商品缓存失效时，用分布式锁控制只有一个请求重建缓存 |

#### 商品列表怎么查

商品列表允许未登录访问。

后端接收关键词、类目、校区、价格区间、分页等查询条件，通过 MyBatis 动态 SQL 查询在售且库存大于 0 的商品列表，最后组装成分页结构返回。

> 商品列表不做缓存。因为关键词、类目、校区、价格、分页和实时库存都会影响结果，组合非常多。如果给每一种组合都做 Redis 缓存，Key 会膨胀，失效也麻烦。这个项目把缓存重点放在商品详情上，列表页直接通过索引查询 MySQL。

分页要限制 `pageSize`，避免一次拉取过多数据。数据量较小时使用普通分页；数据量增大后避免 `LIMIT 100000,20` 这类深分页，改用基于 `(created_at,id)` 或主键游标的 seek 分页。关键词中缀搜索量明显增加后，再考虑全文索引或 Elasticsearch。

#### 商品详情怎么查

商品详情接口接收商品编号，并尝试获取当前登录用户；未登录用户也可以查看公开商品详情。

公开详情接口只返回“在售且库存大于 0”的商品；卖家管理页、管理员审核页使用独立的鉴权查询接口读取草稿、已下架、已售罄和待人工审核商品，不能复用公开缓存，否则可能把非公开数据暴露给普通用户。

普通商品详情先查 Redis 商品详情缓存，命中后返回；未命中时查询数据库和商品图片，组装商品基础详情后写入 Redis。

如果数据库未命中，说明商品不存在或不可公开展示，这时写入短 TTL 空值缓存。

后续同一个商品编号再被请求时，命中空值缓存就直接返回商品不存在，避免恶意请求反复穿透到 MySQL。

正常商品详情缓存 TTL 加随机值，是为了避免大量商品缓存在同一时间集体过期。热点商品的完整读取和重建流程在后文统一说明。

#### 浏览记录和浏览次数怎么写

浏览记录只在商品详情接口写入，不在商品列表接口写入。未登录用户不记录；登录用户重复查看同一商品时不插入多条记录，只更新最后浏览时间。

浏览记录使用 `uniq(user_id, product_id)` 配合 upsert，只更新 `last_browsed_at`。它属于弱一致的行为数据，可以异步执行或使用独立短事务；写入失败只记录日志，不能让商品详情查询失败。为避免频繁刷新造成写放大，可以先在 Redis 做分钟级去重。

`view_count` 也不能在每次缓存命中时同步更新商品表，否则热点商品行会变成数据库写热点。第一版可以异步自增；流量增大后用 Redis `INCR` 聚合增量，再由定时任务批量回写 MySQL。浏览统计允许少量延迟，库存和订单状态不允许这样处理。

#### 缓存分层为什么这样设计

| 层级 | 使用范围 | 作用 |
| --- | --- | --- |
| Caffeine | 仅热点商品详情 | 拦截单个实例内的高频访问，减少 Redis 网络请求 |
| Redis | 普通商品和热点商品详情 | 多实例共享缓存，避免每个实例直接查询 MySQL |
| MySQL | 全部商品事实数据 | 最终事实来源 |

普通商品只走 Redis 旁路缓存；热点商品才增加 Caffeine。热点可以由运营配置或近期访问指标识别；如果第一版尚未实现热点识别，先统一使用 Redis，后续再增加本地缓存，不能把规划说成已经落地。

Caffeine 的过期时间应短于 Redis，并限制最大容量，避免本地内存被大量商品详情占满。

互斥重建不使用 Java 的 `synchronized` 或本地锁，因为项目部署多个后端实例时，本地锁只能限制当前 JVM，限制不了其他实例。

这里使用 Redisson 的 `RLock` 做 Redis 分布式锁，通过 `product:lock:build:{productId}` 控制同一个商品详情同一时间只有一个请求回源重建缓存。

这里不手写 `SET NX EX + Lua`，因为 Redisson 已经封装加锁、释放、持有者校验、可重入和超时释放等细节。

商品详情和卖家信用摘要应按对象分别缓存；订单状态、纠纷状态、权限和封禁状态要求强实时，不放进 Caffeine。

#### 热点缓存击穿怎么处理

热点商品的风险是：某个商品访问量很高，刚好 Caffeine 和 Redis 都没有命中，大量请求同时发现缓存未命中，然后一起去查 MySQL 并重建缓存，数据库会被瞬间打高。

Redisson 互斥重建的思路是：热点商品详情缓存未命中后，不是每个请求都去查数据库，而是先获取 `product:lock:build:{productId}` 对应的 `RLock`。

只有抢到锁的请求负责查询 MySQL、组装详情、回写 Redis 和 Caffeine；没抢到锁的请求短暂等待后重试读缓存，尽量复用抢锁线程重建出的结果。

```text
1. 先查 Caffeine 本地缓存，命中直接返回。
2. Caffeine 未命中，查 Redis 的 product:detail:{productId}。
3. Redis 命中正常详情，回写 Caffeine 后返回。
4. Redis 命中 product:null:{productId}，返回商品不存在。
5. Redis 也未命中，使用 Redisson 获取 RLock：product:lock:build:{productId}。
6. 抢锁成功后先 double check 一次 Redis，避免重复重建。
7. double check 仍未命中，再查 MySQL，组装详情，回写 Redis 和 Caffeine。
8. 数据库也查不到时，写入 product:null:{productId} 空值缓存。
9. 抢锁失败的请求短暂退避，再重试 Caffeine 和 Redis。
10. 重试多次仍未命中时，优先返回稍后重试；必要时只允许少量请求降级查询 MySQL，避免所有请求一起回源。
```

使用 Redisson 时，如果显式设置 `leaseTime`，租约必须覆盖缓存重建的 P99 耗时；显式租约通常不会依赖 watchdog 自动续期。另一种做法是不指定租约而使用 watchdog 自动续期。面试时不要只背“固定 10 秒”，而要说明锁过短会提前释放、锁过长会放大故障影响。

释放锁放在 `finally` 里，并用 `isHeldByCurrentThread()` 判断当前线程确实持有锁后再 `unlock()`，避免误释放其他线程的锁。

```java
RLock lock = redissonClient.getLock("product:lock:build:" + productId);
boolean locked = false;
try {
    // waitTime 为 50ms，leaseTime 为 10s，两个参数统一使用毫秒单位。
    locked = lock.tryLock(50, 10_000, TimeUnit.MILLISECONDS);
    if (!locked) {
        // 没抢到锁时，不直接打 MySQL，先短暂等待后重试缓存。
        return retryReadCache(productId);
    }

    // 抢到锁后再查一次缓存，避免别的线程刚刚已经重建完成。
    ProductDetail cached = readCache(productId);
    if (cached != null) {
        return cached;
    }

    // 只有持有锁的请求才允许回源 MySQL 并重建缓存。
    return rebuildProductDetailCache(productId);
} finally {
    if (locked && lock.isHeldByCurrentThread()) {
        // 只释放当前线程持有的锁，避免误删其他线程的锁。
        lock.unlock();
    }
}
```

这里的重点不是“所有请求最终都能抢到锁”，而是“同一时间只有一个请求回源重建缓存，其他请求等待重试或受控降级”。

#### 缓存一致性怎么控制

缓存一致性统一采用 Cache Aside：

```text
读：缓存未命中 -> 查询 MySQL -> 写入缓存
写：更新 MySQL -> 事务提交 -> 删除正常详情和空值缓存
热点本地缓存：删除 Redis 后，再删除本机 Caffeine
多实例：广播本地缓存失效事件
```

商品上架、下架、下单扣减库存和取消回补库存都会改变详情展示，因此都走同一套失效流程。卖家信用摘要按卖家维度单独缓存，不和商品详情绑在一个失效范围内。

这样做不追求“更新数据库的同时精确更新缓存”，而是用删除缓存降低双写一致性复杂度。`afterCommit` 能避免事务回滚时误删，并显著缩小旧值回填窗口，但不能数学上消灭所有并发竞态；仍要靠随机 TTL、必要时的延迟二删和失败补偿兜底。

多实例 Caffeine 失效可以通过消息或 Redis Pub/Sub 广播。广播不是可靠事实源，某实例离线时可能错过通知，因此本地缓存 TTL 要短、容量要有限；实例恢复后即使漏过广播，也会在短时间内重新从 Redis/MySQL 构建。

### 1.7 业务流 4：下单交易、库存扣减与并发控制

这条业务流解决库存型下单问题：同一商品可以有多件可售库存，多个买家可以分别下单；系统必须保证库存够时可以下单，库存不够时下单失败，并且任何并发情况下都不能超卖。

#### 整体流程

```text
买家提交下单请求和 requestId
  -> 按 buyerId + requestId 查询已有订单，重复请求直接返回
  -> Redis 短 TTL Key 限制连续点击
  -> 校验商品在售、库存充足且买家不是卖家
  -> MySQL 条件更新扣减库存
     ├─ 影响行数为 0：库存不足或商品状态已变化
     └─ 影响行数为 1：在同一事务创建订单、商品快照和状态日志
          -> 数据库唯一约束最终保证同一 requestId 只创建一笔订单
  -> 事务提交后删除商品详情缓存
  -> 订单进入待卖家确认
     ├─ 卖家确认：继续交易，库存不再重复扣减
     ├─ 用户取消：回补本单库存
     └─ 确认超时：系统关单并回补本单库存
```

下单主链路必须同步得出成功或失败结果，不能把库存扣减交给异步消息。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `product` | 保存商品状态和当前库存，下单时做条件扣减 |
| `trade_order` | 保存订单、`requestId`、购买数量、单价、总价和状态，并用唯一约束保证请求幂等 |
| `product_snapshot` | 保存下单那一刻的商品标题、描述、价格、成色、地点和图片 |
| `trade_order_log` | 记录超时取消、用户取消等订单状态流转，方便客服和纠纷解释 |

| Redis Key | 作用 |
| --- | --- |
| `order:submit:{userId}:{productId}` | 5 秒短 TTL，防止同一用户对同一商品连续点击下单按钮 |
| `product:detail:{productId}` | 下单成功、取消回补库存后删除，避免详情页库存展示不一致 |

#### 创建订单怎么走

创建订单时，后端从登录上下文获取买家身份，接收商品编号、购买数量、交易时间、交易地点、备注和 `requestId`。先按 `buyerId + requestId` 查询已有订单，重复请求直接返回原订单；首次请求再使用 Redis 短 TTL Key 限制连续点击。

随后查询商品，校验商品存在、未删除、处于在售状态，购买数量大于 0，并且买家不是卖家本人。校验通过后使用 MySQL 条件更新扣减库存；影响行数为 0 时，返回库存不足或商品状态已变化。

库存扣减成功后，后端读取数据库当前价格和商品信息，计算订单金额，创建待卖家确认订单，并写入商品快照和状态日志。事务提交后删除商品详情缓存。

库存扣减、订单创建、商品快照和订单日志必须放在同一个事务中。任何一步失败都整体回滚，避免出现库存已扣但订单不存在，或者订单存在却缺少快照证据。

订单单价和总价不能相信前端传值。金额使用 `BigDecimal` 和数据库 `DECIMAL`，由后端按数据库当前价格计算 `total_amount = unit_price * quantity`，并明确舍入规则。订单号由后端生成，返回前端时按字符串处理，避免 JavaScript 对超大 Long 精度丢失。

#### 请求幂等和库存并发怎么控制

| 机制 | 解决的问题 | 不能解决的问题 |
| --- | --- | --- |
| Redis 短 TTL Key | 同一用户短时间连续点击 | 网络超时后的重复请求、多用户并发下单 |
| `requestId` + 数据库唯一约束 | 同一次业务请求被重复提交 | 商品库存是否足够 |
| MySQL 条件更新 | 多用户并发扣减库存、防止超卖 | 判断两次请求是否属于同一次业务操作 |

这三层职责不同，不能用 Redis 防重复提交代替数据库幂等或库存并发控制。

Redis 按钮防抖使用 `SET key value NX EX 5`：

```java
// setIfAbsent 对应 Redis 的 SET NX EX，原子操作
Boolean ok = redisTemplate.opsForValue()
        .setIfAbsent("order:submit:" + userId + ":" + productId, "1", 5, TimeUnit.SECONDS);
if (Boolean.FALSE.equals(ok)) {
    throw new BizException("操作太频繁，请稍后再试");
}
```

> 关键点是 NX 和 EX 必须在一条命令里完成，保证原子性；key 不主动删除，5 秒后自动过期即可，逻辑最简单也不会有删错 key 的问题。

这个 key 只是“按钮防抖”，不是严格幂等。网络超时后客户端可能在 5 秒以后重试，单靠它仍可能创建两笔订单。严格幂等需要客户端为一次下单生成 `requestId`，数据库建立 `uniq(buyer_id, request_id)`；重复请求命中唯一键后返回第一次创建的订单，而不是再次扣库存。Redis 防抖负责体验，数据库唯一约束负责最终正确性。

真正防超卖的是 MySQL 条件更新：

```sql
-- 只有商品仍在售且库存足够时，才允许扣减库存。
update product
set stock = stock - #{quantity},
    status = case
        -- 扣减后库存为 0，商品同步进入售罄状态。
        when stock - #{quantity} = 0 then #{soldStatus}
        else #{onSaleStatus}
    end,
    updated_at = now()
where id = #{productId}
  and status = #{onSaleStatus}
  and stock >= #{quantity}
  and deleted = 0;
```

> `soldStatus` 和 `onSaleStatus` 由后端商品状态枚举提供，SQL 不依赖文档中假设的固定英文字符串。

这可以理解成“条件更新式并发控制”。它不是用版本号字段的典型乐观锁，但思路相近：SQL 里带着库存充足条件，更新成功看影响行数。InnoDB 执行更新时会对命中的商品行加排他锁，并发请求会串行判断最新库存；如果库存不够，影响行数就是 0，后端返回库存不足。

例如商品当前库存为 2，用户 A 和 B 各买 1 件可以依次扣减成功；用户 C 再下单时，库存条件不成立。并发目标不是“只允许一个用户成功”，而是库存足够就允许多笔订单成功，同时保证库存永远不会变成负数。

#### 商品快照怎么写

商品快照保存的是“下单那一刻买家看到的商品信息”。订单本身保存本次购买数量、单价和总价；快照保存商品标题、描述、价格、成色、校区、交易地点和图片。

这样后续卖家编辑商品、下架商品、删除图片，都不会影响历史订单展示和纠纷判断。快照应把图片地址列表序列化或写入快照子表；如果 OSS 对象允许被物理删除，还要有“有历史订单引用时不得删除”或归档策略，否则数据库有快照地址但文件已经不存在。

#### 待确认订单超时怎么释放库存

下单成功时库存已经扣减，`trade_order` 同时写入 `confirm_deadline`。如果卖家到期仍未确认，系统要把订单改为超时取消，并回补本单占用的库存。MQ 不参与同步扣库存，只负责在确认期限到达后触发关单。

待卖家确认订单的超时触发采用“延迟消息为主、定时扫描兜底”：

| 方案 | 优点 | 缺点 | 定位 |
| --- | --- | --- | --- |
| 定时扫表 | 实现简单、不依赖消息中间件 | 精度受扫描周期限制，订单量大时有扫描压力 | 第一版实现或兜底 |
| RocketMQ 延迟消息 | 到期触发更及时，不需要持续扫全表 | 要处理发送失败、重复消费和死信 | 主触发链路 |

##### 完整流程先看这里

```text
买家下单
  -> 本地事务扣减库存、创建待卖家确认订单
  -> 订单写入 confirm_deadline
  -> 本地事务提交成功
  -> 生产者发送“订单确认超时”延迟消息
  -> Broker 暂存消息，期限到达前不交给消费者
  -> 到达投递时间，Broker 将消息变为可消费
  -> 消费者收到 orderId，调用 timeoutCancel(orderId)
       ├─ 订单仍是待卖家确认：改为超时取消、回补库存、写状态日志
       └─ 订单已确认 / 已取消 / 已超时处理：直接结束，不再回补
  -> 本地事务成功后 ACK；处理异常则触发 MQ 重试
```

正常情况下，消费者拿到消息时已经到达确认期限，不需要“收到后继续等”。RocketMQ 5.x 可以直接把投递时间设置为 `confirm_deadline`；RocketMQ 4.x 使用固定延迟级别时，应让业务超时时间与可用级别匹配，或者选择第一个不早于截止时间的级别，不能为了更接近而选择更短的级别。选择更大的级别只会稍晚触发，不会提前关单。

消费者 SQL 仍然保留 `confirm_deadline <= now()`，它只是最后一道防御，不是正常流程中的等待分支。这样可以防止延迟级别配置错误、消息被人工提前重放，或者以后超时规则变化时旧消息误关单；正确配置下不会走“尚未到期”的分支。

##### 生产者怎么发送

下单事务只负责扣减库存、创建订单、保存商品快照和状态日志，不在事务内部等待 MQ 网络调用。事务提交成功后，通过 `afterCommit` 或 `@TransactionalEventListener(phase = AFTER_COMMIT)` 发送超时消息；如果订单事务回滚，就不会产生一条实际不存在的订单消息。

消息不携带商品价格、库存等易变化数据，只携带定位和校验所需的最小信息：

| 字段 | 作用 |
| --- | --- |
| `eventId` | 本次超时事件编号，用于日志追踪和问题排查 |
| `orderId` | 定位订单，通常同时作为 RocketMQ 的 message key |
| `confirmDeadline` | 记录本次消息对应的确认截止时间，方便排查延迟和错误配置 |
| `schemaVersion` | 后续消息结构升级时做兼容 |

Topic 可以按订单领域划分，Tag 使用“订单确认超时”。消息发送成功的标准是 Broker 已确认接收，而不是生产者只调用了发送方法；发送日志至少记录 `eventId`、`orderId`、message key、目标投递时间和发送结果，便于定位消息是否发出、何时到期。

`afterCommit` 解决了“事务回滚但消息已经发出”，却不能完全解决“事务已经提交但进程在发送前崩溃”或“连续发送失败”。当前方案对发送做有限重试，失败后记录订单编号并告警，再由低频扫表修复。可靠性要求更高时，增加 Outbox 表：下单事务同时写入待投递事件，后台任务发送成功后标记已投递。即使发生“消息已发出但 Outbox 还没来得及改状态”而重复发送，消费者也必须能够安全处理。

##### 消费者怎么关单

消费者收到消息后先校验必要字段，再按 `orderId` 查询订单。订单不存在属于异常数据，需要记录并告警；订单已经被卖家确认、用户取消或另一个消费者超时处理过，说明消息已经失效，直接 ACK，不需要重试。

真正关单时使用带旧状态和截止时间的条件更新：

```sql
update trade_order
set status = #{timeoutCancelledStatus},
    updated_at = now()
where id = #{orderId}
  and status = #{pendingConfirmStatus}
  and confirm_deadline <= now();
```

影响行数为 1，消费者才获得本次关单资格，并在同一个本地事务中按订单购买数量回补 `product.stock`、写入 `trade_order_log`。商品当前只是因为库存为 0 而售罄时可以恢复为在售；若已经被人工下架或逻辑删除，则只回补库存，不擅自改回在售。事务提交后再删除 Redis 和 Caffeine 商品详情缓存，最后向 Broker 返回消费成功。

影响行数为 0 时不再回补库存。正常原因是订单已经确认、取消或被另一个实例处理；如果查询发现订单仍是待卖家确认但数据库时间确实未到截止时间，则说明消息配置或重放过程有问题，记录告警后结束本次消费，交由正确的延迟消息或兜底扫描处理，而不是让消费者线程等待。

订单状态更新是库存回补的“资格锁”。必须先抢到从待卖家确认到超时取消的状态转换，才能回补库存，不能先加库存再改订单。即使消息重复投递，或者消费者事务已经提交但 ACK 前宕机，Broker 再次投递时条件更新也只会影响 0 行，因此不会重复增加库存。对于这个单一状态转换，订单状态机本身就能实现业务幂等；如果以后消费还要跨多个服务产生副作用，再增加带唯一键的消费记录表。

订单改状态、库存回补和状态日志写入必须在同一事务。数据库死锁、连接超时等临时异常会让本地事务回滚，消费者抛出异常或返回稍后重试；订单已结束属于正常幂等结果，直接 ACK。格式损坏等永久错误不应无限重试，应记录坏消息和告警。超过最大重试次数的消息进入死信队列，死信支持补偿任务或人工重新驱动同一个 `timeoutCancel(orderId)` 方法。

##### 延迟消息会不会丢、重复或不准时

RocketMQ 按至少一次投递设计，不承诺业务上的“恰好一次”。消息可能晚到、重复或处理失败，但正确设计下不应该提前消费：

| 异常 | 处理方式 |
| --- | --- |
| 重复投递、ACK 前宕机 | 订单旧状态条件更新保证只回补一次库存 |
| 消费异常 | 本地事务回滚，RocketMQ 按退避策略重试 |
| 消息进入死信 | 高优先级告警，补偿任务或人工重新驱动同一关单方法 |
| 发送失败、消息丢失或长期积压 | 低频定时扫描补偿，不把 MQ 当作唯一事实源 |

兜底任务只扫描 `status = 待卖家确认 and confirm_deadline <= now()` 的订单，数据库应建立 `(status, confirm_deadline, id)` 联合索引，并按主键分批处理，避免一次加载大量订单。多实例执行时可以按 ID 分片或加任务锁；无论延迟消息还是扫描任务，都调用同一个 `timeoutCancel(orderId)` 领域方法，避免出现两套关单规则。

需要监控发送失败数、实际投递时间与目标时间的差值、消费重试数、死信数、消息积压时间、超过截止时间仍处于待确认的订单数，以及兜底任务实际修复数量。

面试时可以按这条主线回答：订单事务提交后发送延迟消息，Broker 到期才交给消费者；消费者用旧状态条件更新抢关单资格，成功后在同一事务回补库存并写日志；重复消费靠状态机幂等，异常靠重试和死信，消息缺失靠定时扫描兜底，数据库中的订单状态始终是最终事实。

### 1.8 业务流 5：卖家确认、取消订单与交易完成

下单成功后，订单先进入待卖家确认状态，商品库存已经扣减。这条业务流负责处理订单后续状态流转，以及取消订单时如何回补库存。

#### 整体状态流转

```text
待卖家确认
  ├── 卖家确认 -> 已确认
  ├── 买家 / 卖家取消 -> 已取消，并回补本单库存
  └── 系统超时 -> 超时取消，并回补本单库存

已确认
  ├── 买家确认完成 -> 已完成
  ├── 买家 / 卖家取消 -> 已取消，并回补本单库存
  └── 任一方发起纠纷 -> 纠纷中

已完成
  └── 售后窗口内任一方发起纠纷 -> 纠纷中

纠纷中
  └── 普通确认、取消和完成入口全部拒绝，由管理员处理
```

这里使用中文描述业务含义，不限定代码中的订单枚举名或数据库存储值。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `trade_order` | 保存订单状态、买家、卖家、商品、购买数量和完成时间 |
| `product` | 取消订单时按订单购买数量回补库存 |
| `trade_order_log` | 记录每次状态变化的前后状态、操作者、原因和时间 |
| `product:detail:{productId}` | 取消订单会改变商品库存，完成订单如果影响详情展示也要删除缓存 |

#### 卖家确认怎么走

卖家确认时，后端先确认订单存在且操作者是订单卖家，再带旧状态条件将订单从待卖家确认改为已确认，同时写入订单状态日志。卖家确认不改商品库存，因为库存已在下单成功时扣减；重复确认或订单已经取消、超时的请求影响行数为 0，后端读取最新状态后返回。

#### 取消订单怎么走

取消订单允许由订单买家或卖家发起，但旧状态只能是待卖家确认或已确认。后端先条件更新为已取消，只有影响行数为 1，才在同一事务中按订单购买数量回补库存并写入状态日志；事务提交后删除商品详情缓存。这样既能防止重复取消造成库存重复回补，也能避免订单已取消但库存没有恢复。

#### 完成订单怎么走

完成订单只允许买家操作。后端带旧状态条件将订单从已确认改为已完成，写入完成时间和状态日志；事务提交后异步重算成交次数，如果商品详情展示成交状态，再删除对应缓存。完成订单不再修改库存，条件更新会拒绝重复完成、已取消订单继续完成以及纠纷中订单绕过纠纷流程。

第一版只允许买家确认完成，避免卖家单方面把尚未履约的订单标记为已完成。卖家可以发起“提醒确认”，但不能直接完成订单；如果以后设计双方确认，应增加买卖双方各自的确认字段，而不是任意一方一次点击就完成。

#### 并发控制与事务边界

| 动作 | 允许的状态变化 | 同一事务内完成 |
| --- | --- | --- |
| 卖家确认 | 待卖家确认 → 已确认 | 更新订单、写状态日志 |
| 取消订单 | 待卖家确认或已确认 → 已取消 | 更新订单、回补库存、写状态日志 |
| 完成订单 | 已确认 → 已完成 | 更新订单和完成时间、写状态日志 |
| 超时关单 | 待卖家确认 → 超时取消 | 更新订单、回补库存、写状态日志 |

每次状态变化都通过 `where id = ? and status = ?` 条件更新控制并发，接口层提前查询的状态只用于权限校验和友好提示。订单处于待卖家确认时，卖家确认、用户取消和系统超时可能同时到达，只有影响行数为 1 的请求可以继续；需要回补库存的入口必须先成功更新订单，再修改库存，不能颠倒顺序。订单状态日志至少记录前后状态、操作者类型、操作者 ID、原因和时间。

第一版没有在线支付，已确认订单取消时只处理订单、库存和日志。如果以后接入支付，是否允许取消以及何时回补库存，还必须同时受支付和退款状态机约束。

### 1.9 业务流 6：交易评价、卖家信用与纠纷申请

这条业务流补完整个交易闭环：交易完成后沉淀评价和信用；交易异常时进入纠纷流程，并为项目二的 AI 纠纷辅助提供证据链。

#### 整体流程

```text
订单已完成
  -> 买家评价卖家
  -> 写入评价明细
  -> 异步重算卖家信用摘要
  -> 商品详情页展示最新信用和最近评价

订单已确认，或已完成但仍在售后窗口内
  -> 买家或卖家发起纠纷
  -> 创建纠纷单并冻结订单正常流转
  -> 管理员根据订单快照和双方证据处理
  -> 恢复订单、维持完成、取消交易或等待补充材料
```

评价和纠纷都必须绑定真实订单，参与人和被评价人、被投诉人由订单关系推导，不能由前端任意指定。发起纠纷后，普通取消和完成入口失效；项目一由管理员处理，项目二的 AI 也只能整理证据和生成建议，最终结论仍由管理员作出。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `trade_order` | 确定买家、卖家、商品和当前交易状态 |
| `trade_review` | 保存订单完成后的评价 |
| `user_credit_summary` | 保存用户信用聚合数据，用于商品详情页展示 |
| `dispute` | 保存纠纷申请、双方说明、证据和处理状态 |
| `product_snapshot` | 保存下单时商品信息，是纠纷证据链核心 |

商品基础详情和卖家信用按对象分别查询、分别缓存，接口层再组装返回。一次评价只需删除或重建该卖家的信用缓存，不必清理他发布的所有商品详情缓存。

#### 提交评价和更新信用

提交评价时，后端从登录上下文获取评价人，接收订单 ID、评分、评价内容和标签，校验订单存在、已经完成且当前用户是买家，再从订单中确定被评价的卖家并写入 `trade_review`。数据库使用 `uniq(order_id)` 保证第一版同一订单只能评价一次，重复请求直接返回已有结果或提示已评价。

第一版只允许买家评价卖家。如果后续支持买卖双方互评，再把唯一约束扩展为 `(order_id, reviewer_id)`。

信用摘要由评价表聚合得到，避免每次商品详情都实时统计评价表。

| 字段 | 含义 |
| --- | --- |
| `review_count` | 收到的可见评价数 |
| `avg_rating` | 平均评分 |
| `good_review_rate` | 4 分及以上评价占比 |
| `bad_review_count` | 2 分及以下评价数量 |
| `credit_score` | 基础 100 分，根据好评和差评做轻量调整 |

第一版信用分只做简单、可解释的计算：

```text
credit_score = 100 + 好评数 * 1 - 差评数 * 3
最低 60 分，最高 100 分
```

评价事务只同步写入评价事实，提交后发送“信用重算”消息。消费者重新聚合该卖家的可见评价，更新 `user_credit_summary` 并删除信用缓存；商品详情页直接读取摘要和最近可见评价，不实时扫描全部评价。信用摘要是可重建的聚合视图，允许秒级最终一致，这样评价接口事务更小，也能复用同一入口处理“评价被管理员隐藏后重算”。

全量聚合重复执行结果一致，但“幂等”不代表没有并发覆盖问题。同一卖家的重算任务可以按卖家 ID 串行消费，或者更新摘要时带 `summary_version / calculated_at` 条件，避免较早开始的慢任务最后写回旧统计。订单首次进入已完成时还要幂等更新成交次数；成交次数不能只靠评价数推导，因为已成交订单可能没有评价。

#### 发起纠纷怎么走

发起纠纷时，后端从登录上下文获取申请人，接收订单 ID、纠纷原因、文字说明和证据材料。申请人必须是订单买家或卖家，订单必须处于已确认状态，或者已完成但仍在可配置的售后窗口内。后端根据订单关系确定被投诉方，在同一事务中创建纠纷单、保存订单进入纠纷前的状态，并带旧状态条件把订单改为纠纷中；事务提交后按实际展示内容删除相关缓存。

同一订单第一版只允许一张纠纷主单，数据库建立 `uniq(order_id)`，避免并发点击创建两张纠纷。以后确实需要申诉或重开，再拆“纠纷主单 + 处理轮次”，而不是一开始允许多张未明确关联的纠纷单。

#### 纠纷证据链怎么查

纠纷证据链不是一张表，而是一组围绕订单聚合的数据：

| 数据 | 来源 |
| --- | --- |
| 订单当前状态 | `trade_order` |
| 下单时商品信息 | `product_snapshot` |
| 纠纷申请内容 | `dispute` |
| 用户上传证据 | 纠纷单中的证据图片或材料地址 |
| 被投诉方历史信用 | `user_credit_summary` |
| 被投诉方最近评价 | `trade_review` |

当前纠纷以订单状态、商品快照、双方说明和上传证据为主要依据。历史信用和评价只能说明交易风险背景，不能证明本次纠纷由谁负责；项目二的 AI 纠纷辅助也必须保持这个边界。

用户上传的证据至少记录文件地址、上传人、上传时间、文件哈希和材料类型；展示时使用短时签名地址。需要多份证据时建议拆 `dispute_evidence` 子表，避免把不可检索、不可单独撤回的地址数组全部塞在纠纷主表。文字陈述和上传材料都属于“当事人主张”，不应在 AI Prompt 中伪装成已验证事实。

#### 纠纷处理后的订单出口

| 处理结果 | 订单出口 | 库存处理 |
| --- | --- | --- |
| 驳回纠纷 | 恢复到进入纠纷前的状态 | 不变 |
| 维持交易完成 | 进入或保持已完成 | 不变 |
| 双方确认取消 | 进入已取消 | 仅在确认商品已退回且仍可售时回补 |
| 材料不足 | 纠纷改为待补充材料，订单继续冻结 | 不变 |

最终动作必须来自后端枚举白名单，纠纷状态更新、订单状态恢复/关闭、必要的库存回补和日志写入放在同一事务。重复处理依靠 `where dispute_status in (...)` 和订单旧状态条件保证只执行一次；AI 建议不直接触发这些写操作。

#### 事务边界

| 动作 | 事务要求 |
| --- | --- |
| 提交评价 | 事务内只插入 `trade_review`；提交后发送信用重算消息，摘要最终一致 |
| 发起纠纷 | 插入 `dispute`、保存原状态、订单改为纠纷中，属于同一个事务 |
| 处理纠纷 | 更新纠纷结果、恢复或关闭订单、必要时回补库存、写处理日志属于同一个事务 |

评价不改变订单状态；发起和处理纠纷会同时修改纠纷单与订单，因此必须保存进入纠纷前的状态，并通过条件更新防止重复处理和并发覆盖。

### 1.10 支撑资料：数据库设计

前面的业务流已经说明了每个动作改哪些数据，这里只保留全局数据模型、关键约束和索引设计。面试时不需要背建表 SQL，但要能解释“事实数据放在哪里、为什么拆表、靠什么保证一致性”。

#### 领域分表

| 领域 | 核心表 | 职责 |
| --- | --- | --- |
| 用户与信用 | `user`、`user_credit_summary` | 账号与权限是事实数据；信用摘要是由成交和评价聚合出的读模型 |
| 商品 | `category`、`product`、`product_image`、`product_review_log`、`browse_history` | 商品主信息、图片、审核轨迹和浏览行为分开保存，避免商品主表不断变宽 |
| 交易 | `trade_order`、`product_snapshot`、`trade_order_log` | 订单保存交易事实，快照固定下单时信息，日志记录状态变化 |
| 交易后 | `trade_review`、`dispute` | 评价与纠纷都必须绑定真实订单，不能脱离交易关系单独创建 |

#### 关系与数据不变量

| 关系或约束 | 设计原因 |
| --- | --- |
| `product` 与 `trade_order` 是一对多 | 商品支持库存后，同一商品可以产生多笔订单，不能再用“一件商品只能有一笔有效订单”限制交易 |
| `trade_order` 与 `product_snapshot` 是一对一 | 商品后续编辑或下架不能改变历史订单展示和纠纷证据 |
| `trade_order` 与 `trade_order_log` 是一对多 | 主表保存当前状态，日志追加保存每次关键流转，便于审计和排障 |
| `trade_review` 与 `dispute` 第一版都对 `order_id` 唯一 | 当前只支持买家评价一次、一单发起一次纠纷；以后增加互评或多轮申诉时再调整模型 |
| `trade_review` 保存评价事实，`user_credit_summary` 保存聚合结果 | 摘要可以异步重算，评价明细才是最终事实源 |
| 历史订单、快照、评价和纠纷不物理删除 | 这些数据承担交易凭证和审计作用，业务撤销通过状态字段表达 |

状态字段保存稳定编码，所有状态变化必须经过服务层状态机和旧状态条件更新，前端不能直接指定任意目标状态。主要表统一保留创建时间和更新时间；可编辑业务对象按需要增加软删除字段。是否声明数据库物理外键可以按项目规模选择，但无外键时必须由应用校验关联存在，并用非空、唯一约束、状态机和对账任务保证数据完整性。

#### 唯一约束

| 约束 | 保证的业务规则 |
| --- | --- |
| `user(student_no)`、`user(phone)` 唯一 | 并发注册时最终不会创建重复账号 |
| `trade_order(buyer_id, request_id)`、`trade_order(order_no)` 唯一 | 同一次下单请求只创建一笔订单，业务订单号可稳定查询 |
| `browse_history(user_id, product_id)` 唯一 | 重复浏览只更新时间，不重复插入记录 |
| `trade_review(order_id)`、`dispute(order_id)` 唯一 | 落实第一版的一单一评、一单一纠纷规则 |

#### 索引设计

| 表 | 索引 | 服务的查询 | 说明 |
| --- | --- | --- | --- |
| `product` | 根据真实高频条件建立 `(status, campus, category_id, price, id)` 等组合索引 | 商品列表筛选和稳定分页 | 动态查询可能跳过中间列，一个联合索引不能覆盖所有组合，必须用 `EXPLAIN` 和慢日志验证 |
| `product` | `idx(seller_id, status)` | 卖家查看自己的商品 | |
| `product_image` | `idx(product_id, sort)` | 详情页按顺序取图 | |
| `trade_order` | `idx(buyer_id, status)`、`idx(seller_id, status)` | 买家/卖家订单列表 | |
| `trade_order` | `idx(status, confirm_deadline, id)` | 分批扫描已到期的待确认订单 | 状态等值过滤后按截止时间范围查询，`id` 用于稳定翻页 |
| `dispute` | `idx(status, created_at, id)` | 后台按状态查看待处理纠纷 | |

标题 `like '关键词%'` 前缀匹配有机会使用普通 B+Tree 索引，`like '%关键词%'` 中缀匹配通常不能。数据量增大且确实需要中缀检索时，再评估 MySQL 全文索引或 Elasticsearch。索引是否生效以实际 SQL、数据分布和 `EXPLAIN` 为准，不能只看到索引名称就断言一定会走。

### 1.11 支撑资料：性能验证、降级与可观测性

#### 性能结论怎么证明

缓存、索引和异步化是否有效，必须用可复现测试证明。压测报告至少记录以下信息：

| 维度 | 必须记录的内容 |
| --- | --- |
| 环境 | CPU、内存、JDK、数据库和 Redis 部署方式、线程池与连接池大小 |
| 数据 | 商品和订单规模、热点比例、缓存是否预热 |
| 负载 | 并发数、升压时间、持续时间、读写比例和请求参数分布 |
| 指标 | 吞吐、P95/P99、错误率、数据库 QPS、连接池等待、Redis 命中率 |

重点测试四类场景：商品详情冷缓存、Redis 命中、Caffeine 热点命中之间的对照；商品列表在不同筛选条件下的 SQL 执行计划；多用户并发下单时吞吐与库存正确性；关闭 Redis 或限制数据库连接后的降级表现。缓存提升来自减少数据库连接占用、SQL 执行、对象组装和网络往返，不能简单表述为“从磁盘查询变成内存查询”，因为 MySQL 热数据本身也可能位于 Buffer Pool。

没有保存压测报告，就只说明设计目标、测试方法和预期瓶颈，不报虚构的 QPS、命中率或毫秒数。并发下单除了看性能，还必须核对最终库存、成功订单数量和状态日志，不能只看接口没有报错。

#### 依赖故障怎么降级

| 故障点 | 处理原则 |
| --- | --- |
| MySQL 不可用 | 核心读写快速失败并告警，不能把缓存中的旧数据当成订单、库存或权限事实继续写业务 |
| 商品详情 Redis 不可用 | 短超时后受限回源 MySQL；对热点请求限流，避免缓存故障演变成数据库雪崩 |
| 登录态 Redis 不可用 | 需要登录或涉及写操作的接口默认 fail-closed；公开商品读取可以继续服务 |
| 防抖 Key 不可用 | 可以失去体验层防抖，但仍由 `requestId` 唯一约束和库存条件更新保证正确性 |
| Redisson 重建锁不可用 | 限流回源或快速失败，不能让所有热点请求同时穿透到数据库 |
| RocketMQ 不可用或积压 | 同步下单主链路不依赖 MQ；超时关单、缓存补偿和信用重算通过重试、死信告警与定时任务恢复 |
| OSS 上传失败 | 发布或提交证据明确失败，不保存无效地址；历史订单引用的对象采用禁止物理删除或归档策略 |

降级的前提是不能破坏业务正确性。商品详情缓存允许回源，登录态、订单状态和库存不允许用旧缓存猜测；具体的缓存删除补偿和延迟关单补偿已分别在业务流 3、业务流 4 中说明，这里不再重复。

#### 接口安全与审计

| 风险 | 控制方式 |
| --- | --- |
| 越权修改 | 操作者从登录上下文获取，Service 层校验资源归属和角色；前端隐藏按钮不能代替后端鉴权 |
| 参数与输出风险 | 统一做类型、范围和长度校验；文本展示时输出编码，防止超长请求和存储型 XSS |
| 文件风险 | OSS 上传限制类型、大小和数量；纠纷证据使用私有权限与短时签名地址 |
| 信息泄露 | 全局异常处理返回稳定错误码，不向前端暴露 SQL、堆栈和内部表名；日志对手机号、Token 和证据地址脱敏 |
| 操作不可追溯 | 状态变化记录操作者、业务对象、前后状态、原因、时间和 `traceId`，但不记录密码、JWT 和完整敏感材料 |

#### 监控和告警

| 层面 | 重点观察 |
| --- | --- |
| 应用 | QPS、P95/P99、错误率、JVM 堆与 GC、线程池和连接池等待 |
| 依赖 | MySQL 慢 SQL、锁等待和死锁；Redis 命中率、超时和热点 Key；RocketMQ 发送失败、积压、重试和死信 |
| 业务正确性 | 下单成功率、库存小于 0、超时订单未关闭、订单长时间停留在中间态、纠纷待处理时长 |

日志、指标和链路通过 `traceId` 关联。告警同时设置阈值和持续时间，避免单次抖动造成误报；库存异常、MQ 死信和订单状态卡住属于正确性问题，应使用高优先级告警并配合定时对账。

#### 面试证据边界

“踩坑”和性能数字只能讲真实发生并能解释证据链的内容。可以准备 JMeter 报告、`EXPLAIN` 结果、慢 SQL、关键日志、监控截图以及对应修改记录；没有这些材料时，就把内容表述为设计考虑或改进方案，不虚构故障现象、定位过程和修复效果。

## 2. 项目二：校园二手交易智能体系统

项目二是在项目一交易平台上接入 `Spring AI` 的业务增强模块。项目一负责用户、商品、订单、评价、纠纷和状态机；项目二只基于这些真实业务数据做审核、问答、搜索和纠纷辅助，不替代交易系统本身。

### 2.1 项目定位与整体架构

#### 项目定位

项目二是在项目一交易系统之上增加的 AI 能力层，复用原有商品、订单、纠纷、信用和权限体系，不重新实现一套交易系统。它解决四类自然语言与非结构化信息问题：商品合规审核、商品智能查询、智能客服和纠纷辅助处理。

这不是一个让模型自由操作所有业务的通用 Agent 平台，而是按业务入口拆分的受控工作流型多 Agent 系统。大模型负责理解、检索、规划和生成，Java 后端负责鉴权、工具执行、状态机、结果校验和最终落库。

#### AI 能力与入口

| AI 能力 | 入口 | 核心作用 | 最终决定者 |
| --- | --- | --- | --- |
| 商品合规审核 Agent | 卖家申请上架商品 | 根据商品信息和发布规则输出 `PASS`、`REJECT` 或 `NEED_MANUAL_REVIEW` | 后端状态机；高风险和不确定结果转人工 |
| 商品智能查询 Agent | 搜索页智能搜索，或智能客服转交 | 把自然语言需求转换为查询条件，只推荐真实在售且有库存的商品 | 数据库查询结果和后端过滤 |
| 智能客服 Agent | 用户聊天入口 | 回答平台规则，查询订单和纠纷进度，识别找商品意图并转交查询 Agent | 只读工具和规则知识；复杂问题转人工 |
| 后台纠纷辅助 Agent | 管理员打开纠纷审核页 | 汇总事实、双方陈述、证据和规则，生成处理建议 | 管理员 |

普通用户主要感知智能客服和智能搜索；商品审核、纠纷辅助属于平台内部流程。四个 Agent 不是平级群聊：客服只在识别到找商品意图时构造 `ProductQueryTask` 转交商品查询；商品审核由上架事件触发，纠纷辅助由管理员触发，二者不经过客服。

#### 整体架构

```text
业务入口
  ├─ 卖家申请上架
  ├─ 用户聊天 / 智能搜索
  └─ 管理员审核纠纷
        ↓
Java 后端 Orchestrator
  ├─ 登录态与对象权限校验
  ├─ 构建当前任务上下文
  ├─ 注册当前 Agent 的工具白名单
  ├─ 控制超时、轮数和 token 预算
  └─ 校验结构化结果并决定落库、转交或兜底
        ↓
四个领域 Agent
  ├─ 商品合规审核
  ├─ 商品智能查询
  ├─ 智能客服
  └─ 纠纷辅助
        ↓
公共 AI 支撑
  ├─ Spring AI ChatClient 与结构化输出
  ├─ RAG / VectorStore
  ├─ Tool Calling
  ├─ 会话记忆与用户画像
  ├─ SSE 流式返回
  └─ 运行日志、评测与降级
        ↓
项目一业务 Service 与数据
  ├─ 商品、订单、纠纷、评价、信用
  └─ MySQL、Redis、OSS
```

智能客服是用户侧 Router，但真正的执行编排器是 Java 后端。模型不能直接访问数据库，也不能自行获得新的工具；工具内部仍要重新鉴权，核心业务写入必须经过原有 Service 和状态机。

#### 核心边界

| 边界 | 约束 |
| --- | --- |
| 业务事实 | 商品、库存、订单、纠纷和权限以项目一 MySQL 数据为准，模型记忆和生成内容不是事实源 |
| 工具访问 | 每个 Agent 只注册完成当前任务所需的白名单工具，模型不能调用任意接口或直接执行 SQL |
| 写操作 | 模型只返回建议或结构化意图；最终写入由后端鉴权、版本校验、条件更新和状态机完成 |
| 用户数据 | 订单、纠纷工具按当前登录用户重新校验对象权限；后台工具只对管理员开放 |
| 高风险结果 | 纠纷必须人工决定；商品审核中的低置信度、规则缺失和异常结果统一转人工 |
| 记忆使用 | 会话记忆和用户画像只服务客服与商品查询，不进入商品审核和纠纷判定 |
| 失败原则 | 无可靠依据时拒答或转人工，不使用模型常识猜测实时订单、库存和纠纷状态 |

项目二只增加必要的 AI 中间状态，不推翻项目一状态机：

| 业务对象 | 项目二扩展 | 含义 |
| --- | --- | --- |
| 商品 | AI 审核中 | AI 通过或驳回后复用项目一已有状态；不确定时回到待人工审核 |
| 纠纷 | `AI_REVIEWED`、`MANUAL_REVIEWING` | 只表示辅助分析进度，不代表纠纷已经结案 |
| 订单 | 不新增状态 | 客服只能解释和查询，不能替用户下单、取消或完成交易 |

#### 技术主线

| 技术 | 在项目中的职责 |
| --- | --- |
| Spring AI `ChatClient` + 通义千问 `qwen-plus` | 统一模型调用、Prompt、工具和结构化输出 |
| RAG / `VectorStore` | 检索发布规则、交易规则、纠纷规则和商品知识，并保存可追溯引用 |
| Tool Calling | 通过后端受控工具读取实时商品、订单、纠纷和信用事实 |
| Memory | 组合会话摘要、最近消息和经过治理的用户画像，支持连续问答 |
| SSE | 流式返回用户侧长回答；后台审核不依赖 SSE |
| 审计与评测 | 记录运行、工具、规则引用和人工结果，支持回归评测、监控与降级 |

具体业务流程放在 2.2～2.5；RAG、记忆、SSE、评测和降级放在 2.6～2.9；Agent 范式与面试追问统一放在 2.10。2.1 只负责说明“项目是什么、有哪些入口、各部分如何协作、边界在哪里”。

### 2.2 业务流 1：商品合规审核 Agent

项目一由管理员审核全部上架申请；项目二在原流程前增加 AI 初审，减少明显合规商品和明确违规商品的重复人工判断。不确定、依据不足或系统异常时仍回到项目一的人工审核，AI 不替代最终安全边界。

#### 整体状态流转

```text
卖家创建或修改商品
  -> 草稿 / 已下架 / 审核驳回
  -> 卖家申请上架
  -> AI 审核中
       ├─ PASS：后端校验通过 -> 在售
       ├─ REJECT：明确命中规则 -> 审核驳回
       └─ NEED_MANUAL_REVIEW / 异常 / 依据不足
            -> 待人工审核
                 ├─ 人工通过 -> 在售
                 └─ 人工驳回 -> 审核驳回
```

`AI 审核中` 是受控的过渡状态，不是模型自己的状态。商品进入该状态后，卖家不能继续用旧内容重复申请；模型返回的结果也只有在商品状态和版本仍匹配时才能生效。

#### 这条业务流解决什么问题

1. 对标题引流、明显禁售品、类目错误等高频规则先做自动初审，降低管理员重复劳动。
2. 把商品字段、图片检查结果和当前版本发布规则统一交给审核 Agent，输出结构化且可追溯的判断。
3. 用状态机、商品版本和人工兜底约束模型，避免旧结果覆盖新商品、无依据拒绝或异常任务长期卡住。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `product` | 保存商品主体、卖家、状态、版本、标题、描述、类目、价格、成色和交易地点 |
| `product_image` | 提供图片数量、格式和访问地址；图片内容判断需要视觉/OCR 能力 |
| `user_credit_summary` | 作为卖家风险背景，不能成为自动拒绝的唯一依据 |
| `PRODUCT_RULE` | 当前生效的商品发布规则，如禁售品、站外引流、图片和类目要求 |
| `ai_agent_run` | 记录 `reviewRunId`、商品及版本、模型/Prompt/规则版本、运行状态和失败原因 |
| `product_review_log` | 保存 AI 或人工审核结果、原因、建议和规则引用，供卖家查看与管理员复核 |

#### 权限和触发边界

- 只有商品所属卖家可以申请上架；后端从登录态取得用户，不能相信模型或前端传入的 sellerId。
- 只有草稿、已下架或审核驳回的商品可以进入 AI 审核中；在售、待人工审核和已删除商品不能重复提交。
- 商品审核由卖家申请上架触发，不开放在用户聊天入口，也不允许智能客服调用审核工具。
- 管理员只处理进入待人工审核的任务；人工结论仍复用项目一的审核权限和状态机。

#### 申请上架怎么走

申请接口先完成一个短事务：

```text
校验登录态和商品归属
  -> 校验商品未删除且旧状态允许申请
  -> 固化本次 productVersion 和规则版本
  -> 条件更新商品为 AI 审核中
  -> 创建 reviewRunId 对应的 ai_agent_run
  -> 提交事务
```

条件更新用于防止卖家重复点击或两个请求同时启动审核。更新失败说明商品状态或版本已经变化，接口直接返回冲突，不再调用模型。事务提交后才启动审核 Orchestrator；无论本次请求同步等待还是异步执行，模型调用都不能占用数据库事务。

#### AI 审核任务怎么走

```text
1. 按 productId 和提交时的 productVersion 读取商品与图片
2. 先做确定性校验：必填字段、价格范围、类目、图片数量/格式/可访问性
3. 读取必要的卖家信用摘要，但只作为风险背景
4. 按任务记录的 ruleVersion 和生效时间检索 PRODUCT_RULE 规则片段
5. 组装商品快照、检查结果、规则片段和输出 Schema
6. 通过 Spring AI ChatClient 调用审核模型
7. 解析为 ProductReviewResult，并执行后端确定性校验
8. 校验通过后进入结果落库；失败则有限重试或转人工
```

发送给模型的是本次审核快照，不是让模型直接查询数据库。任务至少携带 `productId`、`productVersion`、`reviewRunId`、`promptVersion` 和 `ruleVersion`，这样后续可以判断结果针对哪一版商品、使用了哪一版规则。

#### 结构化输出和结果校验

`ProductReviewResult` 至少包含：

| 字段 | 作用 |
| --- | --- |
| `decision` | 只允许 `PASS`、`REJECT`、`NEED_MANUAL_REVIEW` |
| `riskLevel`、`confidence` | 表示风险与置信度，用于后端阈值和人工兜底 |
| `reasons`、`suggestions` | 给出审核原因和卖家可执行的修改建议 |
| `ruleRefs` | 只能引用本次实际注入的规则 ID，用于追溯依据 |

Spring AI 可以用 `BeanOutputConverter` 将模型结果解析为 DTO：

```java
ProductReviewResult result = chatClient.prompt()
        .system(reviewSystemPrompt)
        .user(productSnapshot)
        .call()
        .entity(ProductReviewResult.class);
```

Schema 只约束格式，不代表结果天然可信。后端还要执行 Bean Validation、枚举和跨字段校验：

- `REJECT` 必须给出原因，并引用当前任务实际提供的有效规则。
- `PASS` 不能同时包含禁止项或高风险命中。
- `ruleRefs` 出现注入集合之外的规则 ID 时，结果无效。
- 低置信度、规则冲突或依据不足统一改走人工审核。
- JSON 不合法或缺少字段时，降低 temperature 有限重试一次；仍失败记录 `AI_OUTPUT_INVALID` 并转人工。

规则引用只能说明结果可以追溯到哪些依据，不能声称已经证明模型内部推理过程。

#### 审核结果怎么落库

模型调用结束后，后端开启第二个短事务，并使用状态与版本条件更新：

```text
where id = ?
  and status = AI_REVIEWING
  and version = submittedProductVersion
```

只有条件更新成功，当前 run 才取得结果写入资格：

| 结果 | 后端动作 |
| --- | --- |
| `PASS` | 经过禁止项、规则引用和置信度校验后，将商品改为在售 |
| `REJECT` | 仅在明确命中有效规则时改为审核驳回，并保存原因和修改建议 |
| `NEED_MANUAL_REVIEW` | 将商品改为待人工审核，保留风险点和缺少的信息 |

状态更新、`product_review_log` 和 `ai_agent_run` 结果必须在同一个事务内完成。事务提交后再删除 Redis 和 Caffeine 商品详情缓存。

如果条件更新影响行数为 0，说明卖家在审核期间修改了商品、另一运行已经处理，或商品状态被人工改变。当前结果标记为过期，不得覆盖新状态，也不能因为旧内容通过就上架新内容。相同 `reviewRunId` 重复返回时也按同一条件处理，不重复推进状态。

#### 图片审核边界

如果第一版只接文本模型 `qwen-plus`，图片部分只能做数量、格式、大小、OSS 可访问性以及标题和描述中的文本风险检查，不能在面试中声称文本模型理解了图片内容。

真正检查二维码、联系方式、禁售品和图文不一致时，需要视觉模型或独立 OCR / 图像审核服务：

```text
私有图片生成短时签名 URL
  -> 视觉 / OCR 服务返回结构化标签和文字
  -> 审核 Agent 将视觉结果、商品字段和规则一起判断
  -> 签名 URL 到期，普通日志不保存永久访问地址
```

视觉结果仍是风险信号。图片模糊、服务不可用、图文冲突或高风险命中统一进入人工审核。

#### 人工审核和异常兜底

| 场景 | 处理方式 |
| --- | --- |
| 规则缺失或冲突 | 转待人工审核；这是平台依据不足，不能标记为卖家违规 |
| 模型超时、限流或供应商不可用 | 结束当前运行并转人工，不循环调用模型 |
| 结构化输出连续失败 | 记录 `AI_OUTPUT_INVALID`、模型/Prompt 版本和脱敏摘要后转人工 |
| 灰色风险或低置信度 | 保留风险点与规则引用，由管理员判断 |
| 审核期间商品版本变化 | 当前结果标记过期，卖家基于新版本重新申请 |
| 运行丢失或服务重启 | 定时扫描长期停留在 AI 审核中的商品，确认无活跃 run 后有限重试或转人工 |

人工通过后进入在售，人工驳回后进入审核驳回；两种结果都写审核日志，并在事务提交后删除商品详情缓存。

#### 事务、并发与幂等边界

这条链路拆成“短事务锁定审核版本 -> 无事务调用模型 -> 短事务写入结果”，避免模型响应数秒时长期占用数据库连接。并发与幂等依靠三层控制：

1. 申请阶段按旧状态和版本条件更新，防止重复创建有效审核。
2. 结果阶段按 `AI 审核中 + submittedProductVersion` 条件更新，防止旧结果覆盖新内容。
3. `reviewRunId` 标识一次运行；重复结果只有第一次成功更新状态，后续视为幂等结束。

数据库状态是最终事实。模型重试、服务重启、重复回调和定时补偿都复用同一套结果落库方法，不能维护两套状态推进逻辑。

#### 设计取舍

商品审核 Agent 的价值是处理非结构化商品内容并给出有规则依据的初审结果，不是获得数据库写权限。明确、低风险且通过全部后端校验的 `PASS` 可以触发自动上架，明确违规的 `REJECT` 可以触发驳回；不确定性和系统异常统一交给人工。

因此不能笼统地说“AI 完全不影响业务状态”，也不能说“模型直接决定上架”。准确表述是：**模型生成结构化审核建议，Java 后端通过规则引用、置信度、商品版本、权限和状态机校验后，才决定自动推进还是转人工。**

### 2.3 业务流 2：商品智能查询 Agent

商品智能查询是项目一商品搜索的 AI 增强层，不是新的交易入口。它把用户口语需求转换成可执行条件，再从平台真实在售商品中筛选、补充信息和解释推荐；商品是否存在、价格、库存和状态始终以数据库查询结果为准。

#### 整体流程

```text
智能客服转交 / 搜索页智能搜索
  -> 构造 ProductQueryTask
  -> 读取本轮明确条件和允许使用的用户偏好
  -> 检索 PRODUCT_KB，解释类目别名、属性和使用场景
  -> 生成 ProductSearchCondition
       ├─ hardConstraints：SQL 必须满足
       └─ softConstraints：用于排序，经用户确认后可有限放宽
  -> 判断条件是否足以执行查询
       ├─ 信息不足或歧义较大：向用户追问一个关键问题
       └─ 条件可执行：继续查询
  -> 商品搜索工具查询真实在售且有库存的候选
       ├─ 候选充足：继续补充信息和排序
       └─ 候选不足：询问用户是否接受放宽指定软条件
  -> 批量补充图片、卖家信用和评价摘要
  -> 在候选集合内排序并生成推荐解释
       ├─ 客服来源：返回客服统一组织回复
       └─ 搜索页来源：返回结构化结果给页面
```

#### 这条业务流解决什么问题

1. 把“适合写代码的便宜笔记本”等口语需求映射为类目、预算、配置和使用场景。
2. 在表达模糊或关键条件不足时主动澄清；在条件过多导致无结果时，由用户确认是否放宽软偏好。
3. 只基于真实候选生成推荐与风险提示，避免模型编造商品、价格、库存和卖家信息。

#### 两种入口和权限边界

| 入口 | 任务来源 | 结果返回 | 会话关系 |
| --- | --- | --- | --- |
| 智能客服转交 | 客服识别到 `PRODUCT_QUERY` 后构造 `ProductQueryTask` | 返回 `ProductQueryResult`，由客服组织最终回复 | 属于当前 `ai_session` |
| 搜索页智能搜索 | 用户直接提交自然语言搜索请求 | 条件足够时返回候选；条件不足时返回澄清问题和可选项 | 不强制创建聊天会话 |

搜索页入口仍要经过登录态、限流和参数校验，但不需要为了复用 Agent 强行制造一轮聊天。商品查询 Agent 只有商品、信用和评价的只读工具，不能调用下单、商品审核或纠纷处理能力。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `PRODUCT_KB` | 解释类目别名、属性映射、使用场景和常见风险 |
| `product` | 按状态、库存、类目、价格、校区和成色查询真实商品 |
| `product_image` | 批量补充候选商品封面和详情图 |
| `user_credit_summary` | 提供卖家信用摘要，作为排序和风险提示的背景 |
| `trade_review` | 提供近期评价摘要，不能替代当前商品事实 |
| `ai_user_memory` | 补充用户稳定偏好，但不能覆盖本轮明确条件 |
| `ai_agent_run`、`ai_tool_call_log` | 记录查询运行、工具参数摘要、候选规模、耗时和结果码 |

#### 查询任务怎么构造

客服和搜索页都要先构造同一个输入契约：

```text
ProductQueryTask
  queryTaskId
  queryText
  sourceType
  sessionId（搜索页可为空）
  explicitConstraints
  memoryHints
  clarificationHistory
  maxResults
  requestId
```

`explicitConstraints` 来自用户本轮明确表达；`memoryHints` 只包含经过治理且与当前查询相关的偏好。两者冲突时，本轮输入优先。例如画像记录“预算 1000 元”，但用户本轮明确说“最多 800 元”，最终上限必须是 800 元。

`queryTaskId` 标识一次完整查询，包括多轮澄清和放宽确认；每次用户提交仍使用新的 `requestId` 做单次请求幂等。`clarificationHistory` 保存当前查询已经问过的问题和用户回答，避免重复追问；它只属于当前查询任务，不直接写成长期用户画像。

#### 条件不足时怎么澄清

Agent 解析需求后先判断条件是否足以形成有意义的查询，而不是拿到一句话就立即查库。条件不足不等于字段没有填满；用户说“找一台 800 元以内的笔记本”已经可以先查，而“帮我找个合适的”“苹果可以吗”缺少明确对象或上下文，直接搜索容易得到大量无关结果。

建议先生成一个澄清判断：

```text
QueryClarification
  clarificationRequired
  missingFields
  ambiguousFields
  clarifyingQuestion
  clarificationOptions
```

澄清遵守以下规则：

1. 只有缺失信息会显著改变查询范围或用户意图时才追问，不能把搜索变成冗长问卷。
2. 一次优先问一个信息增益最高的问题，例如先问品类或用途，再问预算、校区和成色偏好。
3. 用户画像可以生成默认建议，但预算、品类等关键条件不能在用户不知情时用历史偏好静默补齐。
4. 客服入口直接把问题回复给用户并等待下一轮；搜索页返回 `clarificationRequired + clarifyingQuestion + clarificationOptions`，由页面展示输入框或选项。
5. 用户回答后合并到 `explicitConstraints`，沿用同一个 `queryTaskId` 重新构造任务，而不是开启一套新的查询逻辑。
6. 澄清轮数要有配置上限；达到上限仍不明确时，展示当前已获得的条件，让用户选择按宽泛条件查询或暂不搜索。

#### 自然语言条件怎么解析

Agent 检索 `PRODUCT_KB` 后生成 `ProductSearchCondition`，每个条件除值以外还要记录来源和是否允许放宽：

```text
ProductSearchCondition
  category、keywords、campus
  minPrice、maxPrice、conditionLevel
  hardConstraints、softConstraints
  source、relaxable
```

| 条件类型 | 示例 | 后端处理 |
| --- | --- | --- |
| 硬条件 | “预算最多 800”、指定校区、商品必须在售且有库存 | 转为 SQL 必选条件，不能自动放宽 |
| 软条件 | “最好九成新”、同义关键词、偏好的交易地点和排序方式 | 用于评分；候选不足时可以有限放宽 |
| 模型推断 | 根据“写代码”推断内存或硬盘偏好 | 只能作为软条件，并向用户说明 |

硬条件不由字段名称机械决定，而由用户表达强度决定。“必须同校区”是硬条件，“同校区最好”是软条件。后端只允许修改 `relaxable=true` 的条件，模型不能把预算上限等明确约束自行改掉。

#### 候选商品怎么查询和排序

```text
1. 后端校验 ProductSearchCondition 的字段、范围和枚举
2. 商品搜索工具使用硬条件查询 status=在售 and stock>0
3. 只取配置化数量的初始候选，避免把整张表送给模型
4. 批量查询图片、卖家信用和评价摘要，避免逐个 Tool Calling 形成 N+1
5. 使用可解释规则分处理软条件和风险项
6. 必要时让模型在真实候选集合内重排并生成理由
7. 后端校验最终商品 ID 必须属于本次工具返回集合
```

库存、价格和商品状态由 SQL 决定；模型只能在真实候选内部排序。若模型返回集合外商品 ID，该项直接丢弃并记录越界指标，不能再根据模型文本补造商品。

工具只返回生成结果需要的字段，并限制候选数、评价条数和字符串长度。初始候选上限、最终返回数量和是否启用模型重排都应通过页面容量、延迟和离线评测配置，不能写死成无法解释的数字。

#### 候选不足时怎么和用户确认

查询前的“条件不足”和查询后的“候选不足”是两件事。后者说明条件可以执行，但真实商品较少或为零；此时不能直接替用户放宽明确偏好。

```text
保留全部硬条件
  -> 找出导致结果过少的软条件
  -> 生成 suggestedRelaxations
       ├─ 客服入口：询问用户是否接受放宽
       └─ 搜索页入口：展示可勾选的放宽建议
  -> 用户确认后重新查询一次
       ├─ 有结果：返回结果，并记录 relaxedConditions
       └─ 仍无结果：返回暂无匹配，并提示可继续修改哪些条件
```

如果结果为零是硬条件造成的，例如“预算不超过 500 且必须某校区”，系统只能告诉用户冲突在哪里并询问他愿意修改哪一项，不能自行突破预算或校区。模型自己推断出的软条件可以直接移除，但要在结果中说明；用户明确说出的软偏好必须先得到确认。

模型不能无限追问或反复放宽，也不能在结果为空时编造商品。商品工具超时、数据库异常或 RAG 不可用时，返回可解释的降级结果；不能使用会话记忆猜测实时库存。

#### 结果怎么返回

统一输出 `ProductQueryResult`：

```text
ProductQueryResult
  queryTaskId
  clarificationRequired
  clarifyingQuestion
  clarificationOptions
  suggestedRelaxations
  appliedConditions
  items
  recommendationReasons
  risks
  relaxedConditions
  followUps
  knowledgeRefs
```

每个 `items` 中的商品 ID、价格、库存状态和卖家信息都来自本次工具结果。推荐理由可以解释“为什么匹配”，但不能承诺商品质量；风险提示要区分商品事实、卖家历史背景和模型建议。

当 `clarificationRequired=true` 时，`items` 可以为空，调用方应先向用户展示 `clarifyingQuestion`，不能把它当成“无商品”。客服入口只负责结合当前会话组织提问或结果，不能再次修改条件或新增候选；搜索页入口直接展示澄清选项、放宽建议或候选列表。两种入口复用同一查询 Service 和结果校验，避免出现两套推荐逻辑。

#### 一致性、性能和幂等边界

- 查询链路是只读流程，不开启覆盖模型调用的数据库事务。
- 搜索结果只是查询时快照，用户进入详情或下单时必须重新校验商品状态、价格和库存。
- 同一 `requestId` 的重复请求优先返回已有运行结果或避免重复记账，不能重复写入行为日志和 token 消耗记录。
- 同一查询的澄清回答要通过 `queryTaskId` 关联原任务和 `clarificationHistory`，避免每轮都从原始问题重新解析。
- 用户画像更新应从稳定的多次行为异步提取，不能把一次搜索直接写成长期偏好。
- RAG、模型重排或推荐解释失败时，仍可降级为普通结构化搜索结果。

#### 如何评测商品查询

离线数据集覆盖预算、校区、同义词、组合条件、无结果、软条件放宽和注入文本，重点统计：

1. 条件抽取准确率、澄清触发准确率、不必要追问率和澄清后查询成功率。
2. 商品真实性、在售率和库存有效率；这些由工具和后端校验，目标应为 100%。
3. 硬条件违反率、未经用户确认的软条件放宽率和放宽建议接受率。
4. Recall@K、NDCG@K 和人工相关性评分。
5. 无结果虚构率、候选集合越界率、平均澄清轮数和工具调用次数。
6. P95/P99 延迟、输入输出 token 和单次查询成本。

评测用于校准何时追问、问题顺序、候选上限、TopK、重排和 Replan 次数。没有真实结果时只说明数据集和指标，不编造推荐准确率。

#### 设计取舍

商品智能查询不是“让模型替数据库搜索”，也不是条件不全时自作主张。准确口径是：**RAG 和模型负责理解需求、识别缺失信息并提出澄清问题；用户决定关键条件和是否放宽偏好；数据库负责硬过滤与实时事实，模型只在真实候选内做有限排序和解释。**

### 2.4 业务流 3：智能客服入口、会话创建与 Agent 转交

智能客服是普通用户唯一的聊天入口，负责维护会话、理解问题、查询实时业务事实和解释平台规则。它可以把找商品请求转交给商品智能查询 Agent，但不能进入商品审核和后台纠纷判责流程。

#### 整体流程

```text
用户发送消息
  -> 校验登录态和会话归属
  -> 根据 requestId 保存用户消息，防止重复提交
  -> 读取会话摘要、最近消息和允许使用的用户画像
  -> 智能客服识别意图和缺失参数
       ├─ RULE_QA：检索规则后回答
       ├─ ORDER_QA：调用订单只读工具
       ├─ DISPUTE_STATUS_QA：调用纠纷进度只读工具
       ├─ PRODUCT_QUERY：构造 ProductQueryTask 转交商品查询 Agent
       └─ 意图不清 / 参数不足：先向用户追问
  -> 基于真实工具结果或规则片段生成回复
  -> 通过 SSE 返回，并保存 AI 消息、工具日志和规则引用
  -> 异步更新会话摘要；稳定偏好满足条件后再更新用户画像
```

智能客服是用户侧 Router，不是拥有所有能力的超级 Agent。真正的编排器仍是 Java 后端：后端决定本轮挂载哪些工具、允许多少轮调用、何时转交以及如何保存结果。

#### 这条业务流解决什么问题

1. 把规则咨询、订单查询、纠纷进度和商品查询统一收口到一个用户入口。
2. 结合会话摘要和最近消息理解连续问题，同时用 Tool Calling 获取实时事实。
3. 通过结构化路由、工具白名单和二次鉴权，防止模型越权查询或执行交易操作。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `ai_session` | 保存用户会话、状态和最后消息时间，查询时必须按当前用户隔离 |
| `ai_message` | 保存用户与 AI 消息、`requestId`、`sequenceNo`、状态和 token 使用量 |
| `ai_session_summary` | 保存较早对话的摘要和已摘要到的消息位置 |
| `ai_user_memory` | 保存经过治理的稳定偏好，只服务客服和商品查询 |
| `ai_agent_run` | 记录本轮意图、模型/Prompt 版本、运行状态、耗时和结果码 |
| `ai_tool_call_log` | 保存工具名、脱敏参数与结果摘要、耗时和错误码 |
| `ai_rule_reference` | 保存回答引用的规则版本和知识片段 |
| 项目一业务表 | 订单、商品和纠纷的权威事实，由受控工具实时查询 |

#### 会话和用户消息怎么创建

请求进入后先完成一个短事务：

```text
从登录态取得 currentUserId
  -> sessionId 为空：后端创建 ai_session
  -> sessionId 非空：按 sessionId + currentUserId 查询
  -> 按 requestId 检查本轮是否已经受理
  -> 分配 sequenceNo，写入用户 ai_message
  -> 创建本轮 ai_agent_run
  -> 提交事务
```

会话编号虽然由前端携带，但不能只按 `sessionId` 查询，否则用户可能读取他人会话。`requestId` 用于处理网络重试和重复点击；相同请求已完成时返回原结果，正在执行时返回当前状态，不重复调用模型和计费。

同一会话的消息必须有稳定顺序。`sequenceNo` 由后端分配并保证唯一，摘要使用 `summarizedUntilSequence` 标记处理边界，不能只依赖可能相同的创建时间。

#### MemoryContext 怎么构建

| 内容 | 作用 | 优先级 |
| --- | --- | --- |
| 当前用户消息 | 表示本轮明确需求 | 最高的自然语言约束 |
| 最近消息窗口 | 保留当前话题的直接上下文 | 高 |
| 会话摘要 | 压缩更早的目标、约束和待确认事项 | 中 |
| 用户画像 | 补充预算、校区、常看品类等稳定偏好 | 低于本轮明确表达 |
| 实时业务事实 | 通过工具获得的订单、库存和纠纷状态 | 业务事实最高 |

构建时先按 token 预算截取最近消息，再拼接摘要和与本轮相关的画像，最后加入实时工具结果。历史记忆若与当前工具结果冲突，必须以实时业务事实为准；订单状态和纠纷进度不能从旧对话中猜测。

#### 意图路由和 Agent 转交怎么走

路由结果至少包含 `intent`、`confidence`、`missingFields` 和是否需要工具。后端只接受预定义意图：

| 意图 | 后端动作 |
| --- | --- |
| `RULE_QA` | 检索 FAQ / ORDER_RULE，引用规则回答 |
| `ORDER_QA` | 提取订单编号，调用当前用户订单查询工具 |
| `DISPUTE_STATUS_QA` | 调用纠纷进度与材料要求工具，不输出判责建议 |
| `PRODUCT_QUERY` | 构造 `ProductQueryTask`，转交商品智能查询 Agent |
| `UNKNOWN` / 参数不足 | 生成澄清问题或人工入口，不猜测对象 |

客服转交商品查询时发送结构化 DTO，而不是把整段对话原样丢给另一个 Agent。商品查询返回 `ProductQueryResult` 后，客服只能组织表达，不能新增候选、突破硬条件或修改实时商品字段。

商品审核由卖家上架事件触发，纠纷辅助由管理员后台触发，永远不能成为普通用户路由的目标。

#### Tool Calling 怎么注册和鉴权

工具定义在普通 Spring Bean 中，只把当前意图需要的只读工具挂到本轮 `ChatClient`：

```java
@Tool(description = "查询当前用户参与的订单状态")
public OrderStatusView getOrderStatus(
        @ToolParam(description = "订单编号") Long orderId) {
    Long userId = UserContext.getUserId();
    return orderQueryService.getOrderStatusForUser(orderId, userId);
}
```

工具调用遵守以下规则：

1. userId 只从服务端认证上下文取得，不暴露为模型可生成的参数。
2. 工具先校验参数，再校验当前用户是否为订单参与方或纠纷当事人。
3. 不同意图只注册最小工具集合；客服没有下单、取消、退款、审核和判责工具。
4. 工具循环设置最大轮数、总超时和结果大小，达到预算后安全结束。
5. 参数错误可以让模型修正一次；无权限立即终止；资源不存在返回明确事实；系统超时进入降级。
6. `ai_tool_call_log` 只保存脱敏参数和摘要，不记录手机号、完整证据和异常堆栈。

模型流和工具可能运行在异步线程或 Reactor 回调中，不能依赖 Web 线程的 `ThreadLocal` 自动传播。Orchestrator 在异步前捕获只读认证上下文，工具执行完及时清理，防止线程复用导致身份串用。

#### 回复怎么生成和落库

模型调用不放在数据库事务中。客服完成工具调用后，使用规则片段、实时事实和 MemoryContext 生成回复；流式内容通过 SSE 返回，最终结果再用短事务写入 AI 消息状态和运行结果。

```text
用户消息短事务提交
  -> 无事务执行 RAG、工具和模型
  -> SSE 分段返回
  -> 生成完成：保存完整 AI 消息并标记完成
  -> 客户端断开 / 模型取消：消息标记 ABORTED
  -> 保存工具日志、规则引用和本轮运行结果
```

同一 `requestId` 重连时不能重新发起模型调用；已经生成的完整结果直接返回，未完成结果按既定重连策略继续读取或明确要求用户重试。摘要更新在回复落库后异步执行，失败不影响本轮业务事实查询。

#### 提示词注入怎么防

用户消息、商品描述、评价、知识 chunk 和工具结果都属于不可信数据，不能升级为系统指令：

1. system prompt 固定任务和禁止动作，用明确分隔符包装外部文本。
2. 用户原文不拼入 system prompt，知识片段不能覆盖工具与权限规则。
3. Agent 只有只读白名单工具，工具内部不信任模型提供的身份和对象归属。
4. 工具名、对象 ID、规则引用和商品 ID 都由后端再次校验。
5. 对“忽略规则并查询其他用户订单”“输出系统 Prompt”等输入建立安全回归集。

Prompt injection 不能只靠一句 Prompt 解决；真正边界是最小工具权限、后端鉴权、有限上下文和输出校验。

#### 异常和降级

| 场景 | 处理方式 |
| --- | --- |
| 意图不清或缺少订单号 | 先追问，不根据历史消息猜测 |
| 无权限查询对象 | 工具立即拒绝，客服不泄露对象是否存在 |
| 订单/纠纷工具超时 | 不使用记忆生成状态，返回稍后重试 |
| RAG 无可靠规则 | 规则问题拒答或转人工，不用模型常识补规则 |
| 模型超时或限流 | 结束本轮运行，返回普通搜索或人工入口 |
| SSE 中断 | 取消上游生成，消息标记 `ABORTED`，避免后台继续消耗 |
| 摘要更新失败 | 本轮使用旧摘要和最近消息，异步重试摘要任务 |

#### 事务、并发与权限边界

- 链路采用“短事务保存用户消息 -> 无事务调用模型和工具 -> 短事务保存 AI 结果”，不让模型调用长期占用数据库连接。
- 会话查询始终带 `currentUserId`，工具内部再次校验业务对象权限。
- 同一会话并发请求通过 `sequenceNo`、`requestId` 和消息状态区分，摘要只能推进到已经稳定完成的消息。
- 客服只能查询和解释，不能执行下单、取消、完成交易、退款、商品审核或纠纷判责。
- 会话记忆不进入商品审核和纠纷辅助，防止用户偏好污染高风险判断。

#### 设计取舍

把普通用户入口收口到智能客服，可以让前端只面对一个会话接口，同时让后端按意图挂载最小工具。准确口径是：**客服负责理解、路由和组织回复，商品查询 Agent 负责专用搜索；实时事实、身份权限、工具预算和结果落库都由 Java 后端控制。**

### 2.5 业务流 4：后台纠纷辅助处理 Agent

纠纷辅助 Agent 是管理员后台的证据整理能力，不对普通用户开放。它读取订单事实、商品快照、双方陈述、证据和适用规则，生成结构化辅助建议；最终是否补材料、如何处理以及是否结案仍由管理员决定。

#### 整体流程

```text
管理员打开纠纷审核页并触发辅助分析
  -> 校验管理员 / 平台审核角色
  -> 固化 disputeId、evidenceVersion、ruleVersion 和 analysisRunId
  -> 查询订单、商品快照、双方陈述、证据、信用和评价
  -> 按纠纷发生时间检索 DISPUTE_RULE
  -> 分层组装平台事实、当事人陈述和风险背景
  -> ChatClient 生成 DisputeSuggestion
  -> 后端校验结构、规则引用、证据版本和禁止动作
       ├─ 校验通过且证据版本未变：保存辅助建议，标记 AI_REVIEWED
       ├─ 证据版本已变：当前结果过期，基于新证据重新分析
       └─ 依据不足 / 输出越权 / 系统异常：转人工直接审核
  -> 管理员查看建议并作最终处理
```

`AI_REVIEWED` 只表示当前证据版本已有 AI 辅助结果，不代表纠纷已经结案，也不能替代项目一纠纷主状态和人工处理记录。

#### 这条业务流解决什么问题

1. 自动汇总分散在订单、商品快照、双方说明和证据中的信息，减少管理员整理时间。
2. 强制区分平台事实、当事人主张和 AI 推断，避免把单方说法写成已证实责任。
3. 根据纠纷发生时间引用正确版本规则，并保留完整的人机处理审计链。

#### 涉及数据

| 数据 | 作用 |
| --- | --- |
| `dispute` | 保存纠纷原因、双方陈述、证据、证据版本和人工处理状态 |
| `trade_order` | 提供订单时间、金额、状态、买卖双方和交易关系 |
| `product_snapshot` | 保存下单时的标题、描述、价格、成色和图片，是证据链核心 |
| `user_credit_summary` | 提供被申请人信用摘要，只作为风险背景 |
| `trade_review` | 提供近期评价摘要，不能证明当前纠纷责任 |
| `DISPUTE_RULE` | 提供当前案件适用的证据要求和人工处理规则 |
| `ai_agent_run` | 记录 `analysisRunId`、证据/模型/Prompt/规则版本、运行状态和结果码 |
| `ai_rule_reference` | 保存建议实际引用的 `ruleId`、版本和知识片段 |

#### 权限和触发边界

- 只有管理员或平台审核角色可以触发分析和查看完整辅助建议。
- 普通用户只能通过客服查询纠纷进度、材料要求和自己可见的信息，不能调用该 Agent。
- AI 只读取当前纠纷所需数据；管理员权限也不能让模型任意搜索其他订单和用户。
- 纠纷处理、退款、处罚和结案接口不注册为 Agent 工具，模型没有执行权限。

#### 分析任务怎么创建

管理员触发后，后端先用短事务创建一次可审计运行：

```text
校验管理员角色和纠纷存在
  -> 校验纠纷仍处于待人工处理范围
  -> 读取当前 evidenceVersion
  -> 根据交易 / 纠纷时间确定 ruleVersion
  -> 创建 analysisRunId 对应的 ai_agent_run
  -> 提交事务
```

任务至少携带 `analysisRunId`、`disputeId`、`evidenceVersion`、`promptVersion` 和 `ruleVersion`。重复点击可以返回当前活跃运行或已有同版本建议，不能为同一证据版本无限重复调用模型。

模型调用不放在事务内。分析期间允许当事人继续补充证据，但新证据会推进 `evidenceVersion`，旧运行即使完成也不能覆盖新版本结果。

#### 证据上下文怎么构建

```text
1. 查询纠纷主体和双方身份
2. 查询订单时间、金额、状态和交易关系
3. 查询下单时 product_snapshot，而不是当前可编辑商品
4. 读取双方陈述、证据文件元数据和必要的 OCR / 图像标签
5. 读取信用与近期评价摘要，只作为历史风险背景
6. 按 ruleVersion 检索 DISPUTE_RULE
7. 对敏感字段做最小化和脱敏后组装上下文
```

使用商品快照是为了还原交易发生时卖家承诺的内容。若只查询当前 `product`，卖家后续编辑标题、价格或图片会破坏证据链。

证据文件本身不直接塞入普通日志。私有图片使用短时签名 URL 交给受控视觉/OCR 服务，保存文件哈希、上传时间和结构化结果；签名地址到期后不可长期访问。

#### 事实、陈述和推断怎么分层

| 层级 | 示例 | 使用规则 |
| --- | --- | --- |
| 平台事实 | 订单时间、金额、状态、商品快照、证据文件哈希 | 来自数据库和工具，可作为客观事实 |
| 当事人陈述 | “商品与描述不符”“对方临时爽约” | 必须标注提交方和时间，只能称为主张 |
| 历史背景 | 信用摘要、近期评价 | 只能提示风险，不能证明本次责任 |
| AI 推断 | “可能存在描述偏差” | 只能放入 risks，不能写成已证实结论 |

纠纷材料、评价和 OCR 文本都属于不可信数据。即使其中出现“忽略规则”“自动退款”等指令，也只能作为证据内容，不能改变 system prompt、调用新工具或越过输出白名单。

#### 结构化输出和后端校验

`DisputeSuggestion` 至少包含：

```text
evidenceSummary
verifiedFacts
partyClaims
missingEvidence
ruleRefs
risks
suggestedNextStep
```

后端校验重点：

1. `verifiedFacts` 只能来自本次工具返回的平台事实。
2. `partyClaims` 必须保留陈述方，不能混入事实。
3. `ruleRefs` 只能引用本次注入且对当前时间有效的规则。
4. `suggestedNextStep` 只允许补充材料、人工复核、参考规则等白名单动作。
5. 出现自动判责、自动退款、封禁、处罚或关闭纠纷等内容，直接判为越权输出。
6. 证据不足时必须填写 `missingEvidence`，不能为了给出完整答案而虚构。

结构或枚举失败可以有限修正一次；仍失败、规则缺失或内容越权时，不保存为有效建议，管理员直接进入人工审核。

#### AI 建议怎么落库

模型返回后开启第二个短事务，先检查：

```text
disputeId 仍存在
  and 当前 evidenceVersion = submittedEvidenceVersion
  and 纠纷仍处于待人工处理范围
```

条件满足时，在同一事务中保存证据摘要、缺失证据、规则引用、风险和建议动作，更新 `ai_agent_run`，并把 AI 辅助状态标记为 `AI_REVIEWED`。条件不满足说明证据已更新、纠纷已被人工处理或另一运行已写入；当前 run 标记为过期，不覆盖新结果。

历史建议要保留使用的 `promptVersion`、`ruleId + ruleVersion + effectiveAt` 和 `evidenceVersion`。规则更新后不能悄悄重写旧建议；需要重新分析时创建新 run，并保留前后版本用于审计。

#### 人工处理怎么闭环

```text
AI 负责
  -> 证据链摘要
  -> 缺失证据
  -> 适用规则
  -> 风险提示
  -> 建议下一步

管理员负责
  -> 核对原始证据
  -> 要求补充材料或直接处理
  -> 写入最终处理结果和原因
  -> 记录处理人、处理时间并决定是否结案
```

管理员可以采纳、修改或拒绝 AI 建议。最终记录必须区分“AI 建议”和“人工决定”，不能把人工结果反写成模型原始输出。

管理员开始正式处理时，AI 辅助状态可以进入 `MANUAL_REVIEWING`；它仍只是处理进度标记。纠纷是否完成，最终以项目一人工处理接口写入的主状态、处理结果、处理人和处理时间为准。

#### 异常和人工兜底

| 场景 | 处理方式 |
| --- | --- |
| 证据或适用规则不足 | 明确列出缺失项，管理员直接审核或要求补材料 |
| 证据版本在分析期间变化 | 旧结果标记过期，按新版本重新运行 |
| 模型超时、限流或不可用 | 结束运行，后台仍展示原始证据供人工处理 |
| OCR / 视觉服务失败 | 不猜测图片内容，标记未解析证据并转人工查看 |
| 结构化输出失败或越权 | 有限修正一次；仍失败不保存为有效建议 |
| 重复触发同一证据版本 | 复用已有运行或结果，避免重复消耗和重复写入 |

AI 故障不能阻塞管理员处理纠纷。即使没有任何 AI 建议，项目一的人工审核链路仍然可用。

#### 事务、并发和审计边界

- 链路采用“短事务创建运行 -> 无事务聚合证据和调用模型 -> 短事务按证据版本写建议”。
- `evidenceVersion` 防止旧建议覆盖新证据，`analysisRunId` 用于幂等和完整链路追踪。
- AI 建议、规则引用和运行结果一起保存，但不修改人工处理结果。
- `traceId + requestId + analysisRunId` 串联后台请求、RAG、模型、工具和数据库日志。
- 普通日志只保存脱敏摘要；原始纠纷材料和完整模型输入输出进入受限存储并设置短保留期。

#### 规则版本和评测

纠纷不能一律使用“当前最新规则”。系统根据订单发生时间或纠纷事件时间选择当时生效的规则，并在建议中保存 `ruleId + version + effectiveAt`，使管理员能够复核依据。

评测使用脱敏历史案例或人工构造案例，由管理员标注关键事实、双方主张、缺失证据和适用规则，重点统计：

1. 关键事实和缺失证据覆盖率。
2. 规则引用准确率与时间版本正确率。
3. 事实/主张混淆率和越权结论率。
4. 人工采纳率、修改率和平均证据整理时间。
5. P95/P99 延迟、人工兜底率和单次成本。

人工采纳率只能衡量辅助价值，不能表述为“判责准确率”；最终责任由管理员承担。没有真实评测结果时，只说明评测集和指标。

#### 设计取舍

纠纷辅助的核心价值是整理证据和定位规则，不是替平台裁决。准确口径是：**AI 将事实、主张、缺失证据和规则整理成结构化建议；Java 后端控制权限、证据版本、输出白名单和落库，管理员作最终决定。**

### 2.6 支撑能力：RAG 知识库与在线检索

RAG 是四个 Agent 共用的知识支撑层，解决“回答、审核和建议依据从哪里来”的问题。它只提供可检索、可追溯的知识，不替代项目一数据库中的实时业务事实。

#### 知识域怎么隔离

| 知识类型 | 服务场景 | 作用 |
| --- | --- | --- |
| `PRODUCT_KB` | 商品智能查询 | 解释类目别名、属性映射、使用场景和风险提示 |
| `PRODUCT_RULE` | 商品合规审核 | 提供商品发布规范和禁止项 |
| `ORDER_RULE` | 智能客服 | 解释下单、取消、确认和超时规则 |
| `DISPUTE_RULE` | 纠纷辅助 | 提供证据要求和人工处理参考 |
| `FAQ` | 智能客服 | 回答高频平台问题 |

Agent 必须先确定知识类型，再执行检索；商品知识不能作为审核规则，当前订单状态也不能从规则文档中推断。

#### 存储和技术选型

第一版使用通义 `text-embedding-v3`，项目配置为 1024 维，向量存储使用 Spring AI `RedisVectorStore`。模型维度、Embedding API 参数和索引 Schema 必须一致；更换模型或维度后要重建索引。

选择 Redis VectorStore 是为了复用现有 Redis 体系，并满足第一版知识规模和元数据过滤需求。部署环境必须具备 Redis Stack / RediSearch；普通 Redis 不一定支持向量检索。如果环境无法提供 RediSearch，可以评估 pgvector，但迁移仍需重新向量化、重建索引、校准阈值和回归评测，不能理解为只改配置。

MySQL 保存知识原文、版本和元数据，是事实源；向量索引是可重建的派生数据。

#### 知识怎么入库和发布

```text
管理员维护文档
  -> 按标题、条款和语义段落切分
  -> 补充知识类型、来源、版本、权限和生效时间
  -> 写入 MySQL 新文档版本
  -> 调用 Embedding 生成 chunk 向量
  -> 校验 chunk 数量、向量维度和索引完整性
  -> 原子切换 activeVersion
  -> 异步清理旧索引
```

每个 chunk 至少保存 `documentId`、`chunkId`、`contentHash`、知识类型、标题、章节、版本、状态、可见范围、`effectiveFrom/effectiveTo` 和 `embeddingModelVersion`。

切分优先遵循条款边界，过长段落再按配置长度切分并保留少量重叠。chunk 大小不是固定答案，要通过召回评测校准。写 MySQL 成功但向量化失败时，新版本不能生效，线上继续使用上一个完整版本。

#### 在线检索怎么走

```text
识别意图和知识类型
  -> Query 改写
  -> 向量召回 + 关键词 / 规则编号召回
  -> 按知识类型、权限、状态和适用时间过滤
  -> RRF 或规则分合并去重
  -> 可选 reranker 重排
  -> 相似度阈值过滤
  -> 注入少量高相关 chunk
  -> 后端校验并保存 ruleRefs
```

向量检索擅长同义表达，关键词检索补充规则编号、状态名和固定术语等精确命中。候选数、TopK、阈值和是否启用 reranker 都是配置项；没有独立 reranker 时应明确使用 RRF 或规则分，不能只写一个无法解释的 `rerank`。

`ruleRefs` 只能引用本次实际注入的 chunk，后端校验后写入 `ai_rule_reference`。引用表示答案依据可追溯，不代表模型思维过程，也不能证明生成结果必然正确。

#### 时间、权限和安全边界

1. 客服通常查询当前生效规则；纠纷辅助按交易或事件时间选择历史有效版本。
2. 检索必须带知识类型、可见范围和生效时间过滤，不能只依赖相似度。
3. 没有可靠依据时，规则问答拒答或转人工，不能不断降低阈值让模型“总能回答”。
4. 商品知识只用于条件归一和解释，不能替代真实商品搜索。
5. 文档和 chunk 都视为不可信数据，导入时做权限审核和内容扫描；注入 Prompt 时明确标记为参考资料，不能覆盖 system 指令。
6. 不能把整本文档塞进 Prompt，只注入 token 预算内的高相关片段。

#### RAG 怎么验证

准备“问题 -> 相关 chunk / 适用规则”标注集，覆盖同义问法、规则编号、否定表达、跨条款、无答案和注入文本。检索层关注 Recall@K、MRR/NDCG 和过滤正确率；生成层关注忠实度、引用正确率、无依据拒答率和幻觉率；工程层关注延迟、空召回和索引构建失败。

Embedding、chunk、TopK、阈值或重排策略变化后必须回归。完整发布门禁和跨 Agent 指标统一放在 2.9，不在每条业务流重复展开。

#### 设计取舍

第一版使用自定义 RAG Service，便于显式控制知识域、元数据过滤、时间版本、阈值、重排和引用落库。后续可以使用 Spring AI Advisor 简化 Prompt 注入，但知识选择和来源校验仍由后端负责。

### 2.7 支撑能力：用户画像、会话记忆与滑动窗口摘要

用户记忆只服务智能客服和商品智能查询，帮助理解连续对话与稳定偏好。商品审核和纠纷辅助只使用当前业务对象、规则与工具事实，避免聊天记忆污染高风险判断。

#### 三类状态不要混淆

| 状态 | 保存位置 | 作用 |
| --- | --- | --- |
| 业务状态 | 项目一商品、订单和纠纷表 | 权威事实，只能由后端状态机修改 |
| Agent 运行状态 | `ai_agent_run`、当前执行上下文 | 记录任务、版本、工具、结果和失败原因 |
| 用户记忆 | 消息、会话摘要和 `ai_user_memory` | 辅助理解表达，不是业务事实源 |

模型本身不是状态存储。服务重启后，系统依靠数据库中的会话、运行、规则引用和业务状态恢复，而不是依赖模型“记得上次发生了什么”。

#### 记忆怎么分层

| 层级 | 内容 | 边界 |
| --- | --- | --- |
| 当前任务 | 本轮意图、明确条件、待确认项 | 本轮最高优先级，结束后不自动变长期记忆 |
| 最近消息 | token 预算内的近期原始消息 | 保留直接上下文 |
| 会话摘要 | 较早对话中的目标、约束和待办 | 只在当前会话生效 |
| 用户画像 | 稳定预算、校区、品类和交易偏好 | 低于本轮明确输入，可查看、修改和删除 |
| 实时事实 | 工具查询的库存、订单和纠纷状态 | 业务事实优先级最高 |

上下文冲突时遵守：**实时工具事实 > 平台规则 > 用户本轮明确输入 > 会话上下文 > 用户画像**。例如历史消息提到某商品，不代表它现在仍在售；订单状态必须重新查询。

#### 长期记忆为什么以 MySQL 为主

| 内容 | 主存储 | 原因 |
| --- | --- | --- |
| 原始消息 | `ai_message` | 需要审计、顺序、删除和保留策略 |
| 会话摘要 | `ai_session_summary` | 按用户和会话精确读取 |
| 用户画像 | `ai_user_memory` | 需要结构化修改、置信度、撤销和过期 |
| 非结构化历史记忆 | MySQL 原文 + 可选向量索引 | 只有确实需要语义回忆时再建立索引 |

即使未来建立记忆向量索引，它也只是派生数据。召回后必须通过 `memoryId` 回 MySQL 校验 `userId`、状态、有效期和撤销标记；修改或删除记忆后同步使缓存与向量失效，不能把不同用户的记忆放进无用户过滤的公共集合。

#### 会话摘要怎么更新

初始策略是“会话摘要 + 最近若干消息”，实际窗口按 token 动态调整，不能只按固定条数。滑出窗口的旧消息由异步任务压缩，摘要只保留目标、约束、已讨论对象、排除条件和待确认事项，不复制整段聊天。

摘要表保存 `summarized_until_sequence` 和 `version`：

```text
读取当前摘要版本和处理边界
  -> 只选择边界之后、已稳定落库的消息
  -> 生成增量摘要
  -> 按 version 条件更新摘要和新边界
       ├─ 成功：结束
       └─ 版本冲突：读取最新摘要后重试或放弃本轮
```

摘要任务失败不影响当前请求，下次继续重试；原始消息按统一保留策略清理，不能在摘要成功后立即删除。

#### 用户画像怎么生成和治理

模型只能提出“记忆候选”，不能直接把一句话写成长期画像：

```text
回复完成后异步提取候选偏好
  -> 校验字段类型、敏感性、来源和置信度
  -> 用户明确确认或多次稳定表达
  -> 新增 / 提高置信度 / 降低冲突旧值置信度
  -> 到期、用户删除或撤销后失效
```

| 可以保存 | 不允许保存 |
| --- | --- |
| 稳定预算区间、常用校区、偏好品类、交易方式、成色偏好 | 联系方式、身份证明、详细住址、完整聊天原文、纠纷结论、一次性情绪 |

`ai_user_memory` 至少保存类型、规范化值、置信度、来源会话/消息、状态、有效期和更新时间。一次性需求留在当前任务；冲突时不直接覆盖旧值，而是保留来源并调整置信度。用户应能查看、修改和删除自己的画像。

#### MemoryContext 怎么组装

业务流 3 已描述客服完整链路；支撑层只负责按预算提供上下文：

```text
校验当前用户和会话
  -> 读取本轮消息与当前任务
  -> 读取会话摘要、最近消息和相关画像
  -> 去重、隐私裁剪并按优先级压缩
  -> 交给客服查询实时事实和对应规则
```

历史消息、摘要和画像都视为不可信数据，不能覆盖 system 指令或触发未授权工具。记忆中出现订单号也不代表当前用户有权查看，工具每次仍要重新鉴权。

#### 隐私和生命周期边界

1. 所有记忆查询都按当前登录用户隔离。
2. 向模型发送前只保留完成任务所需字段，对姓名、手机号和证据地址等敏感信息脱敏。
3. 明确第三方模型供应商的数据保留、训练使用和访问策略，不能默认外部模型不会留存数据。
4. AI 消息、摘要、工具日志和画像分别设置访问权限与保留期限。
5. 预算、校区和交易偏好组合后仍可能识别个人，不能因为单字段低敏就无限期保存。
6. 记忆缓存只提高读取速度，MySQL 才是事实源。
7. 模型调用不放进数据库长事务，消息和摘要使用短事务独立落库。

### 2.8 支撑能力：SSE 流式输出与 Token 预算控制

SSE 只用于智能客服这类用户可见的长文本回复；商品审核和纠纷辅助返回结构化结果，不需要逐 token 展示。

#### 为什么使用 SseEmitter

项目主体是 Spring MVC，只有客服接口需要服务端单向推送，因此使用 `SseEmitter`，不为单个场景引入完整 WebFlux。SSE 基于 HTTP、浏览器支持重连，适合服务器持续向客户端推送；它不等于模型生成可以自动续传。

#### 流式回复怎么走

```text
短事务创建 ASSISTANT 消息，状态为 GENERATING
  -> 返回 messageId 并创建 SseEmitter
  -> 订阅 ChatClient 流
  -> delta 事件逐段发送，同时在内存中受限聚合完整回复
  -> 正常结束：发送 done，短事务保存全文并标记 COMPLETED
  -> 超时 / 断开 / 异常：取消上游，标记 ABORTED 或 FAILED
```

完整回复只在结束时落库，不逐 token 写数据库。聚合缓冲区必须有最大长度；超过输出预算时主动终止，不能让异常响应占满内存。

SSE 事件协议保持稳定：

| event | 内容 |
| --- | --- |
| `meta` | `requestId`、`sessionId`、`messageId` |
| `delta` | 新增文本和递增 `sequence` |
| `tool_status` | 可公开的“正在查询订单”等状态，不暴露参数 |
| `done` | 最终状态、usage 摘要和最后 sequence |
| `error` | 对用户可见的错误码和是否可重试 |
| `heartbeat` | 连接保活，无业务内容 |

#### 断线、重连和幂等

浏览器断线重连只恢复 HTTP 连接，不保证恢复供应商模型流。客户端必须携带原 `requestId`：

- 消息已完成：返回已保存全文，不重新调用模型。
- 消息仍在生成：按当前实现返回状态或等待，不能再创建第二次运行。
- 消息已 `ABORTED/FAILED`：明确提示重试；新请求使用新 requestId。

如果未持久化每个 delta，就不能宣称支持从 `Last-Event-ID` 精确续传。客户端断开、`send()` 抛异常或超时时，要显式取消上游 `Subscription/Disposable`；同时监控供应商是否真的停止生成和计费。

#### 连接和线程怎么控制

模型流回调使用专用有界线程池或调度器。监控活跃连接、队列长度、平均持续时间、首 token 延迟、取消率和发送失败；达到并发上限时快速返回系统繁忙，不能无限创建异步任务。

`onTimeout`、`onError` 和 `onCompletion` 统一执行取消订阅、清理上下文和消息状态收敛。heartbeat 间隔要与网关、代理空闲超时协调。

#### Token 预算怎么控制

```text
确定模型上下文上限
  -> 为输出预留配置化预算和安全余量
  -> 按优先级装入实时事实、规则、本轮输入、会话上下文和画像
  -> 超预算时从低优先级开始裁剪
  -> 调用后根据 usage metadata 记录实际 token 和费用
```

裁剪顺序复用 2.7 的事实优先级：先去掉无关画像，再压缩较早会话内容，最后减少低相关知识片段；实时业务事实和用户本轮硬条件不能因为省 token 被裁掉。

优先使用与模型匹配的 tokenizer；没有 tokenizer 时保守估算并留余量。每个 Agent 配置输入、输出、工具轮数、澄清/Replan 次数和用户每日额度。简单意图分类可以使用规则或小模型，高成本 reranker 或大模型只在评测证明有收益时启用。

#### 设计取舍

SSE 优化的是等待体验，不改变业务正确性。可靠性依赖 `requestId` 幂等、消息状态、上游取消和最终全文落库；Token 预算同时控制上下文溢出、延迟和费用。

### 2.9 支撑能力：AI 数据表、评测、可观测性与降级

这一节集中描述跨 Agent 的数据、质量和可靠性治理，避免在每条业务流重复同一套表、日志和降级原则。

#### AI 侧核心表

| 表 | 关键字段与作用 |
| --- | --- |
| `ai_session` | 用户、标题、状态和最后消息时间 |
| `ai_message` | 会话、`sequence_no`、role、content、status、`request_id`、token |
| `ai_session_summary` | 摘要、处理边界、version 和更新时间 |
| `ai_user_memory` | 类型、值、置信度、来源、状态和有效期 |
| `ai_agent_run` | runId、Agent、业务对象及版本、模型/Prompt/规则版本、状态、耗时和结果码 |
| `ai_tool_call_log` | runId、工具、脱敏参数/结果摘要、耗时和错误码 |
| `ai_rule_reference` | runId、ruleId、chunkId、规则版本、相似度和引用位置 |
| `ai_knowledge_document/chunk` | 原文、版本、有效期、chunk 元数据和 embedding 状态 |

AI 表保存会话、运行审计、知识和派生建议，不替代项目一商品、库存、订单和纠纷表。

#### 关键状态和约束

- `ai_message` 使用 `GENERATING / COMPLETED / ABORTED / FAILED` 表示流式消息状态，`request_id` 用于请求幂等。
- `ai_agent_run` 至少区分 `RUNNING / SUCCEEDED / FAILED / STALE`，旧业务版本结果标记 `STALE`，不能覆盖新状态。
- 同一会话的 `sequence_no` 唯一；runId 全局唯一；规则引用按 runId 和 chunkId 去重。
- 业务对象版本、证据版本、规则版本和 Prompt/模型版本都要进入运行记录，保证结果可复现和可解释。
- AI 日志与建议可以删除或过期，但不能破坏项目一业务审计记录。

#### 三层测试与评测

1. **确定性测试**：参数、权限、状态机、DTO Schema、引用白名单、版本条件更新和幂等。
2. **Agent 回归集**：固定输入检查路由、条件抽取、工具选择、结构化输出、无依据拒答、澄清、超时和注入攻击。
3. **端到端评测**：固定版本组合，统计质量、延迟、token、费用、人工兜底率，并抽样人工复核。

| 场景 | 核心指标 |
| --- | --- |
| 商品审核 | 高风险召回、误拒、结构化成功、人工兜底、旧版本结果拦截 |
| 商品查询 | 条件/澄清准确、硬条件违反、Recall/NDCG、虚构和越界商品率 |
| 智能客服 | 意图与工具选择、答案忠实度、一次解决率、越权率 |
| 纠纷辅助 | 事实/主张混淆、规则引用、缺失证据覆盖和越权结论率 |
| RAG | Recall@K、MRR/NDCG、引用正确和无答案拒答 |
| 工程 | P95/P99、首 token、超时、取消、token/次、成本/次、供应商错误 |

没有真实评测结果时只描述数据集、指标和门禁，不编造准确率或性能数字。

#### 版本发布和回滚

模型、Prompt、Embedding、chunk、TopK、阈值和工具描述共同组成一次 AI 配置版本。任何一项变化都可能改变结果，发布前应：

```text
绑定候选版本
  -> 跑固定回归集和安全集
  -> 与当前版本比较质量、延迟和成本
  -> 通过门禁后小流量验证
  -> 指标异常切回上一完整版本
```

知识新版本只有在 MySQL、Embedding 和索引都完整后才能激活。模型供应商切换也必须重跑结构化输出、Tool Calling、RAG、流式 usage、延迟和成本评测；Spring AI 只降低接入代码耦合，不能消除模型行为差异。

#### 可观测性和隐私

`traceId + requestId + runId` 串联 HTTP、RAG、模型、工具和数据库。Dashboard 关注调用量、成功率、超时、格式失败、工具轮数、RAG 空召回、澄清率、人工兜底、token 和费用；告警要能定位到 Agent、模型和版本。

普通日志不保存完整 Prompt、手机号、证据 URL 和原始纠纷材料。确需排查的模型输入输出进入加密、RBAC、访问审计和短保留期的受限存储；向第三方模型只发送完成任务所需的最小字段。

#### 模型调用可靠性

| 项 | 规则 |
| --- | --- |
| 超时 | 分开配置连接、首 token 和总生成超时，超过场景总时限立即取消 |
| 重试 | 只对网络抖动、限流和可重试 5xx 做带退避的有限重试 |
| 预算 | 限制工具轮数、澄清/Replan 次数、结果大小、token 和总耗时 |
| 限流 | 按用户、Agent 和全局并发限流 |
| 熔断 | 供应商持续故障时暂停调用，进入场景兜底 |
| 幂等 | runId、requestId 和业务版本共同防止重复执行或旧结果覆盖 |
| 审计 | 保存版本、工具摘要、规则引用、耗时、token、结果码和兜底原因 |

业务拒绝、无权限、参数错误和 Schema 业务校验失败不能当成网络异常反复重试。

#### 全局降级矩阵

| 故障 | 降级 |
| --- | --- |
| 模型不可用或限流 | 客服返回普通搜索/人工入口；审核和纠纷转人工 |
| VectorStore 不可用 | 实时工具仍可用；规则类问题无依据则拒答或转人工 |
| Embedding 入库失败 | 新知识版本不生效，继续使用上一个完整版本并告警 |
| 工具超时 | 不使用记忆猜测实时状态，提示稍后重试 |
| 结构化输出失败 | 有限修正；仍失败进入对应人工或安全兜底 |
| SSE 断开 | 取消上游并标记 `ABORTED`，同 requestId 不重复生成 |
| 摘要任务失败 | 使用旧摘要和最近消息，异步重试 |

降级原则是“保留确定性能力，关闭不可靠的 AI 增强”。AI 故障不能阻塞普通商品搜索、项目一交易流程和管理员人工审核。

### 2.10 设计取舍与面试追问

#### 系统定位

更准确的定义是：

> **面向垂直业务的、受控工作流型多 Agent 系统。**

这里的 Agent 不是一个 Prompt，而是“目标 + 业务上下文 + RAG/工具 + 有限决策循环 + 输出契约 + 后端护栏”。模型处理自然语言和不确定性，Java 后端负责身份、权限、版本、状态机、确定性校验和最终写入。

#### 为什么四个 Agent 使用不同范式

| Agent | 主要范式 | 自主边界 |
| --- | --- | --- |
| 智能客服 | Router + 受约束 ReAct | 在白名单只读工具内选择行动，信息不足先追问或转交 |
| 商品查询 | 受约束 Plan-and-Execute | 规划查询条件；关键条件先澄清，放宽用户偏好需确认 |
| 商品审核 | RAG-augmented Evaluator | 固定审核步骤和结构化输出，后端校验后才能改状态 |
| 纠纷辅助 | Evidence + Generate-Validate + Human-in-the-loop | 只整理证据和规则，管理员最终处理 |

任务越高风险、步骤越确定，模型自主空间越小。项目没有为了“更像 Agent”把所有能力都套成开放式 ReAct。

#### 统一执行骨架

```text
Trigger
  -> Authorize
  -> Build Context
  -> Decide / Plan
  -> Act with Whitelisted Tools
  -> Observe
  -> Generate
  -> Validate
  -> Commit / Handoff / Fallback
  -> Audit
```

`Authorize`、`Validate` 和 `Commit` 必须由后端执行。Agent 之间通过任务 DTO 和结果 DTO 通信，不使用无法约束的自然语言群聊；智能客服只是用户侧 Router，真正的 Orchestrator 是各业务 Service 和 Java 编排层。

#### 关键设计取舍

| 取舍 | 选择 | 原因 |
| --- | --- | --- |
| 通用 Agent vs 领域 Agent | 四个领域 Agent | 工具最小权限、知识隔离、独立 Schema、评测和降级 |
| autonomy-first vs workflow-first | workflow-first | 交易状态明确，高风险写操作必须可审计 |
| 完整 ReAct | 只在客服使用受约束循环 | 审核和纠纷不需要开放探索 |
| 完整 Plan-and-Execute | 只让商品查询规划条件 | 执行步骤和工具由后端固定 |
| 完整 Reflexion | 不使用 | 不保存跨任务自我反思，只做 Generate-Validate-有限修正 |
| 模型直连数据库 | 不允许 | 读取走工具，写入走权限、版本和状态机 |
| 一个模型承担全部任务 | 按评测决定 | 简单路由可用规则/小模型，高风险与生成任务优先质量 |

不使用完整 Reflexion，是因为错误反思可能污染后续任务，高风险场景更需要确定性校验、有限重试和人工兜底。项目记录可审计的意图、工具、结果和失败原因，不保存或展示模型私有思维链。

#### 30 秒面试回答

> 我们做的是受控工作流型多 Agent，不是完全自治的通用 Agent。系统按商品审核、商品查询、智能客服和纠纷辅助拆分，每个 Agent 有独立知识域、工具白名单、任务 DTO、输出 Schema 和失败兜底。客服可以在只读工具内做有限 ReAct，商品查询在条件不足时先澄清，再生成受约束条件；审核和纠纷采用固定流程与人工确认。模型负责理解和生成，权限、业务版本、状态机和最终写操作始终由 Java 后端控制。

#### 高频追问

**1. 这算 Agent，还是普通 LLM Workflow？**

> 两者不是非黑即白。审核和纠纷更偏 Agent Workflow；客服和商品查询会根据上下文选择工具、追问、转交或有限重查，Agentic 程度更高。统一称为领域 Agent，是因为它们具备目标、上下文、工具、有限循环和护栏，但不是自治系统。

**2. 为什么不用一个通用 Agent？**

> 通用 Agent 会同时拥有商品、订单、审核和纠纷工具，权限过大、Prompt 互相干扰，也难以分别设计 Schema、评测和人工兜底。领域拆分后，每个 Agent 只获得完成任务需要的最小能力，底层确定性 Service 仍然复用。

**3. 多个 Agent 怎么通信，谁负责调度？**

> Agent 之间用后端定义的 DTO 通信，例如客服发送 `ProductQueryTask`，商品查询返回 `ProductQueryResult`。Java Orchestrator 负责路由、认证上下文、超时、预算、日志和异常；客服只负责用户侧意图路由。

**4. 如何防止无限调用、越权和幻觉？**

> 每个 Agent 有工具白名单、轮数/时间/token 预算和输出 Schema；工具内部重新鉴权，实时事实只来自工具，结果还要校验候选集合、规则引用和业务版本。达到上限、无可靠依据或校验失败时安全返回或转人工。

**5. 为什么没有完整 Reflexion？**

> 当前只有 Generate-Validate-有限修正，不把模型反思写入长期记忆。审核和纠纷属于高风险短链路，错误经验可能放大风险，确定性校验器和人工兜底更可控。

**6. Agent 如何测试和发布？**

> 分确定性单测、固定 Agent 回归集和端到端评测三层；模型、Prompt、知识索引和工具描述绑定版本。候选版本先比较质量、安全、延迟和成本，通过门禁后再验证，异常时回滚上一完整版本。

#### 最核心原则

> **大模型负责不确定性，后端负责确定性；读取通过受控工具，写入经过权限、版本和状态机；低风险场景允许有限自主，高风险场景必须结构化校验和人工兜底。**
